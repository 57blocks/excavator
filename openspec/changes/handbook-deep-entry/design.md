## 决定

- **D1 条目格式 `/2`**：`operations[]` 的每一项在 `name` 与 `sentences`（步骤，按顺序）之外加五个列表，每个元素带 `evidence`：
  - `triggers`：`{text}`，这条流程由什么开始，例如页面上的按钮、一个路由、一个定时任务、另一个系统的调用。
  - `calculations`：`{text}`，算什么、用哪些输入、怎样取整、上限是多少。
  - `changes`：`{text}`，存下或改动了什么数据。
  - `edges`：`{when, then}`，边界情况或出错的分支。
  - `handoffs`：`{feature, text}`，`feature` 是地图里另一个功能的 id，不能是自己。

  条目顶层另加 `transitions`：`{from, to, by}`。`from` 与 `to` 按标签核对，必须出现在本项引文里；`by` 是叙述。

  键名沿用 `sentences`，不改成 `steps`：取舍是少改十几处读它的代码，代价是名字和含义差一点。

  每个新元素是一个核对项：
  - 主张里带操作名和这一部分的固定文字名，与现在的步骤句一样；
  - 数字按值核对，`feature` 不是读者可见的文字。

  一个操作没有步骤句留下时，它的其他部分随之删去，按 `withParent` 记录，与现在的规则一致。

  兼容方式：
  - `/1` 条目在 `settled` 读取路径上照常通过，缺的列表按空处理；
  - 未定案的条目必须是 `/2`；
  - 改写时格式保持第一轮的格式。
- **D2 一项一件事、每步引它自己**：写作提示要求：
  - 一句步骤只说一件事。
  - 每句步骤引用这一步自己的代码：处理函数、调用、查询或判断条件。
  - 一句里有两件事就拆成两句。

  依据：一次真实运行里，第一名核对者没确认的项占 34%，大多是一句里合了几件事，或者引文只证了其中一件。
- **D3 读出去的上限 40 个文件**：种子之外最多打开 40 个文件，原来是 20 个。更深的内容需要读到服务层和查询。上限仍在，用完就写进「无法确定的内容」。
- **D4 时序图的画法**：
  - 发起者由功能的到达方式决定：菜单或链接是「用户」，自动是「定时任务」，接口是「外部系统」，命令是「操作员」。这几个名字放在固定文字表。
  - 每句步骤取第一段引文的文件，落在哪个应用根目录下（与系统概览用同一份应用根）就是哪个参与者。概览已核实时用它给该应用起的名字，否则用目录。不在任何根下的文件用固定文字「其他代码」。
  - 箭头只标序号：图里写长句会撑破版面，截断句子又可能改变意思。
  - `handbook.md` 用 mermaid 的 `sequenceDiagram` 与 `stateDiagram-v2`。参与者与状态的名字做转义：只保留文字，引号和换行替换掉。
  - 页面：时序图用 React 画内联 SVG，参与者是列，箭头按序号自上而下；状态转换在页面上列成「从 → 到：由什么」的行。不画状态图，是因为状态图要做图布局，代价大；`handbook.md` 里有状态图。
  - 不打包 mermaid：mermaid 有几 MB，还要放宽 CSP。
- **D5 追查按类别**：功能条目的 `traceItems` 跳过 `purpose`、`where[]`、`screens[]`、`screens[].fields[]` 这几类项，它们的主张只有标签或一句用途。概览、发现与系统发现的追查不变。

  一次 72 个功能的运行里，这几类共 900 个追查项，两名追查者一次反证都没给出。追查项因此减少约三分之一，约占总花费的 10%。代价是这几类只有两名核对者把关。覆盖一节用一行固定文字写明，附录的资料来源照旧计数。

  字段规则（`fields[].rules`）、角色、步骤、通知、状态、转换、自动行为、流程的新部分，以及发现，都照旧追查。
- **D6 提示缓存**：写作提示把固定说明放在前面，随功能变化的部分放到最后一段：功能 id、名字、到达方式、种子文件、入口、其他功能、角色和外部名字。字面内容不变，只调顺序。
- **D7 页面数据 `/16`**：
  - 条目的操作带上新的五个列表；
  - 每句步骤带算出的参与者，每个操作带参与者列表；
  - 条目带 `transitions`；
  - 交接带被交接功能的名字，方便页面链过去。

  分块形态照旧：操作仍随功能单元分块。
- **D8 主题事实**：`topic-facts` 给新的项也各出一行，类别名分别是 `trigger`、`calculation`、`change`、`edge`、`handoff`、`transition`。其中交接一行带被交接的功能。主题的写法和判定不变。
- **D9 不做第二名核对者只看第一名确认的项**：如果第一名没确认的项第二名就不必看，第二名能少看约三分之一，但只省总花费的 7% 左右。代价是：
  - 每一轮核对要从并行改成先后两波，每轮多一波等待；
  - D2 预计会降低第一名不确认的比例，省下的会更少。

  所以不做。
- **D10 不在本变更里做阅读材料打包**：事实图（调用、导入、定义位置）由 `lazy-analyze` 写进项目的 `.excavator`，手册规定不读也不写它。要打包，得先让事实图能写到项目之外，这是 core 的改动。

  试点时在语料的一份一次性副本上跑一次 `lazy-analyze`，量两个数：
  - 写作者实际打开的种子之外的文件里，有多少能从种子沿一跳的调用或导入边到达；
  - 有多少只能靠同目录或搜索找到。

  据此决定是否另开变更。

- **D11 左侧导航分组、可折叠**：原来的导航是一列 15 个入口，下面再接全部领域和功能，读者找不到层次。改成：
  - 概览单独放在最上面；
  - 其余入口分三组，每组一个标题：产品（角色矩阵、通知、定时任务；技术视角另有应用矩阵、数据、状态字典）、评估（发现、建议、横切主题、代码健康）、附录（覆盖、待确认问题、术语表、来源与范围）；
  - 下面的功能树（产品视角按领域，技术视角按应用）每个领域或应用可折叠，标题旁写功能数；
  - 每组、每个领域默认收起，只展开含当前页面的那一组或那一个领域，所以从概览进来时导航只有概览、三个组名和各领域名。

  用原生 `details`/`summary`，不加脚本状态；组名都来自固定文字表。代价：收起的入口要多点一次。没有选「各组常开、只折叠领域」，因为常开时入口仍是一长列，正是要解决的问题。

## Oracle

- **O1 脚本测试**（先红后绿）：
  - `/2` 的形状接受与拒绝：交接指向未知 id 或自己时拒绝；转换的状态名不在引文里时拒绝；新写的 `/1` 被拒绝。
  - 已定案的 `/1` 能拼装。
  - 新部分各成一个核对项，主张带操作名与部分名。
  - 一个操作的步骤全删后，其他部分随之删去并记录。
  - 追查文件不含 D5 的几类。
  - 时序图的参与者与箭头按 D4 算出，两次输出逐字节相同。
  - mermaid 的转义正确。
  - 主题事实含新类别。
- **O2 页面测试**：
  - 功能页显示触发方式、带序号的步骤、SVG 时序图、计算、数据变化、边界情况、交接链接与转换；
  - `/1` 数据照常显示；
  - 固定文字都来自表。
- **O6 导航测试**：概览单独在最上面；三个组按序出现，组名来自固定文字表；技术视角的产品组多出三项；当前页面所在的组与领域是展开的，其余收起；每个领域标题旁有功能数；原有的导航测试照常通过。
- **O3 变异**：交接 id 检查、转换的标签检查、追查跳过的类别、参与者的确定、序号编排，各做一个变异，至少一个测试变红。
- **O4 最小真实运行**（go-multirepo，用 Sonnet 运行，这是测量条件，不是 skill 的选择）：
  - **对象**：一个从菜单到达、47 个入口的功能。
  - **准备**：从上一次全量输出复制地图、候选、领域、固定文字到两个新的输出目录。`--sections features --features <id> --language Chinese`，与全量运行同样的 `--views`。
  - **对照**：一个目录用本变更之前的检出，一个用本变更的检出。
  - **量**：
    - 花费、墙钟、写作者的轮数与打开的文件数；
    - 写出的项、核对删去、追查删去，按类别分；
    - 追查项数。
  - **内容**：
    - 新格式的操作数、步骤数，以及触发、计算、数据变化、边界、交接、转换各几项；
    - 拿参考手册里同一功能列出的流程与步骤做召回清单，逐条判覆盖、缺失或矛盾。参考手册只用于验收，不进入运行。
  - **精度**：一个独立的审读子代理读源码，把新格式留下的全部项逐项判为成立、不成立或证据不足。
  - **D10 的测量**：在一份一次性副本上跑。
- **O5**：
  - 本地跑受影响的测试、模板检查、`check-refs` 与 `openspec validate --all --strict`；
  - 全量门交给 CI；
  - 源码零非 ASCII 字符；
  - 名字扫描无命中。

## 风险

- **内容多了，核对与追查的项也多了**：花费按项数增长。D5 抵消一部分。O4 按每个留下的项算花费，与旧格式比。
- **深的内容更难证**：删除比例可能上升。O4 按类别报，一类删得太多就回头调提示，不调核对。
- **时序图只是排布**：参与者来自引文位置，不来自调用关系。一句步骤引了前端文件，但说的是后端的事时，图会画错位置。这类句子过不了核对（引文证不出它）。图下的固定文字说明了画法。
- **全部追查项被推翻的功能仍算已核实**：D5 之后，用途、导航路径、界面与字段标签不进追查。一个功能的被追查项全被推翻时，它只剩这些标签，状态仍是已核实。删除记录列出每一项，覆盖一节有说明。
