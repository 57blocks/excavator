## Context

动机见 proposal.md。现状：
- `skills/excavator-product-handbook/` 有 165 个库模块、约 1.48 万行，`handbook.mjs` 有约 40 条命令；
- `packages/product-handbook-page/` 有 34 个组件，从结构化 JSON 拼出实体页、矩阵与流程图；
- 测试目录有 95 个文件。

`excavator-prd-report` 引用了本 skill 的 `lib/entrypoints.mjs` 与 `lib/normalize.mjs`，这两个模块属于保留的候选部分。

对照试验的提示词、产出与盲审记录在私有语料的运行目录里，不进仓库。仓库里只记机制与数字。

## Goals / Non-Goals

**Goals**
- 模型写的部分全部改成散文提示词加 Markdown。
- 脚本只做四类事：候选与守恒、结构化事实、收尾检查、拼装与页面。
- 跨功能章节不再读代码，主题通道从约 39 条合并成 1 条。

**Non-Goals**
- 不加回任何核对者或追查者。
- 不做逐句的意思核对：没有逐句核对这件事，由每章开头的固定文字说明。
- 不保留旧输出目录的续跑。
- 不改候选列表、数据、状态字典与代码健康的算法。

## Decisions

### D1 留下的命令

`candidates`、`applications`、`check-map`、`select`、`check-ui`、`data`、`history`、`check`、`assemble`、`page`、`reply`、`sections`，共 12 条。

| 命令 | 为什么不交给模型 |
|---|---|
| `candidates`、`applications`、`check-map`、`select` | 候选必须是完整全集，守恒是零模型的确定性检查 |
| `data`、`history` | 结构化事实不让模型转写 |
| `check` | 散文里的要求在压力下会被省掉，要有确定性的地板 |
| `assemble`、`page`、`reply` | 纯机械拼接与渲染 |
| `check-ui` | 固定文字表的键与占位符核对 |

`sections` 打印本次要读的阶段文件，沿用。

**否决的做法：** 把守恒也交给模型。上一次全量运行里，编排者在写地图时就漏过候选，守恒检查是唯一能抓到的地方。

### D2 引文用「路径:行」，不用逐字原文

试验里的写作者写的是「路径:行」，章节可读性好，花费也低。原来的逐字原文要求「在文件里恰好出现一次」，写作者要反复改原文才能过检查。

**代价：** `check` 只能确认行号存在且跨度不超过 80 行，确认不了这几行真的在说这件事。但逐字原文也挡不住「真原文安在错误说法上」。试验的盲审里，两种写法的准确度相当。

### D3 `check` 的规则复用现有模块

- 代码形状词：复用读者文字检查的现有判定；
- 建议词：复用禁词表；
- 路径限制：复用引文定位里的「项目根内、排除目录」判定；
- 事实行的判定：按 spec 里列出的排除项。

`check <out> [<chapter>...] [--before cross]`：
- 不给章节时检查全部；
- 每章一行结果，后面是逐条原因，最后一行是 `Next:`。

每章在 `state.json` 里记：

```json
{"status": "passed|failed", "attempts": n, "reasons": [...]}
```

**尝试次数怎么算：** 按章节文件的 sha256 计。文件内容和上次记录的不同时，次数加一；内容相同时只重记结果。这样续跑时对同一个文件反复 `check` 不会多算，删掉重写后再查才算第二次。

### D4 Markdown 约定里的固定标题

「待确认」「问题」两节的标题、一节没有内容时写的那一行，以及每章开头的「未逐句核对」与「没有通过检查」两句，都是固定文字表里的新键：`chapter.openQuestions`、`chapter.problems`、`chapter.none`、`chapter.notVerified`、`chapter.notPassed`。

写作提示词里直接给出译好的标题文字，脚本按同一张表找到这两节。英文运行用随 skill 发布的表。

**否决的做法：** 用 HTML 注释做标记。模型容易漏写注释，读者也看不出它是一节。

### D5 功能章节的提示词

以试验的提示词为骨架，并入原 `sections/features.md` 里仍成立的内容要求：
- 覆盖什么；
- 顺着代码读出去；
- 例外先于一般规则；
- 否定与绝对断言要先搜全项目；
- 引文要能独立证明这件事；
- 标签照原文。

同时去掉：
- 事实表、发现文件与 `try-*` 的全部段落；
- 文件数上限。

问题一节沿用原来的「什么算发现」与类别表，但写在 Markdown 列表里，每条以类别词开头。

### D5a 版式

试验产出的章节里有整屏的段落，读者很难扫读。提示词写明版式（spec「章节的版式」）：
- 功能章节有固定节序，标题由写作者按 `$LANGUAGE` 写出；
- 有多个属性的条目写成表格；
- 三步以上的操作画 `flowchart`，三个以上状态画 `stateDiagram-v2`。

**`check` 的地板**，只查能确定判定的三项：
- **段落不超过 4 句。** 段落指连续的非空行，不含标题、列表项、表格行与围栏。先去掉引文组，再按 `. ! ? 。 ！ ？` 后接空白或行尾来断句。
- **功能章节至少有一个列表或表格。**
- **mermaid 围栏第一行是已知图类型：** `flowchart`、`graph`、`sequenceDiagram`、`stateDiagram`、`stateDiagram-v2`、`erDiagram`、`classDiagram`、`journey`、`gantt`、`pie`、`mindmap`、`timeline`。

**否决的做法：** 用脚本去查「三步以上的操作有没有画图」。判定步数要理解内容，脚本做不到；硬做只会逼模型为了过检查去删内容。这一条只写在提示词里，验收时人工抽查。

### D5b 选择与续跑

沿用现有的 `--features`（编号或整名）、`--sections`、`--language`（默认英文）、`--fresh`；`select` 命令照旧解析 `--features`。

只写了部分功能时，`check --before cross` 退出 1，编排者跳过跨功能各章，直接拼装，并告诉用户还缺几章。之后用同一个 `--out` 不带 `--features` 再跑，只会补上缺的章，然后再写跨功能各章。

被打断的章没有记录。再跑时先对它跑 `check`：通过就收下，不通过就算第一次尝试。

**否决的做法：** 让写作者先写临时文件、写完再改名。Write 一次写完整个文件，被打断时多半根本没有这个文件；真留下半个文件时，`check` 也会因为缺「问题」一节而拒绝它。

### D6 跨功能章节

在 `sections/cross.md` 里，按以下顺序各派发一个写作子代理：领域、角色、通知与定时任务、横切主题、发现、对策。

**输入：**
- 一律只读 `chapters/` 下的文件；
- 发现一章另读各章的「问题」一节；
- 对策一章另读发现一章与代码健康的 JSON。

**提示词的要求：** 照抄所依据那一行的引文组，不读项目代码。

**级别：** 发现一章按提示词里的固定标准给级别。
- P0：泄露数据、错算钱款或权限越界，读者可以触发；
- P1：读者在正常使用里会碰到的错误行为；
- P2：其余。

**否决的做法：** 按领域拆主题通道。上一次全量运行里，主题通道占了 10% 的花费。一条通道只读章节，上下文是章节的总和，大约几十万 token。超出时按部分分成两条，在提示词里写死分法。

### D7 页面

`product-handbook-page` 保留外壳：顶栏、侧栏、上一章与下一章、视图切换、超过 32 MB 时分块。内容组件换成 Markdown 渲染：
- 依赖 `react-markdown`、`remark-gfm`、`mermaid`，版本与 `prd-report-page` 相同，不新引入别的库；
- 引文组在产品视图里不渲染，在技术视图里渲染成文件与行。

**页面数据：**

```json
{"outline": [...],
 "chapters": {"<file>": "<markdown>"},
 "data": ...,
 "dictionaries": ...,
 "history": ...,
 "coverage": ...}
```

数据、状态字典与代码健康三页沿用现有组件，它们读的是脚本写的 JSON，与本次改动无关。

### D8 输出目录与续跑

`state.json` 的格式串改为 `excavator-product-handbook-state/2`。遇到 `/1` 时停止，并提示用 `--fresh`。`--fresh` 的删除判定认得两种格式串，以及 `candidates.json` 的格式串。

### D9 删除的范围

**保留的库模块：**
- 候选：`entrypoints`、`candidates`、`normalize`；
- 应用根与扫描；
- 地图检查与 `select`；
- 数据与状态字典：`data-*`、`dict-*`；
- 代码健康：`history-*`；
- 固定文字与语言；
- 引文定位里的路径判定；
- 读者文字与禁词判定；
- 页面数据的分块。

**删除的库模块：** 条目、发现、概览、架构、排序、对策、主题、领域、流程图、目录、实体、附录、章节解析与渲染、阶段门，以及它们独占的工具模块。

**删除的测试：** 测试只测被删模块的，一并删除。

**判定方法：** 删前用 `git grep` 确认没有别处引用，`excavator-prd-report` 用到的两个模块必须留下。

## Risks / Trade-offs

- **模型写的角色、通知等汇总可能不全。** 原来的矩阵与总表由事实表算出，至少能保证每条都来自某个条目。
  → 汇总章照抄引文，`check` 照样核对。覆盖一节写明这些章没有逐条核对。

- **跨功能章节会把功能章节里的错误传下去。**
  → 接受；在固定文字里写明。

- **`check` 抓不到「行号对、意思错」。**
  → 与轻量方案相同；试验的盲审给出了这一写法下的错误率，记进验收记录。

- **页面组件改动大。**
  → 外壳、分块与三张脚本数据页不动，只换内容组件。页面测试先红再绿。

- **删除范围大，可能误删共享模块。**
  → 每删一个模块先 `git grep`；整仓受影响的测试一条命令跑完；全量交给 CI。

## Migration Plan

**提交顺序（不 squash，按步可 revert）：**
1. 归档旧变更（已完成）；
2. 本提案；
3. `check` 与状态 v2；
4. 写作阶段的文字与固定文字新键；
5. `assemble` 与 `reply`；
6. 页面；
7. 删除旧命令、模块与测试；
8. 合约测试与验收记录。

**回滚：** revert 合并提交。旧输出目录不受影响，新版本只会要求它们用 `--fresh`。

| O1 | `check` 的每条规则 | 越界行号、跨度 81 行、没带引文的事实行、代码形状词、建议词、缺「问题」一节、五句的段落、没有列表与表格的功能章节、第一行不是图类型的 mermaid，各有一个红样例与一个绿样例；运行前后章节文件逐字节相同 |

| O4 | 页面 | Markdown 表格渲染成表格；坏的 mermaid 显示原文；切换视图停在同一章；改模板后重新生成页面不派发子代理 |
