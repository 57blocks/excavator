## Context

历史扫描给每个提交分配一个提交号，按仓区分；作者按 mailmap 之后的邮箱区分，不分大小写，跨仓共用一个编号表。目录的 `commits` 是它下面各文件提交号的并集，`authors` 是作者编号的并集。上一个变更在扫描时为每个提交号记了年份，目录按年分组。

## Goals / Non-Goals

**Goals:**
- 每个目录能看出提交是集中在少数作者手里，还是分散在很多人手里。
- bot 的提交不混进人的份额。

**Non-Goals:**
- 文件级的份额；按人列出提交数或排名；按行数或时间加权。
- 判断谁懂这块代码、有没有风险。

## Decisions

**1. 扫描时记下每个提交号的作者编号，聚合目录时按作者计数。**
- 做法与上一个变更的年份相同：目录已有提交号的并集，按作者分组即可。同一次提交在一个目录里只算一次，不同仓的提交不会合并。
- 不多跑 `git log`。

**2. 两个数：改得最多的作者所占份额，以及占到八成的最少作者数。**
- 只看第一个数不够：两个人各占四成时份额只有 0.4，但其实两个人就占了八成。第二个数补上这种情况。
- 八成沿用最初建议里实测用的口径，写进字段名 `authorsFor80Percent`，模型读字段名就知道是几成，不必另记规则。
- 「至少八成」用整数比较：前 k 位之和 × 5 ≥ 总数 × 4，避免浮点误差。份额的舍入与文件对的 `shareOfA` 相同，由整数分子算出。

**3. 只做目录级。**
- 文件的提交大多很少：只有 1 次提交的文件，份额必然是 1。按文件排份额，前面会被这类文件占满。
- 代价：chat 答不了「这个文件主要是谁在改」的比例，只能给出 `authors` 与 `commits`；`authors` 为 1 时已能说明只有一位作者。

**4. bot 只按邮箱 @ 前的 `[bot]` 认，不计入份额，在头部计数。**
- 依据（只读 git，不含合并提交）：

  | 语料 | 提交 | 邮箱含 `[bot]` 的 |
  |---|---|---|
  | dataverse | 27,961 | 82 |
  | sakai | 52,765 | 30 |
  | openmrs-core | 12,123 | 921，全部是 dependabot |
  | openmrs-esm-patient-chart | 3,310 | 163 |

- openmrs-core 的依赖文件所在目录，bot 很可能就是「改得最多的作者」。产物里没有名字，模型会把它说成一个人。
- `[bot]` 是 GitHub 应用账号固定的邮箱写法。按子串 `bot` 匹配会把邮箱里恰好有这三个字母的真人算成 bot，所以不用。别的自动化账号（自建 CI 等）按人算，写进残余假设。
- bot 的提交不计入份额的分子和分母。每个目录的 bot 提交数可以由 `commits` 减 `commitsByPeople` 得到，所以不单列；头部只给全项目的数，`.` 行满足 `commits = commitsByPeople + bots.commits`，测试与 oracle 都核对这一条。

**5. 产物里没有名字，skill 与 chat 也不查名字。**
- 汇报会被转发，按人排的数字很容易被当成绩效看。
- 代价：答不了「该问谁」。需要时，用户可以自己跑 `git shortlog`。
- chat 被问到是谁时，说明产物里没有名字；不运行 git 去查，也不读别的文件去查。

**6. skill 的排名只列人的提交不少于 20 次的目录。**
- 提交很少时份额会很极端：1 次提交就是 1。20 次时，一次提交只让份额变化 0.05。
- 阈值写在查询参数里，查询第一行先打印阈值与符合条件的目录数。
- 代价：小目录不进排名。chat 问到单个目录时照样回答，并给出 `commitsByPeople`。

**7. 自检 grep 加入说成负责、风险的用词，但只收不会命中路径的写法。**
- 先查了三份语料的全部路径：
  - `risk` 出现在 openmrs 的 `flags-risk-count` 等路径里，`owner` 出现在 sakai 的 `Owner.java` 里，所以不收这两个单词；
  - 改收 `at risk`、`risky`、`bus factor`、`single point`、`silo`、`owns`、`owned by`、`ownership`、`expert`、`responsible for`、`knows`，以及 `风险`、`单点`、`孤岛`、`负责`、`专家`、`熟悉`、`掌握`；
  - 这些写法在三份语料的路径里一次也没出现。

## Oracle

- **单测**：覆盖规格里的每个场景，包括正好八成、四舍五入、bot、只有 bot、守恒、没有历史、产物里没有邮箱。
- **独立 oracle**：
  - 用 `oracle.py --commits-out` 拿到每个当前文件的提交 sha，它的改名归属是另写的；
  - 每个成员仓用 `git log --format='%H %aE'` 拿到作者邮箱，转小写；
  - 另写一段 Python，只按规格算出每个目录的 `concentration` 与头部 `bots.commits`；多仓按（成员仓，sha）区分提交，作者跨仓按邮箱合并；
  - 与产物逐目录比对，并核对 `.` 行的守恒；
  - 语料：dataverse、sakai、openmrs-workspace（多仓、bot 最多）；
  - 先手动改产物里的几个数，确认比对能报出差异。
- **没有名字**：从各仓 `git log --format='%aN%x00%aE'` 取出全部作者名与邮箱，在三份产物里逐个查找，命中 0 次。
- **耗时与大小**：sakai 全历史，记录前后的耗时与产物大小。增加的耗时不超过 5 秒。
- **真实模型**：Sonnet，headless。
  - dataverse 上 `/excavator-hotspots` 跑一次：份额那一节与产物逐行一致，自检 0 行，不出现名字。
  - openmrs-workspace 上 `/excavator-hotspots` 跑一次：说明 bot 的提交数且不计入份额。
  - dataverse 上 chat 问两次：
    - 「`src/main/java/edu/harvard/iq/dataverse/search` 是不是主要一个人在改」：数字来自 `concentration`，不说有风险；
    - 「这个目录主要是谁在改」：说明没有名字，不跑 git 去查。
