## Context

- 手册的部分由 `--sections` 选择，默认全部；部分与它要读的阶段文件的对应关系在 `lib/sections.mjs` 里。六个跨功能章节（业务域、角色、通知、横切主题、缺陷、对策）都写在 `sections/cross.md` 里，读一次，按三轮派发，对策在最后一轮。
- 跨功能章节只读 `chapters/` 里已写好的章节，不读代码。每个陈述抄写它所依据的章节行的引文组；`check` 核对引文抄得对不对、读者文字里有没有代码词，除对策外拒绝建议词。
- 功能章节的「已知缺陷」只收代码做错的事，明确排除风格与「可能」。横切主题陈述审批、日期、共享数据、权限的现状，不做判断。
- 一次真实运行有 72 个功能，章节中位数约 1.1 万字，全部章节约 80 万字，一个子代理读不下。
- 已有的经验（见 proposal 的 Why 之外）：
  - 模型按片段断言「全表第一」会错，给它全表事实后才稳定；
  - 字段越自由，禁令越挡不住，要拆成可核对的结构字段；
  - 文字检查抓不到「引文是真的，但说的不是这件事」，要有干净上下文的语义核验；
  - 核验轮数要事先定，每多一轮都会再找到错，不会收敛。

## Goals / Non-Goals

**Goals:**
- 一章「设计问题」，覆盖十个维度，每一项能从引用的章节行核对。
- 可选：默认不写；可以加进完整运行，也可以在已有输出上单独运行，前置条件不满足时说清缺什么。
- 对策在有设计问题时也给出改进建议，并在设计问题后补写时自动重写。

**Non-Goals:**
- 不读代码、不重写功能章节；章节没写到的流程，这一章也发现不了。
- 不给每一项打分或算总分。
- 不做第二名核验者，也不做第二轮核验。

## Decisions

### D1 部分、选项与前置条件

- 新的部分 `review`，阶段文件 `sections/review.md`，在 `defects` 之后、`remedies` 之前。
- 对策从 `sections/cross.md` 移到自己的文件 `sections/remedies.md`，排在 `review` 之后，因为它要读设计问题；`cross.md` 剩下五章，派发改为两轮（前四章，然后缺陷）。
- **默认不写**：
  - `parseSections` 的默认值是除 `review` 以外的全部；
  - 新选项 `--review` 把 `review` 加进这次的部分；
  - `--sections review` 只写它。
  - 不加进默认，是因为它花费不小，又是一层判断。代价是要写全量设计问题的用户必须记得加 `--review`，所以回复里会说没写设计问题、加什么选项能写。
- **选中 `review` 时带上 `remedies` 与 `outline`**：`sections` 打印的 `SECTIONS=` 里就包含它们。对策要覆盖设计问题，目录要收进新的一章；带上它们比让用户自己记住更不容易漏。
- **前置条件**：`check "$OUT" --before review --project <root>`。
  - 地图存在，地图上每个功能都有章节，且记录为通过或两次未通过（与 `--before cross` 相同的判断）。
  - 不满足时退出 1，逐行打印缺什么：没有地图；哪些功能没有章节。
  - 阶段的做法：这次运行也选中了 `features`（完整运行）时，按 Phase 8 的做法回到 Phase 5；没选中时跳过这一部分，告诉用户缺什么，以及 `--sections features` 能补上；对策照常写，只是没有设计问题可读。
- **分批的依据**：业务域一章通过且 `domains.json` 存在时按业务域；否则按地图的区域。所以业务域不是前置条件。
- 备选：把 `review` 加进默认、用 `--no-review` 关掉。否决，理由同上；另外它会让所有已有的自动运行静默变贵。

### D2 全表事实

`handbook.mjs review facts "$OUT"` 只从章节与 `domains.json`/`map.json` 算出，写到 `entries/review-facts.json`，同时按批打印。

- **每个功能**：
  - 操作数（操作一节的三级小标题数）；
  - 每个操作的步骤数（该项下顶层列表项数）；
  - 状态数与转换数（状态一节里 `stateDiagram` 的状态与箭头）；
  - 系统内部步骤数（`chapter.serverSteps` 那一行之后的列表项）；
  - 交接数。
- **引用了同一段代码的功能对**：两个功能的引文里有同一文件且行范围相交，列出这对功能、文件与相交的范围，分为同一批内与跨批。
- 小标题按这次运行 `ui.json` 里的固定文字识别；认不出的小节不计数，并在事实里写出它没被计数。
- 每批的写作代理拿到全表：所有功能的这些数字，不只本批，以便它判断「多」是相对什么而言。

备选：让模型自己数。否决，模型转写结构化事实会出错，而这些数字脚本就能确定。

### D3 结构化的项与生成的章节

写作代理不写 Markdown，写 `entries/review/<batch>.json`：

```json
{ "items": [{
  "dimension": "duplication",
  "impact": "medium",
  "features": ["F3", "F12"],
  "title": "<一句话的标题>",
  "situation": "<现状：章节写了什么>",
  "consequence": "<对使用者的后果>",
  "cites": ["<path>:<a>-<b>"]
}] }
```

- `dimension` 取十个之一：`duplication`、`contradiction`、`complexity`、`redundancy`、`dead-end`、`inconsistency`、`manual`、`access`、`traceability`、`other`。
- `impact` 按固定规则：
  - `high`：正常使用时，使用者会得到互相矛盾的结果、会卡住走不下去，或某个角色能做超出其职责的事；
  - `medium`：使用者要多走步骤、同一信息录入两次，或要绕路；
  - `low`：其余。
- `review render "$OUT"` 校验每批的项，拒绝时逐条打印原因（写作代理据此修改，最多 4 次）：
  - 字段齐全、取值合法，`features` 在地图里；
  - 每条引文是从 `features` 列出的某个功能章节里逐字抄来的；
  - `duplication`、`contradiction`、`inconsistency`、`access` 至少有两条引文来自不同的章节行；跨批的项至少引用两个批；
  - `situation`、`consequence`、`title` 里的数字出现在引用的章节行里或这些功能的事实里；
  - 读者文字里没有代码词、文件名和建议词（沿用 `chapter-lint` 的规则）。
- 通过后，脚本生成 `chapters/review.md`：
  - 一级标题和各维度的二级标题取固定文字表；
  - 开头一张维度 × 影响的计数表；
  - 每一项一个三级小标题，下面是影响、涉及的功能（标题加编号）、现状、后果，后两者带引文组。
  - 然后 `check` 照常检查这一章。
- 备选：让写作代理直接写 Markdown，再用文字检查。否决，维度、影响、引文数量这些要求在自由文字里核对不了。

### D4 写作与分批

- 每批一个写作代理，读本批功能的全部章节、全表事实，以及本批功能的「已知缺陷」（只为避免重复）。提示词要求：
  - 只写设计问题，不重述「已知缺陷」里已有的代码缺陷；
  - 后果要具体可核对，「较复杂」「不够友好」不算；
  - 「没有」类的结论写明在哪些章节里没找到。
- 跨批一个写作代理，只读三样：`domains.json` 的交接、跨批的「同一段代码」功能对、各批已通过的项的标题与功能；需要时读相关功能的章节片段。它只写跨批的问题。
- 并发不超过 `$CONCURRENCY`，前台派发，与其他阶段一致。
- **续跑以文件为准**：
  - 有 `<batch>.verdicts.json` 的批已完成；
  - 只有 `<batch>.json` 且 `render` 通过的批，只做核验；
  - 没有文件的批要写。
  - 章节 `review.md` 由脚本从各批重新生成，状态记录照常；它的 `inputs` 记各批文件的摘要，供对策判断是否重写。

### D5 语义核验

- `review claims "$OUT" <batch>` 为每一项打印：项的字段，以及它每条引文所在的章节行原文（按引文找到章节里带这条引文的行）。
- 每批一个核验代理，只看这份输出，不读别的文件；对每一项判 `supported` 或 `unsupported`，并写一行理由，写到 `entries/review/<batch>.verdicts.json`。它判断的是：
  - 引用的行是否说了现状里写的事；
  - 后果是否由现状推得出；
  - 是否只是把一条代码缺陷换了说法。
- `review prune` 删掉 `unsupported` 的项，记到 `entries/review-removed.json`（批、标题、理由），然后重新生成章节。删掉的项不改写、不重试。回复里报出保留数与删除数。
- 核验代理复用 `excavator-handbook-writer`（提示词就是整件任务）；不新增代理。
- 备选：两名核验者都同意才保留（对策与横切主题的旧做法）。否决，花费翻倍；单名核验的残余错误率写进验收记录作为局限。

### D6 对策

- `sections/remedies.md` 的提示词在原有基础上加：有 `chapters/review.md` 时读它，每个有项的维度一段，写共同原因与改进措施，引用设计问题里抄来的引文；建议列表里每条注明针对的缺陷或设计问题。
- 对策的状态记录增加 `inputs`：`defects.md` 与 `review.md` 的摘要。对策已通过但摘要不同（例如后来补写了设计问题），视为待写：删掉旧文件重写。做法与业务域一章的 `json` 摘要相同。

### D7 固定文字

`ui-strings.json` 新增：
- `chapter.review.title`；
- `chapter.review.dimension.<十个>`；
- `chapter.review.impact.<三个>`；
- `chapter.review.field.{impact,features,situation,consequence}`；
- `chapter.review.counts`（计数表的标题）。

翻译与 `check-ui` 照旧。

## Risks / Trade-offs

- **章节决定上限**：章节没写到的流程、写错的事实，这一章都会照着来。
- **判断的残余错误**：单名核验、一轮，会留下错判；验收时按维度分层抽查，报出精度，作为局限写明。
- **「重复」的线索偏向代码**：「引用了同一段代码」能找到共用实现，找不到用不同代码做同一件事的情况；后者只能靠写作代理读章节发现。
- **花费**：一次 72 个功能、约 10 个业务域的运行，多出约 22 次子代理调用加一次对策重写。验收时实测，再写进 SKILL.md 的说明。
- **默认不写**：用户可能不知道有这一章；回复里写明。
