## Context

上一步的审查代理只验过一件事：它在一个植入的缺陷上报出了 Important。参考做法的评测有三部分：
- 用过去真实的缺陷做集，熟悉代码的人确认每个缺陷和它的位置；
- 在已知干净的改动上跑，数会导致有害改动的报告有多少；
- 每次改审查的提示词、工具或模型都在整个集上打分；每次事故加一个用例。

本仓库的约束：
- 评测不编译、不装运行时（build-free）；
- 能由模型按提示词做的不写成代码，但命中与否是结构化的比较，不让被评的模型自己判；
- 花费：每次审查是一次 opus 子代理，串行跑，先实测一次再跑完。

## Goals / Non-Goals

**Goals：**
- 一个小而真实的评测集，每个金标准都核对过；
- 确定性的打分，每个用例落进可见的桶；
- 一次基线：召回、干净用例上的 Important 数、每次运行的花费；
- 改审查规则的 PR 要给出前后分数。

**Non-Goals：**
- 不在 CI 里跑评测：要调用模型，需要用户提供 API key；
- 不量方差：每个用例只跑一次，见 Risks；
- 不追求覆盖每类缺陷：集从小起步，靠漏报来扩充。

## Decisions

### D1 缺陷用例怎样挑

只读的挖掘子代理（opus）按四条规则，从 `origin/main` 上改了非测试代码的修复提交里挑，从最小的开始，看了 30 个：
1. 修复改的是代码，不只是 Markdown 里的提示词或测试；
2. 对修复改掉的行做 `git blame -w`，能找到引入它的提交，并确认这个提交写进了这些行；
3. 缺陷能静态看出：读引入提交的差异与当时周围的代码，不运行任何东西，就能构造出失败的输入；
4. 引入提交改动不超过约 600 行。

结果是 5 处缺陷，分属 3 个引入提交：
- 隐私扫描器第一版的两处：读差异没加 `--text`、只看非合并提交；工作流从事件载荷取标题与正文；
- 全项目结构抽取的两处：并发运行共用临时文件名；扫描清单里的路径没有收敛在项目根内；
- doc-map 的一个测试：期望无条件截断路径，而脚本只截断长于 80 个字符的路径。

doc-map 这一处是规则 1 的例外：缺陷在测试里，修复只改了测试。收进来，是因为 `REVIEW.md` 要求审查确认测试能失败，测试写错也是审查该看见的缺陷。

我逐个读了金标准在引入提交里的行，确认缺陷就在那里。

看过的 30 个里，29 个来自候选清单，1 个是点名加看的 doc-map 测试。收下 5 个，被拒的 25 个按规则计：
- 规则 4 有 10 个：引入提交 945 到约 2,400 行，另有两个来自 1.9 万行与 7.2 万行的批量导入；
- 规则 3 有 7 个：只在内存或规模下显现，或者旧代码本来就符合意图、修复是在语料上调启发式；
- 规则 2 有 6 个：修复是新增功能或字段，没有可 blame 的缺陷行；或者 blame 落在一次改名上，缺陷更早；
- 规则 1 有 2 个：只改了字符串常量的措辞。

收下的修复里有两个也碰了一个 877 行的引入提交，那一部分按规则 4 去掉，只留全项目结构抽取的部分。同一个引入提交里的几处缺陷合成一个用例，只审一次，金标准列出全部行段。

### D2 干净用例

5 个代码提交，各 84–127 行代码，分布在快照读取、hotspots、TS 抽取与 Gherkin 解析。判据是之后没有任何 `fix` 提交碰过它们的文件。我用 bash 逐个重查过，五个都是 0。

这是近似的「干净」：没有被修过，不等于没有缺陷。干净用例上报出的 Important 逐条判是真是假，记进验收记录，不直接算误报。

### D3 怎样跑一个用例

- **执行者**：调用方起一个 opus 子代理，让它按 `<规则版本>:.claude/agents/reviewer.md` 行事，`REVIEW.md` 与 `AGENTS.md` 也取自 `<规则版本>`。这样被评的是一个确定的规则版本。不直接用已加载的 `reviewer` 代理类型，因为它的定义来自会话启动时的工作区，固定不到某个提交。
- **模式**：范围模式，目标是用例的 `range`。代码一律用 `git show <head>:<path>` 读。
- **防泄题**：
  - 不许读引入提交之后的任何提交，不许用 `git log`/`blame` 越过 head，不许读 `origin/main` 上的代码文件；
  - 不许读 `scripts/review-eval/`；
  - 回复首行自报越界。

  修复提交的信息会直接说出缺陷，所以这几条是评测有效的前提。
- **结果**：审查代理把它的 JSON 数组直接写到 `<结果目录>/<用例 id>.json`。这是它唯一的写操作，调用方不转录模型的输出。
- **顺序**：串行。先跑一个用例实测花费，再跑其余的。

### D4 打分

`scripts/review-eval/score.mjs <cases.json> <结果目录>`，零依赖：
- **金标准**：打分的单位是一处缺陷。一处缺陷有一个或多个行段 `{path, start, end}`，例如隐私扫描器那一处同时在第 36 行与第 80–90 行。
- **命中**：一条 Important 的 `path` 与缺陷的某个行段相同，`line` 落在 `[start - 3, end + 3]` 内。留三行余量，是因为审查代理定位的行可能是相邻的调用处或定义处。
- **一条发现只算一处缺陷**：全项目结构抽取的两处缺陷在同一个文件里，加上余量后行段重叠，一条发现可能同时落在两处的范围里。按距离一对一分配：先算每对（发现，缺陷）的距离（在行段内为 0），从近到远分配，发现或缺陷已分配的跳过；距离相同按发现在结果里的顺序、缺陷在用例里的顺序。
- **每处缺陷落进一个桶**：
  - 命中；
  - 看到但档位不对：没有命中，但有一条 Nit 或 Pre-existing 落在它的范围里；
  - 漏掉。
- **用例级的桶**：
  - 没跑：没有结果文件；
  - 读不了：不是 JSON 数组，或某项缺字段。
- **输出**：
  - 每个用例一行；
  - 召回 = 命中的缺陷数 / 缺陷总数；
  - 缺陷用例里没有分配给任何缺陷的 Important 数（可能是另外的真问题）；
  - 干净用例上的 Important 数与 Nit 数。
- **退出码**：有用例没跑或读不了时退出 1，部分结果不能当成完整的分数；否则退出 0。

命中与否由脚本判，不让被评的模型判自己。

### D5 改审查规则的 PR 要给出前后分数

`REVIEW.md` 的流程加一条：改 `REVIEW.md` 或 `.claude/agents/reviewer.md` 的 PR，在 Testing 里给出 `main` 上的版本与 PR head 上的版本在评测集上的分数。
- 这类 PR 本来就是高档，由用户合并，分数是用户合并前看的证据。
- 两版各跑一次是 16 次 opus 审查。`main` 上的版本若已有分数，且之后 `main` 上的 `REVIEW.md`、审查代理定义与 `cases.json` 都没变，PR 可以引用那次分数（给出它所在的 PR），只跑改动后的版本。
- 这一条写进高档的 `REVIEW.md`，所以本 PR 也是高档。

### D6 扩充

`README.md` 写明以下几点：
- **加用例**：审查漏掉、事后修好的缺陷，按 D1 的规则核对后加进 `cases.json`；
- **加规则**：被拒的大提交是下一批候选，可以放宽规则 4；
- **花费**：每次完整评测的花费。

## Oracles（动手前写死）

- **O1 打分装置**：`tests/review-eval/score.test.mjs` 用合成的用例与结果，逐条覆盖：
  - 行段内命中；余量边界上命中；余量外一行漏掉；
  - 路径不同漏掉；同位置的 Nit 计为档位不对；
  - 一处缺陷有两个行段，落在第二个行段也命中；
  - 一个用例两处缺陷只中一处；
  - 一条发现落在两处缺陷重叠的范围里，只算一处；两条发现各算一处；
  - 干净用例上的 Important 与 Nit 计数；
  - 没跑与读不了都退出 1，干净的结果退出 0。

  另做变异，确认有测试变红，做完还原：去掉余量；把 Nit 当命中；把没跑当漏掉；读不了的结果被忽略；一条发现可以算多处缺陷。
- **O2 基线**：
  - 规则版本取上一步 PR 的 head（即将合入 `main` 的版本），8 个用例全部跑完，打分退出 0；
  - 记录每个用例的结果、召回、干净用例上的 Important 数，以及每次运行的 token、调用次数与耗时；
  - 每个命中，读审查代理的解释，确认它来自 head 上的代码，没有提到之后的修复；
  - 干净用例上的每条 Important 判真假。
  - 召回不设及格线：这是第一次量，盲定的阈值没有依据。
- **O3 门**：本地打分测试绿；PR 上 `CI gate` 与 `Privacy scan` 绿。
- **O4 隐私**：改动行、提交信息、路径与正文用本地名单检查全为 0；用例的描述只写机制，不写语料与项目名。

## Risks / Trade-offs

- **集很小**：3 个缺陷范围、5 处缺陷，召回的粒度是 20%，只看得出大的退步。
- **每个用例只跑一次**：模型的方差没有量。比较两个版本时，相差一处金标准不足以下结论。
- **防泄题靠指令与自报**：审查代理能执行 `git`，技术上能看到之后的提交。命中时抽读它的解释，是唯一的旁证。
- **「干净」是近似的**：干净用例上报出的真问题会被当成误报，所以逐条判。
- **花费**：每次完整评测是 8 次 opus 审查。
