## Context

历史扫描已经把窗口内的每次提交按改名归到当前文件，每个文件记着它的提交号集合。提交号按仓分配，不同仓的同一个 sha 是不同的提交号。

## Goals / Non-Goals

**Goals:**
- 列出一起改过至少 3 次的文件对，给出次数和两边各占的比例。
- 排除了什么都在头部写明。

**Non-Goals:**
- 不做目录级的共变，不按提交说明分类，不按作者统计。
- 不判断一对文件是否有依赖，也不判断该不该改。

## Decisions

**1. 扫描完成后，从每个文件的提交号集合反推。**
- 做法：从文件的提交号集合建出「提交 → 文件」，再数文件对。历史扫描不改，也不多跑一次 `git log`。
- 好处：
  - 文件对和文件行的 `commits` 来自同一份归属，两者不会对不上；
  - 提交号按仓分配，所以不同仓的文件不会配对。

**2. 上限 30 个文件、至少 3 次。**
- 依据：用只读 git 粗测（没跟踪改名）。

  | | dataverse | sakai |
  |---|---|---|
  | 改到超过 30 个 HEAD 文件的提交 | 53 次（0.2%） | 466 次（1.6%） |
  | 至少一起改 3 次的文件对 | 7,306 对 | 19,265 对 |
  | 至少一起改 2 次的文件对 | 13,792 对 | 36,992 对 |

- 理由：只一起改过 2 次，很可能是巧合。
- 代价：
  - 只在大提交里一起改过的文件对看不见。这类提交的条数写在头部，也列入残余假设。
  - 提交少于 3 次的文件永远不会成对出现，没列出的对数写在头部。

**3. 比例的分母是文件的 `commits`，超过上限的提交也算在内。**
- 好处：比例和文件行对得上；排除的提交只会让比例偏小，不会偏大。
- 代价：常被大提交改到的文件，比例偏低。
- 计算：用整数分子 `round(together × 100 / commits) / 100`，避开浮点数造成的半位误差。

**4. `pairs` 放在产物顶层，和 `files`、`directories` 并列。** 读头部的查询要把三者一起排除，不然会把全部文件对打印出来。

**5. 「像测试的路径」由 skill 判断，不进脚本。**
- 做法：skill 用 jq 正则按路径名排除常见的测试目录和测试文件名，并说明是按名字判断的。
- 理由：各语言的命名习惯不同，归模型和提示词更合适。

**6. 汇报加一道因果用词自检。** 「不说依赖、调用、因果」只写成规则，在模型压力下容易被忽略。所以把这些词并进第 4 步的建议自检 grep：命中的句子要改写，命中的是文件路径时除外。

## Oracle

- **单测**：覆盖规格里的每个场景，包括恰好 30 和 31 个文件的边界，以及比例的半位舍入。
- **独立 oracle**：
  - 用上次验收写的 `oracle.py --commits-out` 得到每个当前文件的提交 sha，它的改名归属是另写的；
  - 另写一段 Python，只按规格推出文件对和 `coChange`；多仓按（成员目录，sha）区分提交；
  - 与产物逐行逐字段比对；
  - 语料：dataverse、sakai、openmrs-workspace（多仓）；
  - 先在一个文件对上手动改一个数，确认比对能报出差异。
- **耗时**：sakai 全历史，记录加文件对前后的耗时和产物大小。增加的耗时不超过 5 秒。
- **真实模型**：Sonnet，headless，dataverse，各跑一次。
  - `/excavator-hotspots`：汇报含两份文件对清单和 `coChange` 计数，自检 0 行，不说依赖、调用或因果；
  - chat 问「改 `EjbDataverseEngine.java` 的时候通常还要改什么」：答案的数字都来自 `pairs`，不说依赖，用中文回答。
