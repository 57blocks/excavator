## Context

动机见 proposal.md。相关现状：

- 条目（`entry-shape.mjs`）的 `notifications` 每项有 `trigger`、`recipient`、`channel`、`content` 与引文；`automatic` 每项有 `when`、`effect` 与引文。引文是 `{ file, passage }`，`locate.mjs` 的 `locatePassage` 能把通过引文核对的段落定位到首末行。
- `load-run.mjs` 的 `loadCheckedRun` 是 `assemble` 与 `page` 的共同入口：重新核对地图与每个已定案条目，只把 `verified` 的条目放进 `entries`；`candidates` 是候选文件的 `items`，每条有 `id`、`kind`（`route`/`page`/`job`/`main`）、`file`、`line`、`text`（该行文字，至多 200 字符）。
- `render.mjs` 写 `handbook.md`，`page-data.mjs` 组页面数据（格式 `excavator-product-handbook-page/1`），`packages/product-handbook-page` 是页面的 React 源码，构建后内嵌进 `handbook.html`。
- 固定文字来自 `ui-strings.json`（英文）；其他语言在运行时翻译成 `<out>/ui.json`，`loadUi` 核对键集与英文表相同。

go-multirepo 上一轮真实运行的候选里有 16 条 `job`：8 条注册行上有字面时间表（`@every 5m`、`'30 * * * * *'` 一类），2 条是带插值的模板，6 条取自配置、变量或数据库里的记录；其中 4 条在地图里未归入。「报销」的已核实条目有 5 项自动行为，都是事件触发而不是定时任务。

## Goals / Non-Goals

**Goals**
- 两张横切总表，内容只来自已核实条目与确定性脚本。
- 每条 `job` 候选都看得见：守恒、三个桶、未归入的原因。
- 零模型费用；字节级可复现。

**Non-Goals**
- 根因归纳、审批链对比、国家与办公室规则矩阵、数据模型、状态图（各自另开变更）。
- 时间表的自然语言翻译、时区、实例数、幂等性。
- 渠道名归一化。

## Decisions

### D1 汇总放在一个纯模块里，`render` 与 `page-data` 共用

新增 `lib/summary.mjs`：输入 `loadCheckedRun` 的结果与项目根，输出 `{ notifications, jobs, counts }`，不读写别的文件（只为定位引文读项目里被引用的源文件）。`render.mjs` 与 `page-data.mjs` 都从它取数，所以 Markdown 与页面的表一致，测试也只需在一处断言内容。

### D2 时间表的取法：只认注册行文字里的字面量

从候选的 `text` 里按出现顺序取字符串字面量（单引号、双引号、反引号）：
- 不带插值的字面量，内容是五段或六段、每段只含数字、`*`、`/`、`,`、`-`、`?`、`L`、`W`、`#` 与英文月份或星期缩写的 cron 式，或 `@yearly`、`@annually`、`@monthly`、`@weekly`、`@daily`、`@midnight`、`@hourly`、`@every <时长>` 之一 → **字面时间表**，写出第一个这样的字面量；
- 否则，有反引号字面量带 `${...}` 且去掉插值后仍是五段或六段 → **注册时才算出**；
- 否则 → **不在注册行的文字里**。

为什么不读配置或追变量：那是另一类抽取（配置文件格式、环境变量、数据库里的计划），追错了就是编造；本变更只做行文字里能直接看见的，其余进看得见的桶。`text` 截在 200 字符，被截掉的字面量自然落进第三个桶，桶名说的正是「不在注册行的文字里」，不会说错。

为什么任务名（例如 `'nightly-report'`）不取：它不是 cron 式。

### D3 「做什么」只认覆盖注册行的引文，不放宽

对一条 `job` 候选：取它所属功能的已核实条目，逐项看 `automatic`；某项的某段引文与候选同一文件、且 `locatePassage` 定位出的 `[startLine, endLine]` 含候选的 `line`，就列这一项（同一行多项按条目顺序全列）。没有命中时写「没有已核实的描述」。表前写出有描述的行数。

**不退到同文件或同功能。** 一个注册文件里常常登记十几个任务，分属不同功能；按文件或按功能放宽，就会把别的任务的描述挂到这一行上，等于把「找不到」变成「找到别处的」。命中率低是看得见的覆盖缺口，可以接受；挂错描述是编造，不可接受。

定位失败（文件读不到、段落不唯一）的引文当作不命中；`loadCheckedRun` 已核对过引文，正常情况下不会发生。

### D4 通知总表按条目原文，按地图顺序

行序：地图的区域顺序 → 区域内的功能顺序 → 条目里的通知顺序。栏目：功能（编号与名字）、触发、收件人、渠道、内容。不归并相同的行，不归一化渠道名。表前一句：「已核实条目的功能 X 个，共 Y 个功能；其余功能的通知不在表里，见覆盖一节」。没有任何通知时写固定文字「已核实的条目里没有通知」。

### D5 只收 `verified`

`loadCheckedRun` 已经只把 `verified` 的条目放进 `entries`；汇总只从 `entries` 取，`confirmed`（追查未完成）的条目自然不进表。这与功能章节的规则相同。

### D6 页面：两个新页面，数据格式升版本

页面数据加 `summary: { notifications, jobs, counts }`，格式改为 `excavator-product-handbook-page/2`（数据形状变了，页面代码与数据一起发布）。导航在区域列表之后、覆盖页之前加「通知总表」「定时任务总表」两项。表格在手机宽度下沿用现有表格组件的横向滚动容器（页面本身不出现横向滚动）。时间表字面量用等宽字体显示。数据里没有引文路径（只有 `when`、`effect` 文字与候选编号），所以 `withoutRootPaths` 照旧。

### D7 固定文字

新键放在 `md.summary.*` 与页面用的键下（与现有前缀一致），英文表随 skill 发布。已有输出目录的 `ui.json` 缺这些键时，`loadUi` 照现有规则拒绝；续跑时由 skill 的固定文字步骤重新翻译。实现时先确认续跑确实会重做这一步，不会卡住；若不会，在 SKILL.md 的续跑说明里写明要删掉 `ui.json` 重跑那一步（不改状态机）。

## Risks / Trade-offs

- [R1 「做什么」命中率低] 条目作者可能引用任务的处理函数而不是注册行，这样所有行都写「没有已核实的描述」。→ 覆盖缺口看得见，O2 记录命中数；要提高命中，改的是条目写作提示（让自动行为引用注册行），另开变更，不在这里放宽匹配。
- [R2 cron 识别过宽或过窄] 例如六段的字面量其实是别的东西。→ 规则只认字面量里的 cron 字符集与段数，O1 夹具含反例（名字、普通句子、五段以外的字面量）；O2 逐行人工对照 16 行。
- [R3 页面数据变大] 每行几十字节，16 行与几十项通知可以忽略。

## Acceptance oracles（动手实现前写死）

- **O1 单元与夹具**（仓库内，合成项目，不含真实语料内容）：
  - 时间表三个桶：至少含五段 cron、六段 cron、`@every 5m`、`@daily`、名字加 cron（`'nightly-report', '30 * * * * *'` 形）、带插值的模板、配置表达式、变量、普通字符串（`'hello world'`）与截断行；每条断言落桶与写出的字面量。
  - 守恒：行数等于 `job` 候选数，桶计数之和等于行数，未归入的行带地图原因。
  - 「做什么」：同一功能两项自动行为，一项引文覆盖注册行、一项在同文件别处 → 只列前一项；删去前一项 → 写「没有已核实的描述」，不列后一项。另一功能的自动行为引文覆盖该行但功能不同 → 不列。
  - 通知总表：两个 `verified` 条目的通知按地图顺序列出；一个 `confirmed` 条目的通知不列；计数句的 X、Y 正确；没有通知时出现固定文字。
  - 字节复现：同一输入两次 `assemble`、两次 `page`，各自逐字节相同；输出里没有项目根的绝对路径与引文路径。
  - 固定文字：英文表含全部新键；缺键的 `ui.json` 被拒绝。
  - 页面（浏览器测试，沿用 `chrome-cdp.mjs`）：两个新页面可从导航到达，表格行数与数据一致，375 宽下页面不横向滚动，没有网络请求，没有控制台错误。
- **O2 真实输出上重拼**（仓库外，零或近零模型费用）：取 go-multirepo 上一轮真实运行的输出副本（main 当前代码的那次，功能「报销」已核实）以及入口通道分支 after-run 2 的输出副本（「报销」含 4 项通知；若该分支未合入，就只用它的已核实条目文件，不用它的代码）。用本分支插件续跑到拼装与页面（中文；`ui.json` 缺键时重新翻译，记录花费），记录：
  - 定时任务总表 16 行；桶计数与上文 Context 的人工分类一致（8 / 2 / 6），并逐行对照注册行原文；未归入 4 行带原因；
  - 「做什么」的命中数（预期为 0 或很少，「报销」的自动行为都是事件触发）；
  - 通知总表行数等于已核实条目的通知总数，内容与条目逐字相同；
  - `handbook.html` 双击打开（headless Chrome），两个新页面渲染、无网络请求。
  - 任一项不符记为未达标并照实记录，不挪判据。
- **O3 门**：受影响测试；分离检出里跑全量三件套（构建、全量测试、`check-refs`）与 `openspec validate --all --strict`。
