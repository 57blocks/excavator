## 背景

- 轻量方案之后，每个由模型写的单元写一次、脚本检查、`checked` 为终态。
- 功能写作者（Phase 4）与问题写作者（Phase 4c）各自从同一组种子文件读起。
- 概览（Phase 3b）、架构（Phase 4f）与系统问题（Phase 4d）各自读各应用的清单、配置与启动代码。

## 决定

### D1 功能一路合并

- 功能的写作提示词加上问题文件的要求（现有问题提示词的内容：问题的定义、证据、不写建议的规则、空列表），由同一个子代理写。只在 `findings` 被选中时加。
- 子代理交回前依次跑 `try-entry` 与 `try-findings`，都通过再交回。
- 编排者对这个功能依次跑 `check-entry` 与 `check-findings`，两个单元各记各的状态与尝试次数。
- 重派：哪一份不过，就只要求写那一份（另一份已 `checked` 的不动）。
- Phase 4c 只派那些「功能已写过、问题还没写」的功能（例如以前的运行），用现有的问题提示词。正常的全量运行里它不派任何子代理。
- 代价：一个子代理的输出变长，单次轮数增加；省下的是问题一路重新读种子文件与沿调用读的全部轮数。

### D2 系统层合并

- 一个阶段文件 `sections/system.md`（Phase 3b 的位置：地图之后、功能之前），派一个写作者，写它负责的、本次选中的文件：
  - 概览 `entries/overview.json`（选了 `overview`）；
  - 架构章与架构事实表（选了 `architecture`）；
  - 每个应用的系统问题文件（选了 `system-findings`）。
- 提示词由三份现有提示词合成：先列共同的阅读范围（清单、配置、启动、路由注册、数据访问、客户端、认证、调度，每个应用），再分别列每份文件的写法与规则。
- 交回前跑对应的 `try-overview`、`try-architecture`、`try-system-findings`。编排者跑对应的检查命令，各记各的状态。重派只要求写不过的那几份。
- `sections` 命令：`overview`、`architecture`、`system-findings` 任一被选中时读 `sections/system.md` 一次；原来的三个阶段文件不再被读取（保留为补写用的提示词来源时，合并进 `system.md` 的附录，不单独出现在读取顺序里）。
- 大项目的风险：应用多时一个子代理要读的太多。这一片不拆；真实运行若出现上下文压缩或撞上限，记录下来，按应用拆留到以后。

### D3 事件与消息要追到监听者

- 按功能拆分时，最容易丢的是功能之间的连接，不是代码本身：每个入口候选都恰好归一个功能（地图守恒），监听者自己也是候选，归某个功能；丢的是「发出事件的功能」那一章里的交接句。
- 静态地沿导入与调用往下读，到不了按名字订阅的监听者（事件名、队列名、消息主题是字符串）。
- 功能与系统层的提示词在「沿种子文件往外读」一段加一句：代码发出事件、发布消息或把任务放进队列时，用这个名字搜索整个项目，找到每个监听者或消费者，在本章写一句交接（谁接手、做什么），不展开对方功能自己的流程。
- 共用代码（工具函数、共用服务、中间件）：写作者照旧沿调用读进去，按它对本功能的影响写；没有归属的启动、注册、中间件与公共代码由系统层写。共用代码可能被几个功能各读一次：这是各自需要的上下文，不是同一个单元的重复分析；不预先生成共用摘要，因为那样正文会依据二手摘要而不是代码。

### D5 一个功能可以有几个互不相连的入口

- 地图已经把「页面 + 它发的请求 + 服务这些请求的后端路由」放进同一个功能，靠的是代码里的连线。没有连线的入口容易被拆开：同一件事的两个页面（列表页与详情页、管理端与用户端）、页面开始而定时任务或事件监听收尾的流程、邮件里的链接打开的页面。
- 地图提示词「功能」一条加一句：一个功能可以有几个代码里互不相连的入口；入口处理的是同一种业务对象、为的是同一件读者要做的事时放进同一个功能，不要求代码相连；只是用了同一个对象、做的是不同的事时分开。
- 拆错的两个方向都只记录不停下：拆散的由 O3b 的种子文件重叠列出，并错的由按功能抽查看出。不加确定性的合并规则：按控制器或目录合并会把同一控制器下不同的事并在一起，判断留给写地图的模型。
- 代价：提示词多一句，不多派发。

### D4 不变的部分

- 检查命令、状态的键、尝试次数上限、输出与页面都不变。
- 排序、对策、专题、版式不读代码，不在这一片。

## Oracle

- **O1 技能合约**：
  - 正常全量运行里，每个功能只有一次写作派发，系统层只有一次；
  - 功能提示词在选了 `findings` 时含问题文件的要求，并要求依次跑两个 `try` 命令；
  - `sections` 对 `overview`、`architecture`、`system-findings` 的任意组合只读一次 `sections/system.md`；
  - 只要求重写不过的那一份。
  - 地图提示词含 D5 的「几个互不相连的入口」一句，功能与系统层提示词含 D3 的交接一句；换回改动前的提示词，合约测试要变红。
- **O2 脚本测试**：`sections` 的读取顺序与默认列表；已有检查命令的测试不变。
- **O3 连接的事后核对**（确定性，跑完后做，只记录不修改）：列出项目里每个发出事件的位置与事件名，和每个监听者；对每一对，看发出方所属功能的正文有没有一句提到接手的功能或监听的行为；没有的列成问题清单。
- **O3b 功能分组的事后核对**（确定性，跑完后做，只记录不修改）：
  - 种子文件重叠：两个功能的种子文件有一半以上相同时列出，可能是同一个功能被拆成两个；
  - 只有接口没有页面的功能：功能的候选全是后端路由、到达方式又是菜单或链接时列出，可能是页面没配上；
  - 后端路由落在 `unassigned` 的数目与理由分布。
- **O4 真实运行**：一个 NestJS 单仓项目的全量运行，记录每个功能与系统层的派发次数（从运行记录数），应等于功能数与 1（加上重派）；记花费与轮数。
- **O5**：受影响测试、`typecheck`、`openspec validate --all --strict`、零非 ASCII、名字扫描。
