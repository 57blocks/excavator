## 决定

- **D1 阈值与形态**：阈值按序列化后的字节数算，32 MB 以下单文件，形态与现在相同；格式统一升到 `/15`，单文件的核心带一个空的分块索引，明细仍在核心里。32 MB 是浏览器打开单文件 HTML 仍流畅的保守值；阈值写成常量，测试用环境变量调低以走分块形态。
- **D2 什么进核心**：核心 = 导航、概览、各汇总页（角色与功能、通知、定时任务、发现、覆盖、附录等）在不打开单个功能或应用时需要的全部字段；汇总页需要的派生值在写出时算好放进核心，不靠加载分块计算。分块 = 只在单个功能页、单个应用页显示的明细。具体字段按一次真实运行的实测体积划分，写进 design 的附表；一个字段既被汇总页用又很大时，汇总页用的部分算成派生值留在核心。
- **D3 分块文件**：`handbook-data/part-NNNN.js`，内容是 `window.__xvHandbookPart("<id>", <json>)` 一次调用；`<` 照现有办法转义。按单元（功能、应用）顺序装块，单块不超过 8 MB，单个单元超过 8 MB 时拆成该单元的连续几块。块名与内容只由输入决定。核心里有单元到块的索引。
- **D4 加载**：页面一个加载函数：已加载的直接返回；未加载的插入 `<script src>`，`onload` 后从登记处取，`onerror` 记为缺失。单文件形态没有分块，所有数据在核心里，同一个加载函数同步返回，组件只有一条代码路径。
- **D5 CSP**：分块形态的 CSP 是 `script-src 'self' 'unsafe-inline'`，其他指令不变；单文件形态不变。已实测 Chrome 在 `file://` 下按这个策略加载同级脚本；Safari 与 Firefox 能跑就实测，不能就写进已知限制。
- **D6 分页**：表格超过 200 行时分页，每页 200 行，页码在表格下方；筛选在全部行上做，再分页。
- **D7 写出**：每块单独 `JSON.stringify`、单独原子写入；核心同样单独序列化。先写到临时目录，全部成功后再换到 `handbook-data/` 与 `handbook.html`，失败时两者都不留。

## Oracle

- **O1 脚本测试**：阈值以下只写一个文件且两次运行逐字节相同；调低阈值后写出分块，每块不超过上限、两次运行逐字节相同、拼回的数据与单文件形态的数据相同；失败的运行不留下 `handbook.html` 与 `handbook-data/`；写出路径上没有整份数据的字符串（用一个超过 V8 字符串上限的合成数据跑通写出，或用桩证明没有整体序列化）。先红后绿。
- **O2 页面测试**：加载函数在两种形态下返回同样的数据；缺块时显示缺失提示；超过 200 行分页。
- **O3 真实页面**：用真实运行的数据各生成一次单文件与分块形态（调低阈值），无头 Chrome 以 `file://` 打开，两种形态的首页、一个功能页、发现页、字典页截图一致，控制台无错误、除 `data:` 与同级分块外无请求。
- **O4 1 GB**：合成约 1 GB 的页面数据写出分块，无头 Chrome 打开概览与三个功能页，记录写出耗时、峰值内存、打开耗时与 JS 堆，概览不加载任何分块，功能页只加载自己的块。
- **O5**：受影响的测试、模板检查、`check-refs`、`openspec validate --all --strict` 本地跑，全量交给 CI。

## 附表：D2 核心与分块的划分（实测）

一次真实运行（72 个功能，44 个有已核实条目，两个视角）的页面数据序列化后 1,990,720 字节。按字段量得：

| 字段 | 字节 | 去向 |
|---|---|---|
| 功能条目（`features[].entry`，含界面与操作） | 248,758 | 分块：单元 `feature:<id>` |
| 功能的源码位置（`technical.locations` 中功能的部分） | 704,570 | 分块：随功能单元；核心里只留 `{id, items: []}` |
| 字典的值集合（`dictionaries.dictionaries`） | 287,893 | 分块：单元 `dictionaries` |
| 字典的同名不同值（`dictionaries.mismatches`） | 45,384 | 分块：单元 `dictionaries` |
| 数据的表（`data.tables`） | 171,450 | 分块：单元 `data` |
| 数据的已删除表（`data.dropped`） | 5,629 | 分块：单元 `data` |
| 覆盖页（`coverage`） | 280,831 | 核心：覆盖页与概览都读 |
| 附录（`appendix`） | 80,879 | 核心：汇总页 |
| 固定文字表（`ui`） | 37,277 | 核心 |
| 已核实发现（`findings`）与发现位置 | 41,039 与 18,872 | 核心：发现页、建议页、主题页，不打开功能也要显示 |
| 概览的源码位置（`locations` 里 id 为 `overview` 的一项） | 6,883 | 核心：概览页 |
| 导航、通知、定时任务、实体、系统概览、历史等其余 | 小 | 核心 |

分块里的片合计 1,463,684 字节，核心 524,251 字节；核心约占四分之一。

决定与假设：

- **没有一个字段既被汇总页用又很大**：功能条目与源码位置只在功能页读（`FeaturePage` 是唯一读它们的组件），通知与定时任务页读的是 `summary`，不读条目；所以不需要为汇总页另算派生值放进核心。以后若有汇总页读到分块里的字段，必须在写出时算成派生值留在核心。
- **字典与数据按页面成单元，不按应用拆**：字典页与数据页默认同时显示全部应用，按应用筛选只是在已加载的数据上过滤；按应用拆块只会让默认视图加载全部块。每块仍不超过 8 MB，单元超过时连续占几块。
- **单元由「片」组成**（`page-units.mjs`）：每片是一个带标签的小 JSON（`screen`、`operation`、`locationItem`、`table`、`dropped`、`dictionary`、`mismatch`，功能的第一片是掏空 `screens` 与 `operations` 的 `entry`），所以单元超过一块时在片之间断开。一片本身超过上限时写出以用法错误失败（可见，不静默截断）。
- **装块**：按顺序把片装进当前块，装不下就开下一块；多个小单元共用一块，所以一个功能页加载的块里可能还有邻近功能的数据，只是不渲染。块名 `part-NNNN.js`，只由输入与上限决定。
- **体积判定**：阈值比的是核心加全部片的序列化字节数；先把片写进临时目录，总量不超过阈值时丢弃临时的块、把片并回核心写成单文件。
- **环境变量**：`EXCAVATOR_PRODUCT_HANDBOOK_PAGE_CHUNK_THRESHOLD` 调阈值，`EXCAVATOR_PRODUCT_HANDBOOK_PAGE_PART_LIMIT` 调单块上限，只给测试用，skill 不设。
- **分页**：`TableScroll` 与 `ItemList` 自己分页（超过 200 个直接子行或子项），其余组件不改；筛选在上游已经产生子项，所以是先筛再分页；子项个数变化（筛选变了）时回到第一页。各界面、各字段列表仍是各自一个列表，每个列表单独分页。
- **新增固定文字**：`page.chunk.loading`、`page.chunk.missing`、`page.paging.label`、`page.paging.previous`、`page.paging.next`、`page.paging.status`（英文表 `ui-strings.json` 与译文表都要有）。
- **注册表不释放**：已加载的块留在 `window.__xvHandbookParts` 里，访问过的单元不重复加载；内存随访问过的单元增长，不随全部数据增长。
