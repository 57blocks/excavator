## Context

动机与对照试验见 proposal.md。试验的原型脚本、子代理提示词、两边的结果与差异清单都在私有语料的运行目录里，不进仓库。仓库里只记机制与数字。

现状：
- 知识图没有 HTTP 层的关系；
- Core 只为 JAX-RS 生成 `endpoint` 节点；
- 产品手册的入口候选用逐行正则列出 express、nestjs、gin 的路由行，但不拼前缀，gin 的正则还会把出站 HTTP 调用一起列进来。

本变更不动这些，另起一个产物。

## Goals / Non-Goals

**Goals**
- 一份提示词覆盖所有框架和语言，脚本里没有框架分支。
- 编造是硬指标：每条接口与请求都能被脚本对回所引的行；对不回的进桶，不进配对。
- 每条请求落进一个看得见的桶，各桶之和等于请求总数。
- 源码没变的项目不重跑模型。

**Non-Goals**
- 不改 Core、不往知识图里写边。模型产物不进 Core 的事实层。
- 不做 gRPC、GraphQL、WebSocket、消息队列。只做 HTTP 方法加路径。
- 不建模路由器的匹配顺序。例如 Express 先注册者胜，规则统一为「字面段多者胜」，写进残余假设。
- 不判断请求在运行时会不会真的发出，比如死代码或开关后面的调用。
- 不指定模型。

## Decisions

### D1 模型抽取，脚本不做框架适配

接口与请求清单由子代理读代码列出，基地址映射由编排者判断。脚本只核对、配对、计数。

**与 AGENTS.md「事实由确定性脚本写」的关系：** 这份产物不是事实层，是模型写的、逐条带依据行并由脚本核对过的推断产物，与 doc-map 的「功能对到代码」同类。它不进知识图，也不给 Core 当输入。框架知识按「框架知识分三层」放在最低能正确承载它的一层，也就是模型自己的知识，不写数据目录也不写分支。

**否决的做法：** 按框架写抽取（试验里的原型）。它在 go-multirepo 上质量相当，但每种挂前缀的方式都要一段代码，而且它的漏项全部落在长尾写法上，正好是模型做对的地方。

**代价：**
- 每次运行花模型的钱，试验里约 31.5 万 token；
- 两次运行可能不同；
- 漏列不会自己报错。

由 D3、D6、D7、D8 兜住。大项目上花费随文件数增长的情况，本变更只按分片记录花费，不设达标线。

### D2 一个项目一个分片

`plan` 命令列出项目根下的每个项目。项目以清单文件为准：`go.mod`、`package.json`、`pom.xml`、`build.gradle*`、`pyproject.toml`、`requirements.txt`、`Gemfile`、`*.csproj`、`composer.json`、`Cargo.toml`，取最外层，嵌套的归外层。没有清单文件的顶层目录也算一个项目。

一个项目派一个子代理，同时列它注册的接口和它发出的请求。这样前后端同仓的项目（Next.js、全栈 monorepo 的子包）不用先判断它是哪一边。

单个项目超过 `--shard-files`（默认 400 个源文件）时，按顶层子目录再分。前缀跨目录定义的，由子代理在答复里引用别的目录的行，D3 照常核对。

### D3 每条都能被对回所引的行

答复里的每个接口、每个请求都带「依据行」：
- 接口：注册调用那一行，加上路径的每一层前缀所在的行（`Group("/v2")`、`app.use("/leaves", router)`、类上的 `@RequestMapping`）。文件路由用文件路径本身作为依据。
- 请求：调用那一行，加上基地址变量在本文件的绑定行（`const { clientMainApi: mainApi } = config`）。
- 处理函数（可选）：名字与它定义所在的行。

依据行写成 `{file, line, text}`，`text` 是那一行去掉首尾空白后的原文。`check` 逐条核对：
1. 路径收敛在项目根内，越界的不读，直接计为核对不过；
2. 行号在文件范围内；
3. `text` 与那一行去掉首尾空白后相同；
4. 完整路径里的每个字面段（参数段除外）出现在某条依据行、注册行或调用行起的 3 行之内，或依据文件路径里（多行调用的路径常写在下一行）；
5. 方法名出现在注册行或调用行起的 3 行之内（不区分大小写），或依据行里有 `method` 字样；
6. 处理函数的名字出现在注册行起的 3 行之内与它的定义行里。

任一条不过，这条进「核对不过」桶，带上原因，不参与配对。

**为什么不要逐字唯一的引文：** 依据行号定位、原文核对，足以挡住编造的行。路径片段那条挡住「真行配假路径」。这些规则只看文本，不需要知道框架。

**残余：** 把真前缀安到错误的接口上，比如引了别的 `Group` 的行，四条规则都过得了。验收的分层抽查专门覆盖它。

### D4 基地址由编排者判断，脚本交叉验证

编排者读每个子代理报出的基地址变量，判断它指向哪个项目，写出依据行：环境文件、部署文件、代理配置等，`check` 用 D3 第 1–3 条核对。指不到语料里任何项目的写 `null`。

`pair` 为每个基地址算路径重合度：它的请求里，有多少条的路径（不看方法）能配上各项目的某个接口。判断成立要满足两条：编排者选的项目就是重合度最高的项目，且重合度不低于 50%。不成立时，映射标为「冲突」，写出各项目的重合度，这个基地址的请求全部进「基地址判断有冲突」桶。

试验里，按名字认基地址把两个文件里局部重绑的同名变量认错了，重合度因此只有 44%，就是这条规则抓到的。

### D5 配对规则

路径统一写法：
- 按 `/` 切段，去掉查询串；
- `:x`、`{x}`、`<x>`、`${...}`、`[x]` 都写成参数段；
- `*x`、`**`、`[...x]` 写成通配，吃掉其后所有段。

请求与接口配对，要在同一个项目（基地址映射给出）、段数相同（通配除外），并逐段满足：
- 接口段是参数：请求段任意；
- 接口段是字面：请求段相同字面，或请求段是参数。后者记为「参数对字面」。

候选里方法相同的才算。按字面段相同的数目取最多者：
- 只有一个：配上，有参数对字面时带标记；
- 多个：进「多个候选」桶，列出候选；
- 有路径相同而方法都不同的：进「方法不同」桶；
- 都没有：进「后端没有这个路径」桶。

接口方法为 `ANY` 或 `ALL` 的，与任何方法相同。

### D6 桶与守恒

请求的桶：`matched`、`ambiguous`、`verb-differs`、`no-endpoint-path`、`base-unmapped`（映射为 `null`）、`base-conflict`、`unchecked`（核对不过）、`path-unknown`（子代理报出请求，但说明路径无法确定，并写原因）。各桶之和 MUST 等于请求总数。

接口另计：被至少一条请求配上的数目，核对不过的数目。

### D7 防漏读绊线

`plan` 用一组与框架无关的模式扫每个项目，列出疑似注册或疑似请求的行：
- `.` 后跟 HTTP 方法名、`(`（可隔空白与换行），再跟引号，而引号里以 `/` 或 `${` 开头。`searchParams.get('page')` 这类不算；
- `@` 加 HTTP 方法名；
- `fetch(`、`axios`；
- 同一行里有 `method` 与以 `/` 开头的字符串。

`pair` 列出这样的文件：有绊线命中，但子代理的答复里没有任何一条依据行来自它。它们写进产物的 `possiblyUnread`，编排者对这些文件补派一次读取，补读后仍没有条目的照样列出。

绊线只提示、不拦截：模式会命中 `Map.get(` 之类的非请求，也会漏掉不像这些模式的写法。

### D8 缓存与续跑

每个分片的指纹是分片内文件的「路径 + 内容哈希」排序后的哈希。产物里记下每个分片的指纹与它的答复。再次运行时，指纹没变的分片沿用旧答复，不派子代理；`--fresh` 全部重跑。基地址映射在有分片重跑时重新判断。

这样增量运行只为改过的项目花钱，没改过的部分结果也不变。

### D9 产物格式

`.excavator/http-links.json`，格式串 `excavator-http-links/1`。包括：
- `sourceRevision`（与其他产物一样取源码快照）；
- `shards`（指纹、状态、答复的接口与请求）；
- `baseMapping`（判断、依据行、重合度、是否冲突）；
- `pairs`（每条请求的桶与配上的接口）；
- `counts`（各桶计数与守恒）；
- `possiblyUnread`、`residualAssumptions`。

字段值用英文。

### D10 查看页画边

`/excavator-view` 把 `http-links.json` 当作一个产物，状态规则与其他产物相同。读到时，图里为每条 `matched` 的请求画一条从请求所在文件到处理函数所在文件的边；没有处理函数时，画到注册行所在的文件。边的类型是「请求」，有自己的颜色与图例项，并按文件对聚合。这条边不进知识图。

### D11 子代理定义

新增 `excavator-http-links-reader`。它只接收一个分片的文件范围与答复格式，只读，不写答复文件以外的任何文件。提示词写明：
- 不写解析脚本；
- 依据行要逐字抄自文件；
- 看不懂的写法写进 `notes` 并报 `path-unknown`，不猜路径。

答复写到运行目录里由编排者指定的文件，`check` 只读这个文件。

## 验收 oracle（动手前写死）

**语料：**
- go-multirepo，与对照试验同一批提交；
- mixed-suite（另一组框架）。

**参照：** go-multirepo 上原型脚本的结果，逐条人工核对过，存在运行目录里，不进仓库。参照不是真值：两边不同的条目逐条裁定，裁定结果计入。

| # | 检查 | 达标线 |
|---|---|---|
| O1 | 装置先验 | 往一份真实答复里植入 6 类已知假条目：错行号、原文不符、路径段不在依据行、方法不在窗口、越出项目根的路径、处理函数名不符。`check` 6 类全部拒绝；去掉植入后原答复全部通过 |
| O2 | 守恒 | 两个语料上，各桶之和等于请求总数；没有第五种去向 |
| O3 | 编造（go-multirepo） | 分层抽查 40 条 `matched`：嵌套前缀 10、参数对字面 10、跨文件前缀 10、随机 10。错配 ≤ 1 |
| O4 | 召回（go-multirepo） | 裁定后的参照里，接口列出 ≥ 98%，请求列出 ≥ 97%；两边都有的请求，配对相同 ≥ 97% |
| O5 | 稳定（go-multirepo） | `--fresh` 连跑两次，`matched` 配对的对称差 ≤ 2%，基地址映射相同 |
| O6 | 缓存 | 改动一个项目里的一个文件后再跑：只有那个分片派了子代理，其余分片的答复逐字节相同 |
| O7 | 第二语料（mixed-suite） | 跑通，每类桶有计数；分层抽查 20 条 `matched`，错配 ≤ 1；没有参照，召回只报下限 |
| O8 | 查看页 | 无界面 Chrome 打开页面，图里有请求边与图例项；去掉产物后，状态为 not run，并给出命令 |

花费照记：每个语料每次运行的 token 与金额，以及每个分片的花费。不设达标线，但超过试验的两倍时先停下查原因。验收可以钉模型，只记作测量条件。
