# 验收记录：validator-multiline-constructs

验证对象是 `validate-graph.mjs`，读源码、不编译、不装依赖。输入是一次真实 `full` 冒烟留下的事实图（74 文件的 Java 子项目，tree-sitter 事实图，2447 条待核对的边、567 个函数 / 类节点）。图与源码只在 scratchpad 与部署主机里读，不进仓库。判据在动手前写死：按机制分组的六类各自归零，残余不超过 5 条且逐条有源码证据；植入的假样本全部仍被报出。

## 1. 真实图：919 条矛盾

| 类别 | 旧 | 新（最终） |
|---|---:|---:|
| `contains` 边 | 530 | 0 |
| `exports` 边 | 242 | 0 |
| `implements` 边 | 40 | 0 |
| `overrides` 边 | 10 | 0 |
| `calls` 边 | 50 | 0 |
| 锚点不符 | 47 | 0 |
| **合计** | **919** | **0** |

确认数：锚点 567/567，边 2447/2447。`construct-too-long` 为 0（最长的合法前导 / 表达式是 22 行，远小于上限 400）。

**过程中的两次修正**（都由本验收或既有门禁发现，不是事后挪线）：

1. 第一版规则只覆盖注解 / 注释前导与调用表达式，残余 20 条（4 个锚点、16 条边），超出判据的 5 条。逐条看源码：4 个方法的声明折行，`public void` 单独一行，方法名在下一行。这是一类漏掉的机制（多行声明），不是噪音。补上「声明头还没写完就继续读」后归零。
2. 修这条时第一次做成「再宽 ±1 行」，既有的先验装置门禁（证据行指向声明行、期望矛盾）和 `calls` 护栏当场变红：对所有类型放宽一行会让指向相邻行的错边全部通过。改为结构规则：只有仅含修饰符与类型的行才继续往后读；已写完的声明行（带括号 / 花括号）不向后看。随后既有的 `injects` / `references` 用例又变红，才收紧为「带 `token` 的证据条目不享受新宽容」。
3. 设计阶段写的「表达式按括号配平、到 `;` 结束」也有同类缺陷：函数声明行的 `{` 会让扫描一路读进函数体，指向声明行的错边被体内的调用确认。已改为顶层 `{` 结束表达式（括号里的 lambda 块不受影响）。

| `calls` 证据行改指无关行 | 60 | 60 | 60 |

## 3. 已知残余（如实记录）

- **lambda 块里的内层调用**：植入的边把证据行指向 `-> {` 所在语句、被调用者是块内另一次调用，共能构造 3 个（被调用者名需唯一且不在该行），新验证器报出 1 个、确认 2 个，旧验证器 3 个全报。样本只有 3，比例不能外推；机制是设计里写明并接受的代价（表达式扫描会越过括号里的块体，不能改成「遇 `{` 即止」，否则 `.map(x -> {…}).collect(…)` 的 `collect` 会被误判）。
- **名字在声明头第三行及以后，且前面各行都只含修饰符**（`public` / `static` / `void` 各占一行）：按规则会继续往后读，可以找到；若中间某行带括号、花括号、分号或 `=`，则不再往后。极少见，未造夹具断言其为期望行为。
- **错位落在纯前导行里**（注释、注解）会被确认，这与抽取器对被注解声明给出的范围无法区分，是设计里写明的边界；错位进方法体或别的声明仍被报出，测试钉死。

## 6. 评审第 1 轮之后

reviewer 在新验证器上指出两处把「该判矛盾的」确认掉的缺陷，以及一处小问题，逐条复现后都成立：

1. 「整行只有单词」就算折行声明头：`import os`、`return x`、`pass` 也算，Python 里指向 import 行的 `contains`、`calls` 边和锚点被后面的 import 确认。改为第一行必须以声明修饰符开头。
2. 行尾 `++` / `--` 被当作续行：Go 里 `count--` 之后的 `helper()` 被确认。续行判据改为偏向「少认」，同类的可空类型 `?`、`<` / `>`、块注释结尾一并去掉。
3. C# 属性规则把数组字面量的行（`[alpha, 1],`）当属性跳过。改为必须以 `[Name(` 开头，或整行以 `]` 结束。

自查时还发现：`calls` 的证据是表达式起点，不会是注解或注释行，不该享受「跳前导行」；已去掉。

重跑真实图验收：基线仍为 0（锚点 567/567、边 2447/2447），非 lambda 植入仍 260/260，新验证器无多报。

## 7. 评审第 2 轮之后

第 2 轮在第 1 轮的修复上又找到 2 个重要、1 个小问题（`export default router` 被当成折行的声明头、行尾 `*` 被当成续行、`[make(1), 2],` 被当成属性），并指出每个修复都漏了同一类的另一个实例。判断：问题在方法，不在实例，继续补个例到第 3 轮仍会被挑出新的。所以不再补个例：

- **边的声明起点改读图**：不带 `token` 的抽取器证据，只有当被引用的行恰是某个端点自己范围的第一行、名字是期望的 token、且该端点的锚点成立时才确认。文字规则不再碰边。
- **锚点与 `calls` 的文字规则收到最小**：修饰符只收不会开始语句的词；续行只认 `.`、`\`、`=`、`&&`、`||`、`->`、`=>`、单个 `+`；`@x = 1`、`@@x += 1` 与 `*p = 1;` 不当作前导行；括号属性必须以 `]` 结束。
- **整类用表测试**：35 行各种语言的语句形状，分别作为 `calls` 的证据行、锚点起点、`contains` 与 `exports` 的证据行。语句写两遍再接声明（写一遍时，规则错误地跳过它也会在下一行停住，测不出来）。这张表在第一次运行时找到 `@@total += 1`。
- **变异**：11 个变异（边按整个范围确认、不要求锚点成立、`export` 进修饰符、行尾 `*` 或 `,` 当续行、括号属性不必以 `]` 结束、`@x = 1` 与 `@@x = 1` 当注解、`*p = 1` 当注释、表达式上限失效等）全部被拦住；其中 3 个第一次存活，说明表写错了，改后全部被拦。

真实图重跑：基线仍为 0（锚点 567/567、边 2447/2447）。植入 263 个，非 lambda 的 260 个仍全部报出，守恒。植入图里多出 123 条矛盾，全部触及被植入错位的节点（`contains` 82、`exports` 38、`implements` 3），没有一条在外面：一个锚点已经错了的节点，不再替引用它范围起点的边担保。
