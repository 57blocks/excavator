## 实现中的决定

- 代码健康是不派发子代理的脚本部分：`handbook.mjs history` 写 `entries/history.json`，拼装时渲染；`state.json` 不为它记状态。
- 热点与文件对用热点 skill 的 `buildHotspots` 在内存里算，不写项目，也不写项目的 `.excavator`。
- 历史命令只在运行时加载 git 与热点模块：常驻导入让每次 CLI 启动的时间翻倍（约 0.06 秒到 0.13 秒），全量门里两条连续调用 CLI 的测试因此超时。
- 附录在拼装时由已核实的内容算出，不调用模型；手册与页面用同一份计算。
- 页面数据升到 `/14`。

### 抽查

- **应用与年份的提交数**用 `git log --no-merges --full-history` 独立复算：第一次运行少算（一个应用少 68 次，其余也少）。原因是 `git log -- <目录>` 在一个合并的一侧与结果相同时只沿那一侧走，另一侧分支上的提交整段不见。系统事实（`lib/system-facts.mjs`，已在主线上）用同一种读法，概览里的提交数同样偏少。两处都改成 `--full-history`（`369f87e7`），各加一条先红的测试（分支上的提交与主线做了同样的改动）。直接重跑脚本后，5 个应用的提交数、作者数、`authors80` 与 7 年的年份计数全部与复算一致。
- **热点前 5** 用 `git log --follow` 复算提交数：4 个一致，第 1 位少 20 次。不加 `--follow` 也是同样的数，所以不是改名。热点 skill 自己记下了这个文件有 20 处 `lineageConflicts`（分支历史上无法确定一次改动属于哪个同名文件），正好是差的数；它的已知假设里写明了这种情况。手册原来丢掉这个字段，把有出入的数当作确数写出。改为在行里带上 `uncertain`，表里写「441（20 处不确定）」，并在表前加一句说明（`790f418d`）。行数与 `wc -l` 一致。
- **跨应用的文件对**为 0：这个语料的每个应用是一个独立的仓库，文件对只在一个仓库的提交里形成。
- **测试计数**：40 个测试文件，与独立的按约定计数一致。
- **待确认事项** 7 条 = 概览 2 + 两个已核实条目 3 + 2。
- **术语表** 22 个，全部（不只 10 个）对照条目复算：术语集合相同，类型与状态含义逐项相同，按码点排序。
- **资料来源**：功能条目保留 150、核对删掉 26、追查删掉 4，与 `state.json` 的删除记录（30）与条目里带出处的项一致；概览、发现、系统发现、对策的计数同样一致。
- **跨领域主题** 写 4 行而不是 7 行：`repeated` 通道是在 `c018eec1` 之前跑的，之后它的事实加了应用名，摘要变了，按设计算作针对别的内容，不写出，并在覆盖情况里写明。

线（零编造）：修正后**过**。修正前两处数字偏少（提交计数、热点第 1 位），都是确定性读法的问题，不是模型写出的内容。
