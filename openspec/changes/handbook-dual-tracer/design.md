## Context

`product-handbook-map` 的 D14 定下三道核对：每份两名只看引文前后 20 行的核对者（`part-<n>.a.json`、`part-<n>.b.json`，都 `verified` 才算），定案后每份一名能读全项目的追查者，只判 `holds` 或 `contradicted`。`handbook-value-source` 给追查者加了值来源规则；它的验收记录显示，剩下的漏判是追查的方差：

| 已知错误 | 代号 | 用现行规则的单名追查者抓到的次数 |
|---|---|---|
| 津贴来源说成所选申请的行程 | S1 | 装置 6/6，真实运行抓到 |
| 汇率日期说成交易日期 | S2 | 装置 6/6；真实文件 2/3，真实运行放过 |
| 植入的津贴来源错误 | S3 | 装置 6/6（只在装置里） |
| 插入位置 | X1 | 装置 6/6，真实运行抓到 |
| 「三步总在」 | X2 | 装置 6/6，真实运行抓到 |
| 同地往返判定比主张窄 | R1 | 装置 6/7，真实运行放过，被 Opus 抽查查出 |
| 打开别人的记录会跳到审批详情 | R2 | 装置 3/6，真实运行放过，被 Opus 抽查查出 |

（装置次数取 `handbook-value-source` 第 2–4 轮，规则版本不同但都含值来源规则。）抽查剩下的 2 项正是 R1、R2。核对者那一步遇到过同样的形状：同一份文件再跑一次就抓到，所以用两名互不相见的核对者解决了。

## Goals / Non-Goals

**Goals:**
- 每份两名追查者，任一名找到反证就删；
- 两个判词文件各自守恒、各自校验，问题逐个份-字母报告与重派；
- 删去的记录保留每一名判 `contradicted` 的追查者的理由与位置。

**Non-Goals:**
- 不改追查者的判法与规则；
- 不改核对者、改写与拼装；
- 不处理召回（「未知」其实答得了的那类）。

## Decisions

### D1 两名追查者，判 `contradicted` 取「或」

一名追查者对 R2 的抓到率约一半。设两名互相独立，「或」的漏判率是单名的平方：R2 从约 50% 降到约 25%，R1 从约 15% 降到约 2%，S2 在真实文件上从约 33% 降到约 11%。这只在漏判是随机的时候成立；`handbook-value-source` 第 0 轮那样的系统性漏判（3 次都放过），加多少名都没用，那一类靠规则补，已经补了。

考虑过的别的做法：
- **Opus 追查**：核对者那一步试过 Opus 核对，抓得住，但把抽查确认为真的 8 项也拒了，花费约 5 倍。不选。
- **三名取多数**：多数票留下「一名抓到、两名放过」的错误，与零编造的方向相反。三名取「或」又比两名多一半花费；先量两名，不够再说。
- **只对 `holds` 的项再派一名**：要多一轮串行派发，状态里多一种「半追查」的中间态；两名并行的花费相同，时长更短。不选。

代价：「或」也会把一名追查者误判的真话删去，误删的机会约翻倍。删去的是召回，不是编造，覆盖一节照样列出；O1 与 O3 量出误删的次数。

### D2 判词文件的命名与逐个校验

- 每份两个判词文件：`<out>/trace-verdicts/<id>/part-<n>.a.json` 与 `part-<n>.b.json`，与核对者的 `verdicts/round-<r>/<id>/part-<n>.<x>.json` 同一写法。字母表与核对者共用一个常量。追查文件仍是每份一个 `<out>/trace/<id>/part-<n>.json`，两名追查者读同一个文件。
- `trace` 打印 `Part <p>/<k>: <m> items | Trace file: <path> | Verdict files: <a 的路径> <b 的路径>`，与 `slices` 的 `Verdict files:` 同形。它照旧先清掉该功能旧的追查与判词目录，所以上一版留下的 `part-<n>.json` 不会混进来。
- `trace-verdicts` 对每个判词文件**单独**执行现有的全部检查：每项恰好一个判词、没有别的 id、判词只有两种、理由非空且一行、`contradicted` 至少一个 `at` 且每个 `at` 在项目内存在且行号在文件内、理由不点文件名、`contradicted` 的理由过读者文字的门。同一文件里两条 `holds` 理由相同仍拒（说明那一名没有逐项追）；a 与 b 之间理由相同不拒（两名独立写出同一句是可能的，且不说明谁敷衍）。
- 问题行以 `part <n><x>:` 开头。任一文件缺失、不是 JSON 或有问题，退出 1，什么都不记。`Next:` 行与核对者相同：只缺文件时「为恰好这些缺失的份-字母再派一次」；有被拒的文件时「删掉被拒的那些文件，为缺失与被拒的份-字母再派一次」。

### D3 合并与记录

- 两个文件都有效后逐项合并：任一名 `contradicted` 就是 `contradicted`，否则 `holds`。一个 `contradicted` 一定带着已经校验过的 `at`，所以「带有效 `at` 的 `contradicted`」就是文件有效时的 `contradicted`。
- 删去的记录（`state.json` 的 `removed`，`step: "trace"`）：
  - `reason`：读者在覆盖一节看到的那一条，取 a、b 顺序中第一名判 `contradicted` 的理由。读者看一条就够；两条并排常是同一件事换个说法。
  - `reasons`：每一名判 `contradicted` 的追查者的理由，按 a、b 顺序，一名时一条、两名时两条。给运行的人核对，不进手册正文与页面。
  - `at`：每一名判 `contradicted` 的追查者的全部 `at`，按 a、b 顺序，同一文件同一行只留一个。
- 状态校验接受删去记录上可选的 `reasons`（字符串数组）。核对者那一步的记录不带它。
- `holds` 的理由不记录，与现在相同。

### D4 重派

- 缺失或被拒的每个份-字母重派一次，提示与第一次相同；被拒的先删旧文件，提示后附被拒的原因，与核对者、现行追查者相同。
- 重派后仍不成立，功能停在 `confirmed`，手册覆盖一节列为核对未完成。**不退回到只用另一名的判词**：单名追查正是本变更要去掉的漏判来源；退回会让同一个功能在不同运行里时而有两名、时而一名，覆盖一节看不出来。代价是偶尔一个功能因一名追查者两次写坏文件而进不了正文，这是可见的覆盖缺口。

### D5 花费与时长

- 追查花费约翻倍：上两次真实运行在 89 项 4 份上是 $4.54（7.7 分钟）与 $5.09（10.7 分钟），预计 $9–10。一个功能从核对到追查约 $18–23。
- 一个功能 4 份就是 8 名追查者，一条消息派完（上限 10），时长与一名时相近；5 份以上分两批。
- O3 实测并记录。

## Risks / Trade-offs

- [R1 两名追查者的漏判并不独立：同一个模型、同一份提示，可能在同一处一起漏] → O1 用两次重复量；装置上 S1–X2 单名都是 6/6，R1、R2 是这次要量的。一起漏的照实记，不挪判据。
- [R2 误删翻倍] → O1 数已知为真的项被删的次数，O3 逐条对照源码判真错或误删。误删记为召回损失。
- [R3 装置偏差：第 4 份多了同类对照，可能把追查者引向汇率调用] → `handbook-value-source` 已记录；O3 的真实运行与 O4 的独立抽查是最终判据。

## Acceptance oracles（动手实现前写死）

- **O1 装置**（仓库外的副本，不跑真实运行）：上一轮真实运行的追查文件第 2、3、4 份（25、25、17 项；第 4 份含 `handbook-value-source` 植入的 1 项错误与 2 项对照）的副本，同一份语料副本，现行追查者定义。
  - 已知错误 7 处：S1、S2、S3、X1、X2、R1、R2（R1、R2 已在 `handbook-value-source` 的验收记录里对照源码确认为真错）。
  - 已知为真 30 项：此前独立抽查判为 `verified` 的项（含总额一项）与两项对照，同 `handbook-value-source` 的 O1。
  - 做法：每次重复里每份派两名 Sonnet 追查者，各写一个判词文件；按与 `trace-verdicts` 相同的「或」合并。重复两次。
  - 通过条件：7 处已知错误在两次重复里都被「或」判为 `contradicted`；任一次都没有已知为真的项被判 `contradicted`。其余被判 `contradicted` 的项逐条对照源码，记为真错或误删。
- **O2 脚本**：`trace-verdicts` 的测试先在旧代码上看到红，再在新代码上看到绿：
  - a `holds`、b `contradicted` 的项被删，记录带 b 的理由、`reasons` 一条与 b 的 `at`；
  - 两名都 `contradicted`：`reason` 取 a 的，`reasons` 两条，`at` 为并集且同一位置只留一个；
  - 两名都 `holds`：不删；
  - b 文件缺失：退出 1，什么都不记，`Next:` 只点名 `1b`；
  - a 有效、b 里一个 `at` 越出项目根：退出 1，什么都不记，问题行以 `part 1b:` 开头；
  - 同一文件内两条 `holds` 理由相同被拒，a 与 b 之间相同不拒；
  - `trace` 打印两个判词路径；状态校验接受 `reasons`、拒绝不是字符串数组的 `reasons`。
- **O3 真实运行**（go-multirepo，「报销」）：在上一轮真实运行定案后的产物副本上（功能 `confirmed`，89 项，核对者阶段不变），插件取本分支（`--plugin-dir`），只跑追查：Sonnet 钉死模型、`CLAUDE_CODE_PRINT_BG_WAIT_CEILING_MS=0`、`--out` 在语料外。记录花费、时长、每份两名的判词计数、删去的项及每项对照源码的真假；列出已知错误（S1、S2、X1、X2、R1、R2）各自是否被删。
- **O4 Opus 抽查**：O3 的结果上由 Opus 审读者按条目项类型分层新抽 30 项（新种子），可读语料全部源码（`.excavator` 除外）、不读产物，对照源码判定。主张的矛盾数为 0 即达标；未达标照实记录，不挪判据。能从种子以外文件回答的「未知」照旧记为召回问题。
- **O5 门**：受影响的测试（`trace.test.mjs`、合约测试，以及读 `state.json` 删去记录的测试）、`node scripts/check-refs.mjs`、`openspec validate --all --strict` 在本地；全量三件套在分离检出里跑。
