## Why

改到部署相关文件的 PR 目前会跑完整的发布流程（测试门 → 构建 `linux/amd64` 镜像 → 自检），只是不推送。最近四次这类 PR 运行里，镜像构建与自检每次约 7.5–8 分钟，占整次 CI 的约三分之二；而镜像仓库尚未配置，镜像目前由本地构建、以 tarball 交付，PR 上构建出的镜像并不会被使用。用户决定 CI 暂时不需要构建镜像。

## What Changes

- 改到部署相关文件的 PR 只运行仓库测试门，不再构建镜像、不再自检。
- 镜像构建、自检与推送只在发布触发（推送 `runner-v*` tag 或手动 dispatch）下运行，规则不变：全部通过且镜像仓库参数齐全才推送，否则报告跳过推送及原因。
- `docs/deploy.md` 的 CI 一节同步改写；镜像在合入前的验证改为本地构建并运行自检（文档已有该流程）。
- 恢复 PR 上的镜像构建只需撤掉镜像任务上的触发条件。

## Capabilities

### New Capabilities

（无）

### Modified Capabilities

- `runner-image`: 「镜像可自检且按固定规则发布」——PR 不再运行镜像构建与自检，只运行测试门；镜像构建、自检与推送限于发布触发。

## Impact

- `.github/workflows/runner-image.yml`：镜像任务加触发条件，头部说明改写；测试任务与触发器不变。
- `docs/deploy.md` §12。
- 代价：PR 合入前不再由 CI 证明 Dockerfile 能构建、镜像能自检；镜像问题会推迟到本地构建或发布触发时才暴露。
- 无产品代码、无依赖变化。
