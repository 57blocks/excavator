# 验收记录：validator-leading-lines

验证对象是 `validate-graph.mjs`，读源码、不编译、不装依赖。输入是一次真实 `full` 冒烟留下的事实图（74 文件的 Java 子项目，tree-sitter 事实图，567 个函数 / 类节点，2447 条待核对的边）。图与源码只在 scratchpad 与部署主机里读，不进仓库。判据在动手前写死（见 `tasks.md` 5.1 到 5.3）。

## 1. 先验装置

新测试文件 `test_validate_graph_leading_lines.test.mjs` 先在未改动的验证器（`main` 的代码）上跑：93 个用例里 9 个红、84 个绿。红的是真实形状（注解在前的锚点、注解块、属性列表、过长的前导行、CLI 字段、边按范围起点确认）；绿的是护栏（错位锚点、注解后跟另一个名字的声明、语句形状表、模型引用的证据、证据行指向无关行），`main` 本来就把它们判为矛盾。装置看得见已知假样本。

## 2. 真实图

| 类别 | 旧（`main`） | 新 |
|---|---:|---:|
| 锚点不符 | 47 | 4 |
| `contains` 边 | 530 | 12 |
| `exports` 边 | 242 | 4 |
| `implements` 边 | 40 | 0 |
| `overrides` 边 | 10 | 0 |
| `calls` 边 | 50 | 50 |
| **合计** | **919** | **70** |

确认数：锚点 563/567，边 2381/2447。`construct-too-long`：0（最长的合法前导块是 22 行，上限 400）。

残余 70 条按机制逐条分类（分类用与验证器规则无关的纯文本判断），没有一条在这两类之外：

- **`calls` 50 条**：本变更没有动 `calls` 的核对，原样保留。表达式写成多行，归 `validator-multiline-calls`。
- **折行声明头 20 条**：4 个带注解的方法，锚点本身矛盾（注解之后那一行只有 `public void`，名字在再下一行），连带它们的 12 条边；另有 2 个不带注解的方法（`private void` 一行、方法名在下一行），锚点靠 ±1 通过、但不是精确的，所以不再替它们的 4 条边担保。合计 4 个锚点加 16 条边。归 `validator-multiline-calls`。
- **其他：0 条**。

第一次分类时「其他」是 4 条，逐条看源码后发现是上面第二种折行声明头（靠 ±1 通过的锚点），是分类器漏了这一种，不是规则漏判。

## 3. 召回：植入假样本

在真实图的副本里按固定种子植入 415 个，决定与重放都在副本里做，仓库不动。每个植入先用与验证器规则无关的纯文本判断确认「确是坏的」（如：错位后的行及上下各一行不含该名字；被调用者名不在其后 12 行；别的成员注解之后 30 行不含目标名；偏一行后的那一行是代码行且不含名字）。

| 植入 | 数量 | 旧验证器报出 | 新验证器报出 |
|---|---:|---:|---:|
| 锚点错位 3–30 行进入方法体 | 70 | 70 | 70 |
| `calls` 证据行改指无关行 | 60 | 60 | 60 |
| `contains` 证据行改指别的成员的注解 | 60 | 60 | 60 |
| `exports` 同上 | 40 | 40 | 40 |
| `implements` / `overrides` 同上 | 30 | 30 | 30 |
| 节点范围与边的证据行同时偏一行（边） | 107 | 107 | 107 |
| **合计（不含 lambda）** | **367** | **367** | **367** |
| `calls` 证据指向含 lambda 块的语句 | 3 | 3 | 3 |

- 守恒：植入数 = 报出数 = 367，漏报 0。旧验证器同样 367/367，装置对照成立。
- 同时偏一行的 45 个节点：新验证器仍确认它们的锚点（靠 ±1 通过，保持 `main` 的行为），它们的边全部被报出。这正是第三轮评审指出的问题的反例：靠 ±1 通过的锚点不再替边担保。
- 新验证器在植入图里多出 121 条「既不是植入、也不在基线里」的矛盾，全部触及一个被植入错位的节点，没有一条在外面。这是预期的一致性：一个锚点已经错了的节点，不再替引用它范围起点的边担保。
- lambda 3/3：`calls` 没有改动，与 `main` 一致。

## 4. 变异

在已提交的版本上把每条规则改坏，确认至少一个用例变红，随后从提交还原：

| 变异 | 失败用例数 |
|---|---:|
| 前导行把代码行也跳过 | 7 |
| `@x = 1` 当注解 | 2 |
| `@@x += 1` 当注解 | 1 |
| `*p = 1` 当注释 | 1 |
| 多行括号属性不必以 `]` 结束 | 1 |
| 单行括号属性不必以 `]` 结束 | 3 |
| 边按整个范围确认 | 1 |
| 边不要求锚点精确 | 5 |
| ±1 通过的锚点也算可信 | 2 |
| 模型引用的证据也享受宽容 | 1 |
| 带 `token` 的证据也享受宽容 | 1 |
| `calls` 也享受宽容 | 1 |
| 扫描上限失效 | 2 |
| `*` 开头的注释续行不再被跳过 | 1 |

第一次有 3 个变异存活（带 `token` 的证据、`calls`、`*` 注释续行），说明测试对这三条规则没有约束力。补了三个用例后全部被拦住；其中 `*` 那条的夹具第一次写错了：类名 `Doc` 恰好出现在注释 `Documents` 里，不管规则在不在都匹配，换名之后才咬人。
