## Context

动机见 proposal.md 的 Why。这里只写做法依赖的现状：

- 设计问题阶段（`handbook-design-review`，已完成未归档）：业务域批 `b1…bn` 各一名写作代理写 `entries/review/<batch>.json`，`review render` 检查，每批一名核验代理判 `supported`/`unsupported`，`review prune` 删除并记到 `entries/review-removed.json`，脚本从各批生成 `chapters/review.md`；最后一个 `cross` 批只读交接、跨批同段代码对与各批标题。
- 对策阶段：一名写作代理读 `defects.md`、`review.md`、`entries/history.json`，按缺陷类别与设计问题维度分节，最后 1 到 10 条建议；状态里记两章的摘要，摘要变了就重写。
- 已有的确定性产物：`map.json`（功能与它的入口候选）、`candidates.json`（候选的种类、文件、行）、`dictionaries.json` 与 `data.json`（数据部分）、`domains.json`（业务域与跨域交接，交接文字里写着功能编号）、`chapters/topics.md`（横切主题的表）、`entries/review-facts.json`（全表事实与同段代码对）。功能章节有固定小标题的「操作」「状态」「与其他功能的衔接」各节。
- 页面（`handbook-page-structure`，已完成未归档）：问题页每行链到改进建议页里类别或维度那一节；页面搜索、功能页、业务域页已就位。

约束：模型产物只做判断，结构化事实由脚本产出（项目约定）；skill 不指定模型；源码与散文零非 ASCII 字符，OpenSpec 用中文；公开仓库里不写语料名。

## Goals / Non-Goals

**Goals:**
- 重叠与矛盾的两边由脚本拼出原文，核验不再因为「两边只引了一边」删项。
- 每个确定性线索都落进可见的桶，漏判看得见。
- 流程只由章节里已有的名字串成，每个名字逐字可查。
- 每个切片单独可测、可交付，先在一个业务域上标定花费再跑全量。

**Non-Goals:**
- 不为流程建调用图或重读源码；流程的正确性上限是章节。
- 不给流程打分（步数阈值之类）；「复杂」仍由写作代理比较全表事实判断。
- 功能章阶段不写卡；卡只在设计问题阶段从已通过的章节抽。
- 不加第二轮核验；残余错误率作为局限写进验收。
- 缺陷不并进设计问题，两章各自独立。

## Decisions

### D1 部分、选项与顺序

- 新部分 `processes`，阶段文件 `sections/processes.md`；顺序为 `defects` → `processes` → `review` → `remedies` → `outline`。流程在设计问题之前，因为流程的精简项要读流程清单。
- `--review` 选中 `processes`、`review`、`remedies`、`outline`；`--sections review` 同样带上 `processes`；`--sections processes` 只带 `outline`。
- 前置条件与设计问题相同（地图存在，每个功能都有已记录的章节），用同一个 `check --before`。
- 备选：流程单独一个默认开启的部分。否决：它与设计问题一起才有用，默认开会让已有的自动运行静默变贵。代价：只想看流程的用户要记得 `--sections processes`，回复里会说明。

### D2 条目编号

- `D<n>`：缺陷按 `defects-items` 的拆法（P0、P1、P2 小节，节内顺序）连续编号；缺陷一章的文件不改，`handbook.md` 与页面在短标题前写编号。
- `R<n>`：`review render` 生成章节时按维度、批、批内顺序连续编号，写进三级小标题；`P<n>`：流程清单顺序。
- 编号随产物重排而变；对策记录三个输入的摘要，任一变化就重写，所以对策里的编号总与当前产物一致。
- 备选：用内容哈希作稳定编号。否决：读者看不懂、对策里不好引；稳定性由「摘要变了就重写」保证就够了。

### D3 对比候选

- `review compare-facts "$OUT"` 写 `entries/review-compare.json` 并打印 `CANDIDATE` 行（编号、来源、功能、事实、分给哪一批）。
- 两套实现：对每个功能，取 `map.json` 里它的入口候选中种类为服务端路由的那些，按系统事实里的应用（候选文件所在的应用根目录）分组；落在两个以上应用的功能是候选，事实写出每个应用的路由个数。只看应用，不看名字——「旧」「v2」之类的文字既会漏也会误报。
- 字典不一致、共用的表：直接读数据部分已算好的比对与「被多个应用读写」的表，不重算。
- 横切主题：拆 `topics.md` 的表行，一行里出现两个以上功能编号就是候选，主题决定分给哪一批（见 D5）；第五个主题「同一种问题出现在多处」汇的是缺陷，不取。
- 同一段代码：沿用 `review-facts.json` 的跨批功能对。
- 桶由 `review compare-status` 算：保留的项（任一批）涉及的功能包含候选的全部功能，或项的 `candidates` 字段列了它，算「成了设计问题」；排除列表里有它算「不是问题」；其余「没判」。结果写进设计问题一章的覆盖一节。
- 备选：让对比写作代理自己去找线索。否决：上一轮的 `cross` 批说明模型不会自己去读这些产物；候选与桶让漏判可见，而不是靠提示词。

### D4 规则卡

业务域批的文件增加两个键：

```json
{ "items": [...],
  "cards": [{ "kind": "eligibility", "subject": "<短语>", "feature": "F12",
              "statement": "<一句>", "cites": ["<path>:<a>-<b>"] }],
  "dismissed": [{ "candidate": "X3", "reason": "same" }] }
```

- `kind` 八种：`limit`、`eligibility`、`deadline`、`states`、`required`、`approval`、`calculation`、`entrance`。卡的编号由脚本给：`<batch>.k<n>`。
- 检查沿用项的规则：引文必须从所属功能的章节逐字抄来，陈述里的数字必须在引用的行里，读者文字的禁词与代码词照旧。
- 核验：`review claims` 在项之后打印每张卡与它引用的行；核验代理对卡也写 `supported`/`unsupported`（`verdicts` 增加 `cards` 列表）；`review prune` 同时删卡，记到删除记录。
- 备选：单独派一名写卡代理（每批多一次调用，约 +0.5 倍花费）。先不做：写项时本就在读全部章节，顺手写卡最便宜。风险是写卡挤占写项的注意力，验收时与上一轮同批的项数对比；项数明显下降（任一维度降一半以上）就退回单独的写卡代理，这在任务里是一个预先写好的分支。

### D5 对比批

- 批编号 `c1`（数字类：`limit`、`deadline`、`calculation`）、`c2`（名单与取值类：`eligibility`、`states`、`required`）、`c3`（路线与入口类：`approval`、`entrance`）。一批的卡超过 400 张时，按种类拆成 `c1-limit` 等。上限 400 是为了让一名写作代理一次读完卡与候选；拆开会丢掉跨种类的配对，这一点由植入回放测量。
- 候选分配写死在脚本里：字典不一致、共用的表、领域之间的数据行 → `c2`；审批路线与权限行、同一段代码 → `c3`；日历与时区行 → `c1`；两套实现 → 功能所在的业务域批。
- 对比批在所有业务域批核验、删减之后才写，只读通过核验的卡。
- 项的形状：

```json
{ "items": [{ "dimension": "contradiction", "impact": "high", "title": "<短语>",
              "cards": ["b3.k4", "b7.k2"], "candidates": ["X5"],
              "difference": "<一句>", "consequence": "<一句>" }],
  "dismissed": [{ "candidate": "X9", "reason": "different-subject" }] }
```

- `dimension` 只能是 `duplication`、`contradiction`、`inconsistency`；`cards` 至少两张、引文不在同一章节行；可以同属一个功能，因为前后端两套规则常写在同一章的两行；`features` 由卡推出，不写。
- `review render` 拼出 `situation`：「<功能标题>（<编号>）：<陈述>；<功能标题>（<编号>）：<陈述>」，`cites` 是卡的引文之和，然后按普通的项生成章节。模型从头到尾不转写两边。
- 核验代理看拼好的现状、差别与后果，判断差别与后果是否由现状推得出、是不是设计问题。卡已在业务域批核验过，不再判第二次。
- 删除规则：派发核验前，脚本先删掉通过核验、引文不在同一章节行的卡不足两张的项。
- 备选：保留 `cross` 批、只把卡给它。否决：一名写作代理读全部卡（验收语料约 1000 张）会漏配对；按种类分批让每批的卡说的是同一类事。

### D6 两套实现

- 业务域批的写作代理拿到本批的两套实现候选（`CANDIDATE` 行，带每个应用的路由数）。它写一项 `dimension: duplication`、`dual: true`、`features` 含这个功能、`candidates` 列出候选编号，现状写两边各有哪些操作（引文从这一章抄）；或在 `dismissed` 里排除。
- `review render` 拒绝一个既没有这一项也没有排除的候选，原因里写出功能。
- 核验照常；被核验删掉的两套实现项，候选落进「没判」，覆盖一节看得见。

### D7 流程事实

`processes facts "$OUT"` 写 `entries/process-facts.json` 并打印：
- `OP <feature> <操作标题>`：操作一节的三级小标题原文；
- `STATE <feature> <状态>`：状态图里的状态；
- `ROLE <角色>`：地图的角色表（全系统一份，地图不按功能分角色）；外加固定的 `system`（系统自动做的一步）与 `any-user`（任何登录用户）。章节里的角色写法与角色表不一致时，写作代理取角色表里的名字；做不到时用 `any-user`，验收的独立读者会看到。
- `EDGE <from> <to> <来源>`：章节「与其他功能的衔接」一节里提到的其他功能编号，以及 `domains.json` 交接文字里提到的功能编号对；方向按衔接一节所在的功能指向被提到的功能，业务域交接按 `from` 域里的功能指向 `to` 域里的功能。
- 小标题按这次运行 `ui.json` 的固定文字认，认不出的小节写明没被计数（与全表事实相同）。

### D8 流程清单

```json
{ "processes": [{ "name": "<短语>", "domain": "<业务域名或 null>",
                  "steps": [{ "feature": "F8", "operation": "<操作标题>", "role": "<角色>" }],
                  "end": { "feature": "F1", "state": "<状态>" } }],
  "outside": [{ "feature": "F3", "operation": "<操作标题>", "reason": "view-only" }] }
```

- 理由三种：`view-only`、`configuration`、`standalone`。
- `processes check` 的规则见规格；跨功能的相邻两步要有任一方向的 `EDGE`（衔接常常只写在一边）。
- 一名写作代理写全部流程；操作超过 400 个时按业务域分成两半，各自以本半的业务域为起点、步骤可以跨出去，`outside` 只管本半的操作；脚本合并，步骤序列完全相同的两条流程合成一条。
- 不派核验代理：流程里除名字外都是事实里的原名，检查逐字核对；名字只是标签。顺序是否合理（同一功能内两步的先后）检查不了，由验收的独立读者测量。
- 备选：让模型写触发条件与结果两句话。否决：那是转写，需要再加一层核验；结束状态取状态图的原名已经够读者看懂一条流程在哪里结束。

### D9 业务流程一章

- `processes render` 生成 `chapters/processes.md`：一级标题与小节标题取固定文字；每条流程 `## P<n> <名字>`，下面是业务域、`flowchart LR` 流程图（节点「角色：操作」，按功能放进 `subgraph`）、步骤表、结束状态；每步的引文取这个操作的三级小标题下第一组引文。
- 覆盖一节：`outside` 按理由分组；没被任何相邻两步走过的 `EDGE`。
- 生成后 `check` 照常检查这一章（引文、代码词）；它是脚本写的，不通过时不重写，只报原因（与设计问题一章相同）。

### D10 流程的精简项

- 批 `p1…pn`：按流程清单的顺序装批，每批步数之和不超过 60。
- 写作代理读本批流程在业务流程一章里的小节、这些功能章节的操作与规则节，写项；项多一个必填字段 `process`（`P<n>`），维度限 `duplication`、`complexity`、`redundancy`、`manual`、`dead-end`，`features` 必须是这条流程的功能。
- 不写卡、不分配候选。核验、删减与业务域批相同。

### D11 对策

- `remedies inputs "$OUT"` 打印三张表：缺陷（编号、等级、类别、功能、短标题、引文）、设计问题（编号、维度、影响、流程、功能、标题、引文）、流程（编号、名字、功能）；写作代理只从这些表引用，必要时回读章节原文。
- 章节结构见规格。措施是列表项，开头是加粗的措施类型（固定文字），结尾是方括号里的编号，例如 `[R12, D3]`。
- `check remedies` 在原有规则之外检查：编号存在、类型在表里、流程小节的标题是「P<n> <名字>」且与清单一致、每条措施与清单条目至少引用一个编号。
- 覆盖缺口不让模型写：`remedies coverage "$OUT"` 算出没有措施引用的 `high` 设计问题与 P0 缺陷，拼装与页面都在对策末尾生成这一节。
- 状态里的 `inputs` 增加 `processes.json` 的摘要。
- 备选：让模型自己在末尾写「未覆盖」一节。否决：这是结构化事实，模型转写会漏。

### D12 页面

- 「业务流程」一页：路由 `#/product/processes` 与 `#/product/processes/P<n>`，导航放在业务域之后；流程图与步骤表来自章节（页面不重算）。功能页列出经过它的流程（从章节的步骤表反查）。
- 问题页：行的编号与改进建议的链接来自对策里的 `[...]` 引用；改进建议页把 `[R12]` 渲染成链到问题页那一行的链接，每条措施有锚点。
- 对策里一个编号都没有时，按旧输出处理，链到类别或维度一节。
- 固定文字新增：业务流程一章与页面的标题、覆盖小节、`outside` 的三个理由、措施类型、对策的固定小节名与覆盖缺口一节。

### D13 验收的判据（事先定死）

在验收副本上，每个切片只跑一轮，结果照记，不事后调阈值：

- **绊线**：(1) 办公地点名单的两套判断（一个功能的章节在两行里写前端 4 个、后端 7 个；另一个功能的章节写界面按 5 个国家名、服务端按 7 个）成为至少一项保留的矛盾或不一致，卡引用这些行；(2) 验收副本上 6 个两套实现的功能，每个都有保留的两套实现项，或一条验收人同意的排除。
- **候选守恒**：每个来源的三个桶相加等于候选数；报出「没判」的比例，不设阈值。
- **植入回放**：在副本的章节里植入 10 处（5 处矛盾、5 处重复，跨不同业务域，由验收代理事先写好、不告诉写作代理），只重跑设计问题阶段；召回 ≥ 7/10 为达标，否则照记未达标并逐条归因（没写成卡、卡被删、对比批漏配）。
- **精度**：保留的对比项不超过 30 项时全量、否则分层抽 30 项，由独立代理读卡引用的章节与源码行判断；报出精度。
- **流程**：清单检查通过即守恒成立；两名独立读者各取两个业务域，只读章节列出流程，按「同一组操作」对照，报出两边各自有、对方没有的流程。
- **装置**：每条新检查先用已知不合格的样本（编出的操作、无交接的跳转、一边的卡、不存在的编号）证明它会拒绝。
- **花费**：每个切片先在一个业务域上跑、按实测外推全量再跑；与上一轮设计问题阶段的花费对比写进验收记录。

## Risks / Trade-offs

- [写卡挤占写项] → D4 的对比与预先写好的退路（单独的写卡代理）。
- [约 1000 张卡、按种类分批会漏掉跨种类的配对] → 植入回放测量召回；拆批规则固定，不按语料调。
- [流程守恒的压力让写作代理凑流程] → 「流程之外」有三个正当的理由；独立读者对照测量凑出来的流程。
- [一部分功能没有衔接一节或衔接为空（验收副本上约 15 个）] → 它们的操作只能独自成流程或进 `outside`；覆盖一节看得见，不靠模型补边。
- [同一处前后端不一致既可以看作设计问题，也可能已作为缺陷写进缺陷一章，核验会按「只是缺陷换了说法」删掉它] → 绊线 1 照记结果；删掉时看缺陷一章是否已有这一条，有就记为「已在缺陷里」，不改核验规则。
- [字典比对里有噪声（同义的取值写法不同）] → 由对比写作代理用「两边一致」排除，桶里看得见。
- [花费是推算] → 设计问题阶段预计 1.8 倍（S2 +0.1、S3 +0.3、S4 +0.15、S5 +0.25）；每个切片先标定。
- [页面集成的工作量没算进模型花费] → 页面放在最后一个切片，前面的切片不依赖它。

## Migration Plan

- 旧输出里的 `cross.json`、`cross.unpruned.json`、`cross.verdicts.json`：`review status` 不再列 `cross`，下次运行设计问题时 `review reset` 清掉；删除记录里旧的 `cross` 条目保留。
- 旧的业务域批文件没有 `cards`：`review render` 按缺 `cards` 拒绝，所以下次以 `--review` 运行时这些批重写；对策随之重写。
- 页面读旧输出：没有业务流程一章就不显示那一页；对策没有编号就链到类别或维度一节。
- 回退：按切片的提交逐个 revert；每个切片的产物在副本上可以单独删除重跑。
