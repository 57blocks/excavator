## Context

动机与数字见 proposal。`validator-leading-lines`（#89）之后的现状：锚点在起点 ±1 行或跳过前导行之后的那一行找名字，名字必须就在那一行；`calls` 证据只看被引用的一行；边的「读图」规则要求端点锚点精确。`CONSTRUCT_SCAN_LINES`、`construct-too-long` 缺口、`LEADING_SYNTAX` 的扩展名表、`exactAnchors` 集合都已存在。

剩下的 70 条（真实冒烟，74 文件 Java 子项目）按机制：

| 类 | 条数 | 机制 |
|---|---:|---|
| `calls` 边 | 50 | 证据行是表达式起点，被调用者的名字在其后 1 到 11 行 |
| 折行声明头，锚点 | 4 | 带注解的方法：跳过注解后是 `public void`，名字在再下一行 |
| 折行声明头，边 | 16 | 上面 4 个方法的 12 条边，加 2 个不带注解的方法（`private void` 一行、名字下一行，锚点靠 ±1 通过但不精确）的 4 条边 |

此前这两件事和 #89 合在一个变更（#88，已关闭）里评审了三轮。前两轮的重要问题都出在这两部分的文字启发式里（把一行语句当成折行声明头，把行尾的 `*`、`++`、`--` 当成续行），第三轮出在边规则与 ±1 的交互里。#89 吸收了第三轮的教训与注解、注释部分的所有类，本变更把剩下的部分用同样的方法做：依赖语言的假设按扩展名限定，按语言写表，用变异验证表会咬人。

AI-first scope gate：这是机器校验器本身的判定规则，要确定性复用，没有 skill / prompt 的替代。

## Goals / Non-Goals

**Goals:**
- 上表三类在真实冒烟图上归零，且归零不靠放宽到错位也能通过。
- 校验器仍然看得见已知假样本（证据行指向无关语句、指向声明行、改错被调用者名），宽容只给抽取器写的证据，且只给有这种语法的语言。
- 越界结果可见：过长的表达式与声明头既不静默放过也不误报。

**Non-Goals:**
- 不改抽取器、`deploy/`、`EXCAVATOR_MAX_CONTRADICTED`；不引入语言解析器。
- 不处理 Python、Ruby 的 `calls` 表达式：它们靠缩进或 `end` 结束语句，隐式续行只发生在括号里，没有真实样本，也没有验证过的规则。

## Decisions

**D1　依赖语言的假设按扩展名限定，一开始就做。** #89 的两轮评审都是在同一类上找到实例：一行文字在某种语言里是语法，在另一种里是语句（`@log.info(item)`、`[a, b] = [b, a]`、表达式续行里的 `*`、`//`）。所以两条规则都带一张语言表，写在代码旁，不在表里的语言不享受宽容（可见、方向安全：多报矛盾，不多确认）：
- 表达式扫描：有大括号加语句语法的语言（Java、Kotlin、Scala、Groovy、Swift、Dart、TypeScript、JavaScript、C#、Rust、PHP、Go、C、C++）。
- 折行声明头：声明总是以 `;` 或体结束的语言（Java、C#）。在 Kotlin、Scala、Swift、Dart、TypeScript、Groovy、PHP 里，一行可以结束一条声明（`private x`），只有修饰符和单词的一行本身就可能是完整声明，下一行是另一个成员，所以这些语言不在表里（评审第 1 轮：Kotlin 的 `sealed interface Shape` 被当成没写完的头）。

**D2　`calls` 按整条表达式核对，只对抽取器写的证据。** 证据行是表达式起点，被调用者名字在后。表达式边界：
- 顶层（括号深度 0）的 `{` 是块体（函数体、分支），到此结束，不并入表达式。否则指向 `void m() {` 的错边会被体内任何一次调用确认，已知假样本（证据行指向声明行）就看不见了。括号里的 `{`（lambda、匿名类）不受影响，所以 `.map(x -> {…}).collect(…)` 的 `collect` 仍能找到。
- 顶层 `;` 结束。
- 括号深度回到 0、行尾不是续行、下一个非空行也不以续行开头时，在这一行结束。每行先查 token 再判是否结束，所以终止行本身也算。查 token 读的是这一行里的**代码**：注释去掉、字符串与字符的内容抹掉，再按整词匹配。后续行的名字出现在注释或字符串里（`.bar(); // helper`、`.log("helper failed")`），或者是更长名字的一部分（`.helperFactory()`），都不是被调用者；`main` 对这些行是矛盾，不能让扫描把它们确认掉。续行的判据（行尾的 `.` 等，下一行是否以 `+` 开头）读同一份代码，所以字符串里的 `//` 不会被当成注释而截掉行尾的点，下一行以 `++` 开头是自增而不是续行。这四处是评审第 1 轮之后我自己继续往后行放宽的方向审出来的，先写成失败用例确认都被错误确认，再改。

评审第 2 轮指出声明头的后续行仍按子串匹配，是同一类我只修了一半。类是：**凡是在被引用的那一行之外找名字的地方，都必须按代码、整词匹配**。所以收成一个函数 `namedInCode`，用在三处：表达式的行、声明头的行，以及 #89 里「跳过前导行之后的那一行」（评审没有点到，但它是同一个子串匹配：`@Test` 之后的 `public void helperFactory() {}` 会让节点 `helper` 的锚点变精确）。被引用的那一行本身、起点 ±1 行内的名字保持 `main` 的读法（子串），因为那是 `main` 的行为，不是新放宽。续行的前瞻也读代码：下一行以注释开头、或夹着只含注释的行，注释之后的续行照读；下一行打开一个没闭合的块注释时，扫描在那一行停下（读不到头就停），它遮住的行不会被当成代码。

`source: "model"` 的证据不享受这条：模型写的引用是不可信输入，只核对被引用的那一行。带自己 `token` 的条目已经写明「这一行写着什么」，引用错行就是矛盾，也不享受。

**D3　续行的判据偏向「少认」。** 只认行尾的 `.`（不是 `..`）、`\`、`=`、`&&`、`||`、`->`、`=>`、单个 `+`，和下一行以 `.`、`?.`、`&&`、`||`、`+`、`?`、`->`、`=>`、`|` 开头。行尾的 `,`（深度 0 时它表示外层列表，下一行是另一个元素）、`++`、`--`、`-`、`*`、`%`、`&`、`|`（引用类型）、`<`、`>`、`/`、可空类型的 `?` 以及块注释的结尾都不算。少认一个续行只会多报一条矛盾；多认一个会把错边确认掉。#88 的评审在 `*` 与 `++` 上各找到过一次。

**D4　折行声明头：以修饰符开头，只含单词，且本身不是完整声明。** 声明本身也会折行（`public void` 单独一行、方法名在下一行）。#89 的锚点检查在跳过前导行之后只看那一行；本变更在那一行以声明修饰符开头、且只含单词与类型（没有括号、花括号、分号、`=`）时，名字可以在其后只含单词的行里，直到出现第一行带这些符号的行。修饰符取一个封闭集合，只收不会开始语句的词：`export`、`const`、`static`、`async` 都会开始语句，不收。「整行只有单词」不够，#88 的评审里 `import os`、`return x`、`pass` 都被当成了声明头。

三条保险，都是评审第 1 轮的发现：带声明关键字（`class`、`interface`、`enum`、`record`、`struct`、`delegate`、`event`、`namespace`、`operator`）的行已经有名字（`private class Marker`），不是没写完的头；续行如果以修饰符或 `@` 开头，它是自己的声明，不是头的续行（`public Foo` 之后的 `public void helper() {}`）；只在 Java 与 C# 里读（D1）。续行以返回类型开头（`public static` 之后的 `void bare() {}`）仍读。

靠这条找到的名字是精确的（名字在跳过前导行之后的声明头上），所以锚点进入 #89 的精确集合，能替引用它范围起点的边担保；这正是 2 个不带注解的折行方法的 4 条边归零的方式。

**D4b　词法读不到头就停下，不去猜。** 表达式扫描靠自己对字符串、字符、注释的判断去数括号，而这个判断在每种语言里都有盲区：跨行的字符串（Java 文本块、TypeScript 与 Go 的模板与原始字符串、C++ 与 Rust 与 Kotlin 的原始字符串、C# 的逐字字符串）、heredoc、跨行的块注释、Rust 的 `'`（字符字面量 `'('` 还是生命周期 `'a`）。评审第 1 轮在 Rust 的字符字面量与文本块上找到两个实例，它们是同一类：一个读了一半的字面量里的括号被当成了代码里的括号，扫描停不下来，一路读到函数的结尾，被函数体里别处的调用确认。

不逐个补盲区，而是定一条规则：**扫描器在一行末尾仍处在「字符串或块注释没有闭合」的状态，或碰到 PHP 的 heredoc，就停止扫描。** 停下的方向永远是只看被引用的那一行，也就是 `main` 的行为，只会多报矛盾，不会多确认。代价：参数里带跨行字符串的表达式，被调用者在字符串之后的，被报为矛盾。Rust 的 `'` 单独读：匹配 `'x'`、`'\n'`、`'\u{…}'` 的是字符字面量，整体跳过；其余是生命周期，不是引号。

同一条规则用在跳前导行的括号读取上（`readBrackets`）：注解的参数里开了一个没闭合的字符串或块注释，这一行不是前导语法，构造从这一行开始。这是 #89 的代码里同一类的潜在问题，评审没有点到，但它读括号用的是同一套不完整的词法。

**D5　上限仍是一个可见的桶。** 声明头或表达式超过 `CONSTRUCT_SCAN_LINES`（400）仍没有结束时，节点或边标 `unverified`，计入 `construct-too-long`，既不确认也不算 contradicted。上限只对抽取器写的证据可达，模型引用不走扫描，所以上限不能被用来让一条虚构的边「过关」。

**D6　改动的数据流。** 新增两个纯函数：`findTokenInDeclarationHead`（锚点检查在跳过前导行之后调用，命中即精确）与 `findTokenInExpression`（边检查对 `calls` 调用），返回「行号 / 过长 / 无」三态；两张语言表放在 `LEADING_SYNTAX` 旁。`validateAgainstSource` 的结构不变。

## Risks / Trade-offs

- **[表达式扫描会越过 lambda / 匿名类的块体：指向 `submit(() -> {…})` 这类语句的错边，若被调用者恰好是块内的另一次调用，会被确认]** → 不能改成「遇 `{` 即止」：`list.stream().map(x -> {…}).collect(…)` 的 `collect` 在块之后，那样会把大量真边误判。接受这个精度代价，在验收里专门植入这类假边并如实记录被确认的比例；不事后挪规则。
- **[续行判据漏掉某种真实写法]** → 偏向少认，漏掉只会多报矛盾；真实图里 50 条 `calls` 的距离分布与类型要全部覆盖，归零作为验收。
- **[声明头的修饰符集合漏掉某种真实写法]** → 同上，方向安全。
- **[把一行语句当成声明头或续行，在没有分号的语言里放过错边]**（#88 评审的类）→ 两条规则都按扩展名限定（D1）；整类用按语言写的表测试：各语言的语句形状，必须不被当作声明头、不被当作续行；每行写两遍再接目标，使「把它当前导行 / 续行」的规则一路跳到目标而被确认，从而被测出；表用变异检查过会咬人，存活的变异说明表漏了一种，补表后重跑。
- **[字符串、字符或注释的词法有盲区，一个读了一半的字面量里的括号被当成代码里的括号]**（评审第 1 轮 2 个实例）→ 不补盲区，读不到头就停（D4b）。整类用按语言写的表测试：各语言里「字符串或注释跨行、后面还有括号」的写法必须判矛盾；同一段文字在一行内闭合的必须读；Rust 的字符字面量与生命周期各一个正向用例。表用变异检查过会咬人：被调用者要写在被遮住的那段内容里，才能区分停与不停。
- **[语言不在表里，它的多行 `calls` 与折行声明头仍被报为矛盾]** → 可见、方向安全，往表里加一行即可扩展；验收只覆盖 Java 一种真实语言，其他语言靠夹具。
- **[400 行上限的 `unverified` 被误当作「通过」]** → `unverified` 不进 `edge-contradicted`，但缺口 `construct-too-long` 带计数与样例；验收记录要写该计数。

## Migration Plan

校验器是纯函数加一个 CLI，输出字段只增不减，本变更不新增输出字段（`construct-too-long` 由 #89 引入）。回滚就是还原 `validate-graph.mjs`；旧阈值与 `deploy/` 未动。
