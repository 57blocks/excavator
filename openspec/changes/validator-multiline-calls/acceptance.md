## 3. 召回：植入假样本

在真实图的副本里按固定种子植入 505 个，决定与重放都在副本里做，仓库不动。每个植入先用与验证器规则无关的纯文本判断确认确是坏的。除 #89 的 415 个之外，本变更新增两类（`calls` 边）：证据行改指表达式之后相邻的语句（1 到 3 行，被调用者不在其后 12 行内）60 个，证据行改指别的函数的开头（行尾是 `{`，被调用者不在其后 12 行内）30 个。

- 守恒：植入数 = 报出数 = 457，漏报 0；旧验证器同样 457/457，装置对照成立。
- **lambda 的精度代价**：植入 3 个，新验证器只报出 1 个，确认了 2 个。这是设计里写明并接受的代价：表达式扫描会越过括号里的 lambda 块体，不能改成「遇 `{` 即止」，否则 `.map(x -> {…}).collect(…)` 的 `collect` 会被误判。样本只有 3，比例不能外推；`main` 与 #89 对这类植入是 3/3，本变更让这一类变成 1/3，是本变更相对 #89 唯一放宽的地方。
- 新验证器在植入图里多出 123 条「既不是植入、也不在基线里」的矛盾，全部触及一个被植入错位的节点，没有一条在外面。这是预期的一致性：锚点已错的节点，不再替引用它范围起点的边担保。

## 4. 变异

在已提交的版本上把每条规则改坏，确认至少一个用例变红，随后从提交还原。24 个变异，涵盖：声明头在所有语言里生效、`export` 与 `static` 当修饰符、整行只有单词就算头、头的第一行不必以修饰符开头、完整的声明行被读过去、过长的头不报告、头命中不精确；表达式在所有语言里扫描、块体并入表达式、`;` 不结束表达式、行尾 `*`、`,`、`++`、`-`、可空 `?` 当续行、下一行一律算续行、模型引用与带 `token` 的证据也被扫描、表达式上限失效、行尾注释遮住续行、撇号永远不是引号、Rust 生命周期当引号、过长的表达式被判矛盾。

第一次有 3 个变异存活，说明测试对这三条规则没有约束力：

- 完整的声明行被读过去：原有护栏的第一行不以修饰符开头，走不到这条规则。补了一个以 `public` 开头但已写完的行。
- `;` 不结束表达式：缺一个 `;` 之后紧跟以 `.` 开头的行的用例。补上。
- 行尾注释遮住续行：缺 `client. // note` 这种点在注释前面的用例。补上。

补用例后 24 个全部被拦住。另外一个用例我第一次写错了：用 Java 的 `char c = '{';` 想表达「撇号是引号」，但 `;` 已经结束了表达式，换成没有分号的 Kotlin 才表达出来。

## 6. 评审第 1 轮之后

reviewer 找到 3 个重要问题，都是验证器确认了 `main` 判为矛盾的东西。逐个复现：

1. Rust 里字符字面量里的括号（`s.find('(')`）被当成代码里的括号，`;` 不能结束表达式，一路读到函数结尾，被函数体里别处的调用确认。原因是我把 Rust 的 `'` 排除在引号之外（为了生命周期）。
2. 跨行的字符串（Java 文本块、TypeScript 模板字符串）里的括号同样被当成代码里的括号，遮住了闭合调用的 `);`。每一行的引号状态都重置，所以闭合行上的引号被当成开头。
3. `sealed interface Shape`、`private class Marker` 这类已经写完的无体声明被当成没写完的声明头，下一行是另一个成员，错的锚点被判为精确。

判断：前两个是同一类，**扫描器靠自己对字符串、字符、注释的判断去数括号，而这个判断在每种语言里都有盲区**；第三个是**一行只有修饰符和单词，在允许换行结束声明的语言里本身就可能是完整声明**。顺着类往外查又找到：跨行块注释、C# 的 `public int Count` 属性后面跟另一个成员、`public Foo` 后面跟另一个以修饰符开头的成员。11 个复现用例里 7 个被错误确认。

不逐个补盲区，改的是规则：

- **读不到头就停**：扫描器在一行末尾仍处在字符串或块注释之中，或遇到 PHP 的 heredoc，就停止扫描，只看被引用的那一行（`main` 的行为，只会多报矛盾）。Rust 的 `'` 单独读：字符字面量整体跳过，其余是生命周期。同一条规则用在跳前导行时的注解参数上。
- **折行声明头**：只在声明总以 `;` 或体结束的语言（Java、C#）里读；一行带声明关键字，或续行以修饰符、`@` 开头，都不是头。

- **先验装置**：新的两张表（词法读不到头、已经写完的声明行）在评审时的代码上 30 个红，包括评审点到的全部几个与我找到的同类。
- **变异**：33 个变异全部被拦住。第一次有 5 个存活（未闭合的块注释、heredoc、注解参数里的字符串与块注释、`export` 当修饰符），原因都是用例里被调用者不在被遮住的那段内容里，所以停与不停结果一样；改成被调用者写在被遮住的内容里之后全部被拦住。
- **真实图重跑**：与第一次完全一致。919 到 0；非 lambda 植入 457/457；lambda 1/3；多出的 123 条矛盾全部触及被植入错位的节点。折行声明头现在只在 Java 与 C# 里读，真实图是 Java，不受影响。

评审之外，我顺着「表达式后续行被放宽」的方向自查，找到四处同类，都会确认 `main` 判为矛盾的边，先写成失败用例（13 个红）再改：被调用者的名字出现在后续行的注释里（`.bar(); // helper`）或字符串里（`.log("helper failed")`），被调用者是更长名字的一部分（`.helperFactory()`），下一行以 `++` 开头被当成以 `+` 开头的续行，字符串里的 `//` 被当成注释截掉了行尾的点。改为后续行按代码匹配：注释去掉、字符串与字符的内容抹掉、整词匹配，续行判据读同一份代码。8 个变异里 7 个被拦住，存活的那个是等价变异（进入扫描的前提是被引用的那一行本身没有命中，所以第一行用子串还是整词没有区别），随死代码一起删除。真实图重跑结果不变。

## 7. 评审第 2 轮之后

reviewer 在声明头上找到一个重要问题：它的后续行仍按子串匹配，所以 `public void` 之后的 `helperFactory() {`，或夹在头里的一行注释 `// helper`，让节点 `helper` 的错锚点变精确，连带确认了 `main` 判为矛盾的 `contains` 边。另有一个小问题：规格说续行的前瞻读代码，实现读的是原文。

这是我上一轮自查里修了一半的类（后续行按代码、整词匹配，我只用在了表达式扫描上）。所以这一轮先列出所有在被引用行之外找名字的地方：表达式的行（已修）、声明头的行（评审点到）、#89 里「跳过前导行之后的那一行」（评审没有点到，同样是子串匹配：`@Test` 之后的 `public void helperFactory() {}` 会让 `helper` 的锚点变精确）。9 个复现用例里 4 个被错误确认；前瞻读原文导致 2 个合法的续行（下一行以注释开头、或夹了只含注释的行）没被读到。

改法：收成一个函数 `namedInCode`，三处共用；前瞻读代码，跳过只含注释的行。

- **先验装置**：新的两张表（别处的名字按代码整词计、前瞻读代码）在评审时的代码上 22 个红，其中包括评审点到的几个与 #89 的前导行。
- **变异**：8 个变异里 7 个被拦住，存活的 1 个是等价变异（前瞻里单独写的「遇到未闭合块注释就停」是多余的防线，因为扫描进入那一行时本来就会停），随多余的检查一起删除。
- **真实图重跑**：结果不变。919 到 0，非 lambda 植入 457/457。

评审之外，我再按「词法读不到头」的方向自查，找到字符串插值：插值里的代码可以带自己的字符串，引号错位配对后，字符串里的括号被数进代码、字符串里的名字被当成代码。按语言表（`${}`、`{$}`、`\()`、`$"`）读不了含插值的行：表达式扫描停下，`namedInCode` 当作没找到；没有插值的语言（Java、Go、C）照读，同样的文字在那里不被误停，有对照用例。15 个新用例先红，7 个变异全部被拦住，真实图重跑结果不变（Java，不受影响）。
