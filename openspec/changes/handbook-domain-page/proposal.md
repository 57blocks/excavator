## Why

页面的领域页只有「它做什么」和功能列表，技术视角多一张应用表。参考手册的领域页分七节：它做什么、功能一览、关键规则与状态、功能明细、代码在哪里、与其他领域的关系、已知问题。读者在领域页上看不到这个领域和别的领域怎样交接，也看不到它的代码在哪里、有哪些问题。

参考手册还有两张全局的图，我们都没有：
- 业务全景：领域之间的数据流；
- 技术架构：整体结构。

handbook-deep-entry 让条目有了「交接」：一个已核实的操作交给哪个功能、交什么。领域之间的关系可以由脚本从这些交接算出来，不需要模型另写。

## What Changes

- **领域关系由脚本算出**：
  - 一个已核实条目的交接，从本领域的功能指向别的领域的功能，算作「提供给其他领域」；反过来算作「从其他领域获得」。
  - 同一领域内的交接不算。
  - 只有已核实条目里的交接才算。旧格式 `/1` 的条目没有交接，它所在的领域就没有这类关系。
- **领域页按参考页的七节重排**，每节都只取脚本算出或已核实的内容：
  1. **它做什么**：已核实功能的用途（不变）。
  2. **功能一览**：按到达方式分组，每组带数量，每个功能链到自己的功能页。
  3. **状态与转换**：本领域已核实条目里的状态与转换，按功能列出。参考页的「关键规则」要判断哪些规则算关键，这里不做；规则留在功能页。
  4. **功能明细**：不在领域页展开，功能一览已链到各功能页。
  5. **代码在哪里**（只在技术视角）：
     - 改动最频繁的文件：代码健康的热点里，归属本领域功能的那些；
     - 引用最多的文件：本领域已核实条目引用的文件，按引用次数排；
     - 数据表：数据一节里，名字出现在这些被引用文件中的表；
     - 各应用的引用数（原来的应用表）。
  6. **与其他领域的关系**：分「从其他领域获得」和「提供给其他领域」两栏，每条写明两端的功能和交接内容，链到对方领域与功能。
  7. **已知问题**：发现里，属于本领域功能的那些组，链到发现页。
- **业务全景图**：在概览页，节点是领域，一条边是两个领域之间所有跨领域交接的合计，标交接条数。没有任何跨领域交接时写明没有，不画空图。
- **技术架构图**（只在技术视角）：在概览页，节点是应用与外部系统，边是已核实概览列出的调用方到外部系统。
- **`handbook.md`**：领域一节加「与其他领域的关系」；概览加两张图的 mermaid。
- 图在页面上用内联 SVG 画，布局由一个确定性的分层函数算出；同样的输入画出同样的字节。
- 页面数据格式升一版。

**不做：**
- 功能组的概览流程图（参考页每个原章导语的那张）。它把多个操作串成一条线，这个顺序在代码里证不出来。每个操作的时序图和状态图已经在功能页上。
- 「关键规则」的挑选。
- 应用之间的调用边：前端经 HTTP 调后端，事实图里没有这类边，脚本也没有可靠的依据。
