## 验收摘要

- **O1**：24 个单测通过，覆盖规格的全部场景；每类断言都用注入变异确认能变红。全量门在三个代码提交上各跑一次，均通过。
- **O2**：花费、轮数、modelUsage、子代理构成与上一个变更的独立数字逐项相同。墙钟差 11–17 秒，是进程起止与记录内时间戳的口径差，已解释，`run` 两种都记。截断记录给出规格要求的缺失项。
- **O3**：见 2.2。报告与 jq 抽查逐项相同；发现的「记录里没有的调用」已单列。

两个规模点的对比（缓存读占比按 modelUsage 总量算）：

| | 夹具（70 个文件，不含 F4） | cargotracker（209 个文件，含 F4） |
|---|---|---|
| 花费 | $6.32 / $8.47 | $30.42 |
| 每文件（派生） | $0.090 / $0.121 | $0.146 |
| 墙钟 | 20 / 26 分钟 | 85 分钟 |
| result 事件（编排者被唤醒的段数） | 12 / 6 | 1 |
| 编排者缓存读占比 | 69% / 70% | 22% |
| 编排者上下文（首次 → 最大） | 8.5 万 → 20 万 / 8.4 万 → 25 万 | 8.5 万 → 26 万 |
| file-analyzer 缓存读占比 | 19% / 18% | 31% |
| summary-verifier 缓存读占比 | — | 27% |
| 记录里没有的调用 | 0 | 11% |

- 阶段时长（cargotracker）：setup 1.8、F1 0.2、F2 23.5、F3 16.1、F4 43.0、F5 0.6 分钟。F4 占一半墙钟，缓存写的 42% 来自 summary-verifier。
- 编排者不是固定大头。夹具上它占七成，是因为文件少而唤醒段多。cargotracker 上 F2 与 F4 子代理占主导，编排者只占两成多，但它的上下文随派发次数一路增长：50 次派发从 8.5 万涨到 26 万。派发再多一个数量级，单个会话装不下，所以大仓库必须能分块跑、能续跑，这正是第 6 步。
- 子代理的花费随批数线性增长，编排者的花费随唤醒段数和派发次数增长。预估要按阶段、按批数分别估，不能按文件数线性外推。

**第三个规模点：现在不跑。** 理由：第 6 步的验收本来就要求在一个测试仓库上，比对运行前的预估与实际运行；那次实际运行就是第三个点，而且是独立于标定数据的点。现在单独再跑一次，只能多一个标定点，花费约是 cargotracker 的数倍。代价：在第 6 步之前，增长曲线只有两个点，而且两点在是否含 F4 上不同。按阶段、按批的费率拆开估可以避开这个差异，但 F4 的费率只来自 cargotracker 一个点。

已知局限：
- 「记录里没有的调用」的归属查不出。总花费与 modelUsage 是可靠的，按角色的占比要扣掉这一行再看。
- 输出 token 不按角色拆（规格如此），按角色的花费因此只能看输入侧占比。
