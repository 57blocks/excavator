## Context

动机见 proposal.md。与本设计相关的现状：

- 事实层（`.excavator/knowledge-graph.jsonl`）只有文件、函数、类、配置与 imports/calls 等边，没有页面、菜单、字段这类产品层事实。产品层的东西要么由脚本从源码列出，要么由模型读源码写出、再由脚本核对。
- `excavator-prd-report` 的入口列表（`lib/entrypoints.mjs` + `entrypoint-catalog.json`）已经能按框架列出页面、路由、定时任务与 `main`，在 go-multirepo 上列出数百个候选，其中页面约占三成。它是一份确定性的完整候选集，新 skill 需要同一份东西。
- 同一 skill 的 `lib/normalize.mjs` 有「引文在文件里恰好出现一次」的规范化查找。
- 被替代的旧 skill 在 go-multirepo 上的章节：证据块约占三成字数，正文里服务名与角色代码出现上千次，而它的 lane prompt 里早就写着「正文不放代码」。只靠写作规则挡不住技术词进正文。

## Goals / Non-Goals

**Goals**
- 产品地图：每个候选恰好进一个功能或可见的未归入清单；每个功能标明读者怎样到达它。
- 功能条目：结构化，每一项都有原文出处，值与引文由脚本核对，读者可见的文字过禁词门。
- 只读源码，不读任何生成的文档；只写 `--out`。

**Non-Goals**
- 不判断条目语义上对不对（干净上下文核对是下一片），本片只保证「引文真实存在、值出现在引文里、读者文字里没有代码」。
- 不写问题、不排序。
- 一次运行只出一种语言；把已有结果翻译成别的语言、页面内切换语言是下一片。
- 不按框架写字段或规则的确定性抽取器（见 D5）。

## Decisions

### D1 为什么写代码（AI-first scope gate）

模型做的：把候选归成区域与功能、判断到达方式、读源码写条目。这些是判断与写作，留在 `SKILL.md` 和 lane prompt 里。

脚本做的只有机器校验与确定性产物：候选列表（完整候选集）、守恒、引文与路径、值核对、禁词门、状态记录、拼装。这几样都是「模型写了、但必须能被机器拒绝」的东西；旧 skill 的经验是写作规则单独挡不住技术词进正文，所以禁词必须是门而不是提示。

### D2 目录、命令与产物

`skills/excavator-product-handbook/`：`SKILL.md`、`handbook.mjs`（命令入口）、`lib/`。

| 命令 | 作用 |
|---|---|
| `candidates <project> [--scope <dir>]` | 列入口候选，写到标准输出 |
| `check-map <out> --project <root>` | 地图的格式、守恒、引文、禁词 |
| `check-entry <out> <id> --project <root>` | 一个条目的格式、引文、值、禁词；把结果记进状态 |
| `mark <out> <id> dispatched\|failed …` | 记录派发与无产出的失败 |
| `check-ui <out>` | 固定文字表的键、占位符（D12） |
| `assemble <out> --project <root>` | 拼出 `handbook.md` |
| `page <out> --project <root>` | 写出 `handbook.html`（D13） |

退出码沿用仓库惯例：0 通过，1 检查不过（逐行打印原因，最后一行 `Next:` 说下一步），2 用法或读写错误。

`<out>`（默认 `<project>/.excavator/product-handbook`）：

| 文件 | 写者 |
|---|---|
| `candidates.json` | `candidates` |
| `map.json` | 编排者（模型） |
| `entries/<id>.json` | 该功能的 lane |
| `state.json` | `check-map`、`check-entry`、`mark` |
| `ui.json` | 语言不是英文时由翻译子代理写；英文时由脚本从随 skill 发布的表复制 |
| `handbook.md` | `assemble` |
| `handbook.html` | `page` |

格式串：`excavator-product-handbook-candidates/1`、`excavator-product-handbook-map/1`、`excavator-product-handbook-entry/1`、`excavator-product-handbook-state/1`。

### D3 入口列表迁到新 skill

`entrypoints.mjs`、`entrypoint-catalog.json` 与 `normalize.mjs` 移到 `skills/excavator-product-handbook/lib/`；`excavator-prd-report` 改为从新位置引用。列表函数返回不带 `format` 的对象，由各自的命令盖上自己的格式串，所以旧 skill 的 `entrypoints.json` 一个字节都不变。

备选：新 skill 从旧 skill 目录引用。否决：旧 skill 迟早要删，到时还得再搬一次，而且新代码会留下指向旧名的路径。

### D4 产品地图

`map.json`：

- `areas`：`{id: "A1", name, evidence?}`。区域名是读者可见的文字。如果它就是源码里的菜单分组名，必须带引文；如果是模型起的名字（例如「自动进行的工作」），可以不带引文，但要过禁词门。
- `features`：`{id: "F1", name, area, reach, label?, evidence?, candidates: [...], seedFiles: [...]}`。
  - `reach` 取 `menu`（从菜单进入）、`link`（不在菜单里但能到达：公开链接、邮件里的链接、页面内跳转、菜单被注释掉而路由仍注册的页面）、`automated`（定时或后台）、`interface`（给外部客户端或其他服务的接口）、`operator`（运维命令）之一。
  - `menu` 与 `link` 的功能必须有 `label` 和 `evidence`，并且 `label` 出现在引文里：菜单项就引菜单配置那一行，链接就引路由注册或发出链接的那一处。
- `unassigned`：`{candidate, reason}`，例如测试代码、死注册、出站 HTTP 调用被模式误认成路由。
- `roles`：`{label, evidence}`，项目里的角色，条目只能从这里取。

`check-map` 检查以下各项，不成立的逐行打印：
- 每个候选恰好在一个功能的 `candidates` 里或在 `unassigned` 里，被重复归属或遗漏的候选逐个列出；
- 种子文件都存在；
- 每段引文都通过 D6；
- `label` 出现在它的引文里；
- 所有读者可见的名字都过 D7。

`reach` 不是问题判定：`link` 只是一个可见清单，下一片的问题发现会逐项判断。

### D5 功能条目

`entries/<id>.json` 的顶层键：`id`、`purpose`、`who`、`where`、`screens`、`operations`、`states`、`notifications`、`automatic`、`unknowns`。各项都是 `{…读者可见的字段…, evidence: [{file, passage}]}`：

- `who`：`{role, can}`。`role` 必须是 `map.roles` 里的某个 `label`。
- `where`：读者走到这个功能的路径（菜单 → 子菜单 → 页面标签），每一级都是引文核对过的标签。
- `screens[].fields[]`：`{label, rules: [{side: "frontend"|"backend", text}]}`。两侧分开记，下一片的跨功能对比就靠这个分侧。
- `operations[]`：`{name, sentences: [{text, evidence}]}`。每个操作是一段自由叙述，按句切开，每句自带出处；这是给非技术读者的可读部分。
- `states[]`：`{label, meaning}`；`notifications[]`：`{trigger, recipient, channel, content}`；`automatic[]`：`{when, effect}`。
- `unknowns[]`：`{item, searched}`，写明代码里定不下来的内容和搜索过的范围。没有出处，但要过禁词门。

值不让模型自由转写。备选是按框架写抽取器（gin 的 binding tag、Go 常量、TS enum），被否决，原因有三：
- 违背「框架知识放在能承载它的最低一层」，每个框架一套代码；
- 前端校验写法五花八门，抽取器覆盖不全反而制造静默缺口；
- 现在还没有转写错误率的数据。

改为：值必须连同引文一起写，脚本核对「值 ⊂ 引文 ⊂ 文件」（D6、D8）。本片的真实运行会量出转写错误（O6）；如果错误集中在某类值上，再为那一类做抽取器，进 roadmap。

### D6 引文核对

- 路径以项目根为基准解析，真实路径必须落在根内（经 `..` 或符号链接越界的一律拒绝），且不在 `.git`、`.excavator`、`node_modules`、`vendor`、`dist`、`build` 下。
- 引文按 `normalize.mjs` 的规范化（空白、换行），在该文件里必须恰好出现一次；出现多次时提示加长引文。
- 一项的多段引文各自核对。

### D7 禁词门

对读者可见的字段（地图里的名字，条目里除 `evidence` 以外的所有字符串）逐个 token 检查。拒绝以下几类：

| 类别 | 判据 |
|---|---|
| 下划线标识符 | 两个词字符之间夹 `_` |
| 驼峰标识符 | 小写字母后紧跟大写字母 |
| 多峰帕斯卡词 | 例如由两段「大写+小写」直接相连组成的词 |
| 路径 | 以 `/` 开头、后跟词字符的片段 |
| 源码扩展名 | `.go`、`.ts`、`.tsx`、`.js`、`.jsx`、`.java`、`.py`、`.sql`、`.json`、`.yaml`、`.yml` |
| 调用形 | 词后紧跟 `(` |
| 成员目录名 | 候选文件路径的第一级目录名，即多仓项目的各成员仓库名 |

豁免：命中的片段落在同一文件（地图或该条目）里某个已经通过引文核对的标签之内，就不算违规。例如菜单名本身是驼峰形，引文核对过，就允许出现。

拒绝时打印字段路径、命中的片段和类别。备选是由模型自查，被否决，理由见 Context。

### D8 值核对

- 每个 `label` 必须出现在本项的某段引文里。
- 读者可见文字里的每个数字（连续数字，允许千分位逗号与小数点）去掉千分位后，必须作为数字出现在本项的某段引文里，引文里的数字同样去掉千分位与下划线分隔后再比较。
- `unknowns` 没有出处，不做值核对，只过禁词门；它说的是「定不下来」，不是事实陈述。
- 序号、日期等合法但不来自源码的数字，只能出现在拼装时生成的部分（编号、计数），不能写进模型写的文字。SKILL.md 要求数字一律写成阿拉伯数字，用词写数量（例如「两级审批」）的情况脚本挡不住，记为残余风险（R2）。

### D9 lane、状态与续跑

- 编排者为每个要写条目的功能派一个前台子代理，最多 `--concurrency`（默认 3）个同时运行。子代理只读该功能的种子文件，以及否定类陈述所需的全项目搜索，只写 `entries/<id>.json`。
- `check-entry` 通过记为 `checked`，不通过记为 `failed` 并保存原因。第一次失败后，带着原因重派一次；第二次仍失败就保持 `failed`，文件保留供查看。
- 状态只经过脚本改变，编排者不手改 `state.json`。
- 重跑时，已 `checked` 的功能不再写；`--fresh` 清空 `<out>`，规则同旧 skill：只清空不存在、为空或含本 skill `state.json` 的目录。
- `--features <ids>`：只为这些功能派 lane。地图仍覆盖全部候选；没写条目的功能在手册里列为「未写」。

### D10 不读生成的文档

- SKILL.md 与 lane prompt 明令：只读项目源码与事实层（`knowledge-graph.jsonl`、MCP），不读 `.excavator/` 下别的产物，也不读项目里由本工具生成的文档。
- 机器层面，D6 拒绝 `.excavator/` 下的引文路径，生成文档的内容进不了条目的出处。读了但没引用这种情况，由 O6 检查运行记录。

**domain graph 也不作输入。** 我在 go-multirepo 上看过 `excavator-domain` 的产物：6 个域、29 个流程、157 个步骤，流程名已经是业务说法。它看起来能直接当区域和功能的草稿，但不用，理由有四：
- 它也是模型写的产物。拿它分区，地图就继承了另一个模型的归组，验收时也分不清地图是从源码推出来的还是照抄的。
- 它不守恒：没有定时任务、对外接口和多个菜单区域，29 个流程和入口候选对不上。
- 它的业务规则（共 27 条）没有出处，不能当事实。
- 它有自己的修订和新鲜度，依赖它就多了一个「先跑 domain」的前提。

它的用处放在两处：
- O6 里由审读者拿地图的区域和 domain 的域对照，作为分区合理性的旁证。
- 做跨功能问题的那一片里，它的跨域交互可以当搜索起点，但每条都要从源码重新证明。

### D11 拼装

`handbook.md` 由 `assemble` 确定性生成，同样的输入得到同样的字节，不含时间和本机路径：

- 文档开头：按区域列出功能，并按到达方式计数。
- 每个功能一节，按条目字段排版：
  - 用途、谁能用、在哪里；
  - 字段表，三列：字段、前端规则、后端规则；
  - 各操作的叙述，句子原样拼接；
  - 状态表、通知表、自动行为；
  - 「代码里无法确定的内容」。
- 覆盖一节：候选总数与守恒结果、`unassigned` 清单、`link` 功能清单、没有条目或条目失败的功能。

正文不放出处，出处留在 JSON 里。小节名与表头取自 `ui.json`（D12）。

### D12 语言

`--language` 决定所有读者可见文字的语言，可以是中文、英文或其他语言，默认英文。

- **叙述**：地图里的区域名、条目里的叙述，由模型直接用该语言写。源码里的标签保持原文，不翻译，这样读者能对上自己在产品里看到的字。
- **固定文字**：`handbook.md` 的小节名、表头，页面上的栏目名、按钮、空状态提示，来自随 skill 发布的英文表 `ui-strings.json`。
  - 英文运行由脚本直接复制。
  - 其他语言由一个子代理只读这张表、写出 `ui.json`。`check-ui` 核对键与英文表完全相同、`{name}` 这类占位符一个不少、值都不为空；不通过就重派一次，再不通过运行失败。
  - 不在代码里内置中文等语言的表：语言种类不设上限，源码保持零中文字符的约定。
- **对用户说的话**：编排过程中对用户说的话同样用该语言，写法同旧 skill 的 Language 段。

备选是一次运行写多种语言。否决：每种语言都要重写条目，花费成倍增加，而且不同语言的版本会各自漂移。下一片改为把一次运行的条目整体翻译：结构与出处不变，脚本核对数字和标签与原文一致。

### D13 HTML 导出

`page` 把 `map.json`、通过检查的条目、`state.json` 与 `ui.json` 组装成页面数据，填进新包 `packages/product-handbook-page` 构建出的单文件模板，写出 `<out>/handbook.html`。

- **页面**：双击即可从磁盘打开；内容安全策略禁止任何网络连接，脚本、样式、字体都内联。
- **结构**：左侧按区域列出功能，带到达方式的标记；功能页按条目字段排版（同 D11）；覆盖页列出守恒结果与各个清单。要适配手机宽度，支持浅色与深色。
- **语言**：页面上所有固定文字都取自 `ui.json`，页面代码里不写死任何一种语言的文字。`<html lang>` 取 `--language` 对应的语言标签。
- **确定性**：同样的输入得到同样的字节，不含时间和本机路径。正文不显示出处，出处在下一片做逐条核对时再以折叠方式展示。
- **构建**：沿用现有报告页的构建方式（单文件内联、许可清单、模板里的两个标记），只是一个独立的包，不与旧页面共享组件，旧页面会随旧 skill 一起删除。

## Risks / Trade-offs

- [R1 引文恰好出现一次过严：短标签，例如 "Submit" 到处都是] → 要求引包含标签的整行或前后文；失败信息会提示加长引文。代价是重试与更长的引文。
- [R2 值核对只看数字与标签：用词写的数量、意思被改写的规则过得了门] → SKILL.md 要求阿拉伯数字；语义核对在下一片做；O6 用分层抽查量出本片的编造。
- [R3 禁词误伤：PayPal 这类产品名] → 已核对标签豁免；没有标签可引时由 lane 改写。误伤率在 O6 计数。
- [R4 守恒成立但归组错：候选进了错的功能] → 守恒只保证不漏；O6 按到达方式分层抽查归组。
- [R5 条目把细节压扁] → 叙述按操作写成段落；O6 拿旧章节当召回尺，比对流程与字段。
- [R6 成本未知] → O6 实测并记录。系统视角是最贵的环节，由 O7 先做一次探针。
- [R7 固定文字译得不对：键与占位符都对，意思却错了] → 脚本只能核对形状；表很短（几十条），O6 由审读者通读一遍中文版的固定文字。
- [R8 页面代码里漏写死英文：某个按钮没走 `ui.json`] → O8 用每个值都加了标记的 `ui.json` 渲染页面，查出所有没带标记的固定文字。

## Acceptance oracles

装置先验（先用已知的坏样本证明检查看得见）：O2、O3 里每一类拒绝都要先有一个应当被拒绝的夹具，看到它变红，再看合法夹具变绿。

- **O1 门**：三件套、`node scripts/check-refs.mjs`、`tests/refs/legacy-literals`、`openspec validate --all --strict` 全过。
- **O2 `check-map`**：以下夹具各自退出 1，并打印对应那一行：
  - 漏掉一个候选；
  - 一个候选归了两次；
  - `menu` 功能的引文里没有它的标签；
  - 引文不在文件里；
  - 引文出现两次；
  - 引文路径在 `.excavator/` 下、在根外（`../`）、在 `node_modules` 下；
  - 种子文件不存在；
  - 读者可见的名字里有禁词。
  
  合法夹具退出 0。身份夹具：两个文件内容相同、路径不同，引其中一个只在那个文件里查；两个功能同名、分属不同区域，各自有独立的 id。
- **O3 `check-entry`**：以下夹具各自被拒：
  - 数字不在引文里；
  - 标签不在引文里；
  - 带千分位的数字与源码不带千分位的写法相互比对（应当通过，作为对照）；
  - 七类禁词各一例；
  - 同一片段落在已核对标签内（应当通过，作为对照）；
  - `who.role` 不在 `map.roles` 里；
  - 多出的键；
  - 某项缺出处。
  
  状态与重试：第二次失败保持 `failed`，已 `checked` 的功能重跑时不再写。
- **O4 迁移无副作用**：迁移前后，旧 skill 在同一夹具上的 `entrypoints.json` 逐字节相同；旧 skill 的测试不改断言即全过。
