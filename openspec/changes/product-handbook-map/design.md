## Context

动机见 proposal.md。与本设计相关的现状：

- 事实层（`.excavator/knowledge-graph.jsonl`）只有文件、函数、类、配置与 imports/calls 等边，没有页面、菜单、字段这类产品层事实。产品层的东西要么由脚本从源码列出，要么由模型读源码写出、再由脚本核对。
- `excavator-prd-report` 的入口列表（`lib/entrypoints.mjs` + `entrypoint-catalog.json`）已经能按框架列出页面、路由、定时任务与 `main`，在 go-multirepo 上列出数百个候选，其中页面约占三成。它是一份确定性的完整候选集，新 skill 需要同一份东西。
- 同一 skill 的 `lib/normalize.mjs` 有「引文在文件里恰好出现一次」的规范化查找。
- 被替代的旧 skill 在 go-multirepo 上的章节：证据块约占三成字数，正文里服务名与角色代码出现上千次，而它的 lane prompt 里早就写着「正文不放代码」。只靠写作规则挡不住技术词进正文。

## Goals / Non-Goals

**Goals**
- 产品地图：每个候选恰好进一个功能或可见的未归入清单；每个功能标明读者怎样到达它。
- 功能条目：结构化，每一项都有原文出处，值与引文由脚本核对，读者可见的文字过禁词门。
- 只读源码，不读任何生成的文档；只写 `--out`。

**Non-Goals**
- 不写问题、不排序。
- 一次运行只出一种语言；把已有结果翻译成别的语言、页面内切换语言是下一片。
- 不按框架写字段或规则的确定性抽取器（见 D5）。

## Decisions

### D1 为什么写代码（AI-first scope gate）

模型做的：把候选归成区域与功能、判断到达方式、读源码写条目。这些是判断与写作，留在 `SKILL.md` 和 lane prompt 里。

脚本做的只有机器校验与确定性产物：候选列表（完整候选集）、守恒、引文与路径、值核对、禁词门、状态记录、拼装。这几样都是「模型写了、但必须能被机器拒绝」的东西；旧 skill 的经验是写作规则单独挡不住技术词进正文，所以禁词必须是门而不是提示。

### D2 目录、命令与产物

`skills/excavator-product-handbook/`：`SKILL.md`、`handbook.mjs`（命令入口）、`lib/`。

| 命令 | 作用 |
|---|---|
| `candidates <project> [--scope <dir>]` | 列入口候选，写到标准输出 |
| `check-map <out> --project <root>` | 地图的格式、守恒、引文、禁词 |
| `check-entry <out> <id> --project <root>` | 一个条目的格式、引文、值、禁词；把结果记进状态 |
| `mark <out> <id> dispatched\|failed …` | 记录派发与无产出的失败 |
| `check-ui <out> [--language <name>]` | 固定文字表的键、占位符（D12） |
| `assemble <out> --project <root>` | 拼出 `handbook.md` |
| `page <out> --project <root>` | 写出 `handbook.html`（D13） |
| `try-entry <out> <id> --project <root>` | 与 `check-entry` 相同的检查，给 lane 交回前自查；不读不写状态（D9） |
| `select <out> --project <root> --features <list>` | 把 `--features` 解析成功能 id（D9） |
| `reply <out> --project <root>` | 重新检查整个运行，按固定格式打印最终回复的几行：两个产物的路径、各状态的功能数、失败的 id、候选守恒。不改任何文件 |

退出码沿用仓库惯例：0 通过，1 检查不过（逐行打印原因，最后一行 `Next:` 说下一步），2 用法或读写错误。

`<out>`（默认 `<project>/.excavator/product-handbook`）：

| 文件 | 写者 |
|---|---|
| `candidates.json` | `candidates` |
| `map.json` | 编排者（模型） |
| `entries/<id>.json` | 该功能的 lane |
| `state.json` | `check-map`、`check-entry`、`mark` |
| `ui.json` | 语言不是英文时由翻译子代理写；英文时由脚本从随 skill 发布的表复制 |
| `handbook.md` | `assemble` |
| `handbook.html` | `page` |

格式串：`excavator-product-handbook-candidates/1`、`excavator-product-handbook-map/1`、`excavator-product-handbook-entry/1`、`excavator-product-handbook-state/1`。

### D3 入口列表迁到新 skill

`entrypoints.mjs`、`entrypoint-catalog.json` 与 `normalize.mjs` 移到 `skills/excavator-product-handbook/lib/`；`excavator-prd-report` 改为从新位置引用。列表函数返回不带 `format` 的对象，由各自的命令盖上自己的格式串，所以旧 skill 的 `entrypoints.json` 一个字节都不变。

备选：新 skill 从旧 skill 目录引用。否决：旧 skill 迟早要删，到时还得再搬一次，而且新代码会留下指向旧名的路径。

### D4 产品地图

`map.json`：

- `areas`：`{id: "A1", name, evidence?}`。区域名是读者可见的文字。如果它就是源码里的菜单分组名，必须带引文；如果是模型起的名字（例如「自动进行的工作」），可以不带引文，但要过禁词门。
- `features`：`{id: "F1", name, area, reach, label?, evidence?, candidates: [...], seedFiles: [...]}`。
  - `reach` 取 `menu`（从菜单进入）、`link`（不在菜单里但能到达：公开链接、邮件里的链接、页面内跳转、菜单被注释掉而路由仍注册的页面）、`automated`（定时或后台）、`interface`（给外部客户端或其他服务的接口）、`operator`（运维命令）之一。
  - `menu` 与 `link` 的功能必须有 `label` 和 `evidence`，并且 `label` 出现在引文里：菜单项就引菜单配置那一行，链接就引路由注册或发出链接的那一处。
- `unassigned`：`{candidate, reason}`，例如测试代码、死注册、出站 HTTP 调用被模式误认成路由。
- `roles`：`{label, evidence}`，项目里的角色，条目只能从这里取。`label` 优先取产品界面上显示的角色名（角色下拉、角色列表里的文字），只有产品没有显示名时才用代码里的键。真实运行里地图取了枚举值（带下划线的键），因为它们是「核对过的标签」而豁免禁词门，读者就看到了代码键，而源码里另有一张角色显示名表。这一条先只写进写作指南，不加脚本检查：没有显示名的项目里，强制检查会让地图无法通过。
- `names`：`{label, evidence}`，源码里出现的外部产品、系统与集成的名字（例如某个即时通讯或代码托管服务）。它们常常是驼峰或多峰形，引文核对过后在整本手册里豁免禁词门（D7）。
- `language`：本次运行的 `--language`。

`check-map` 检查以下各项，不成立的逐行打印：
- 每个候选恰好在一个功能的 `candidates` 里或在 `unassigned` 里，被重复归属或遗漏的候选逐个列出；
- 种子文件都存在；
- 每段引文都通过 D6；
- `label` 出现在它的引文里；
- 所有读者可见的名字都过 D7。

`reach` 不是问题判定：`link` 只是一个可见清单，下一片的问题发现会逐项判断。

### D5 功能条目

`entries/<id>.json` 的顶层键：`id`、`purpose`、`who`、`where`、`screens`、`operations`、`states`、`notifications`、`automatic`、`unknowns`。各项都是 `{…读者可见的字段…, evidence: [{file, passage}]}`：

- `who`：`{role, can}`。`role` 必须是 `map.roles` 里的某个 `label`。
- `where`：读者走到这个功能的路径（菜单 → 子菜单 → 页面标签），每一级都是引文核对过的标签。
- `screens[].fields[]`：`{label, rules: [{side: "frontend"|"backend", text}]}`。两侧分开记，下一片的跨功能对比就靠这个分侧。
- `operations[]`：`{name, sentences: [{text, evidence}]}`。每个操作是一段自由叙述，按句切开，每句自带出处；这是给非技术读者的可读部分。
- `states[]`：`{label, meaning}`；`notifications[]`：`{trigger, recipient, channel, content}`；`automatic[]`：`{when, effect}`。
- `unknowns[]`：`{item, searched}`，写明代码里定不下来的内容和搜索过的范围。没有出处，但要过禁词门。

值不让模型自由转写。备选是按框架写抽取器（gin 的 binding tag、Go 常量、TS enum），被否决，原因有三：
- 违背「框架知识放在能承载它的最低一层」，每个框架一套代码；
- 前端校验写法五花八门，抽取器覆盖不全反而制造静默缺口；
- 现在还没有转写错误率的数据。

改为：值必须连同引文一起写，脚本核对「值 ⊂ 引文 ⊂ 文件」（D6、D8）。本片的真实运行会量出转写错误（O6）；如果错误集中在某类值上，再为那一类做抽取器，进 roadmap。

### D6 引文核对

- 路径以项目根为基准解析，真实路径必须落在根内（经 `..` 或符号链接越界的一律拒绝），且不在 `.git`、`.excavator`、`node_modules`、`vendor`、`dist`、`build` 下。
- 引文按 `normalize.mjs` 的规范化（空白、换行），在该文件里必须恰好出现一次；出现多次时提示加长引文。
- 一项的多段引文各自核对。

### D7 禁词门

对读者可见的字段（地图里的名字，条目里除 `evidence` 以外的所有字符串）逐个 token 检查。拒绝以下几类：

| 类别 | 判据 |
|---|---|
| 下划线标识符 | 两个词字符之间夹 `_` |
| 驼峰标识符 | 小写字母后紧跟大写字母 |
| 多峰帕斯卡词 | 例如由两段「大写+小写」直接相连组成的词 |
| 路径 | 以 `/` 开头、后跟词字符的片段 |
| 源码扩展名 | `.go`、`.ts`、`.tsx`、`.js`、`.jsx`、`.java`、`.py`、`.sql`、`.json`、`.yaml`、`.yml` |
| 调用形 | 词后紧跟 `(` |
| 成员目录名 | 项目根下含 `.git` 的第一级子目录名，即多仓项目的各成员仓库名；普通目录名（如 `src`、`api`）不算，免得误伤日常用词 |

豁免：命中的片段落在某个已经通过引文核对的标签之内，就不算违规。标签的范围包括：地图里的功能标签、角色、`names` 与带引文的区域名（对整本手册有效），以及该条目自己的标签（只对该条目有效）。例如菜单名本身是驼峰形，引文核对过，就允许出现。

拒绝时打印字段路径、命中的片段和类别。备选是由模型自查，被否决，理由见 Context。

### D8 值核对

- 每个 `label` 必须出现在本项的某段引文里。
- 读者可见文字里的每个数字（连续数字，允许千分位逗号与小数点）去掉千分位后，必须作为数字出现在本项的某段引文里，引文里的数字同样去掉千分位与下划线分隔后再比较。
- `unknowns` 没有出处，不做值核对，只过禁词门；它说的是「定不下来」，不是事实陈述。
- 序号、日期等合法但不来自源码的数字，只能出现在拼装时生成的部分（编号、计数），不能写进模型写的文字。SKILL.md 要求数字一律写成阿拉伯数字，用词写数量（例如「两级审批」）的情况脚本挡不住，记为残余风险（R2）。

### D9 lane、状态与续跑

- 编排者为每个要写条目的功能派一个前台子代理，最多 `--concurrency`（默认 3）个同时运行。子代理只读该功能的种子文件，以及否定类陈述所需的全项目搜索，只写 `entries/<id>.json`。
- `check-entry` 通过记为 `checked`，不通过记为 `failed` 并保存原因。第一次失败后，带着原因重派一次；第二次仍失败就保持 `failed`，文件保留供查看。
- lane 交回前先自己跑 `try-entry`：检查与 `check-entry` 相同，但不读不写 `state.json`，不算一次尝试。真实运行里两次尝试都栽在同一种机械错误上：引的是真实存在的源码行，文件却写成了同目录的另一个文件（共 7 处）。这种错 lane 自己搜一下就能改，不该每次都花掉整条 lane 的一次尝试。两次尝试的上限不变，`check-entry` 仍是唯一记结果的检查。
- 状态只经过脚本改变，编排者不手改 `state.json`。
- 重跑时，已 `checked` 的功能不再写；`--fresh` 清空 `<out>`，规则同旧 skill：只清空不存在、为空或含本 skill 写出的 `state.json` 或 `candidates.json`（按 format 字段认）的目录。认 `candidates.json` 是因为 `check-map` 通过前还没有 `state.json`，在那之前中断的运行否则无法 `--fresh`。
- 最终回复由 `reply` 打印，模型只照抄（非英文时只翻译词句，路径、数字与 id 不动）：回复的计数来自脚本，不由模型加总。
- `--features <list>`：只为这些功能派 lane。地图仍覆盖全部候选；没写条目的功能在手册里列为「未写」。
  - 功能 id 由模型写地图时才定，运行前不知道，所以列表里每一项可以是 id，也可以是功能名（不分大小写、整名相等）。
  - 由脚本 `handbook.mjs select` 在 `check-map` 通过后把列表解析成 id：每项恰好匹配一个功能才算数；有项不匹配或匹配多个时退出 1，打印该项与地图里全部的 id 和名称，运行停在这里，不派任何 lane。不做模糊匹配：猜错功能比停下更糟。

### D10 不读生成的文档

- SKILL.md 与 lane prompt 明令：只读项目源码，不读 `.excavator/` 下的任何东西，也不读项目里由本工具生成的文档。本切片连事实层（`knowledge-graph.jsonl`、MCP）也不用：条目靠读种子文件与全项目搜索，用不上图；规则收成「`.excavator/` 一概不读」后，O6 检查运行记录时任何一次读取都算违规，不必区分哪些文件可读。以后某一片确实需要事实层时，再放开并写明可读的文件。
- 列入口候选的脚本与别的 skill 共用；它在知识图存在时读图头里的框架列表。本 skill 调用它时关掉这一步，一律从构建文件检测框架（在 go-multirepo 上两种方式列出的 878 个候选逐项相同）。
- 机器层面，D6 拒绝 `.excavator/` 下的引文路径，生成文档的内容进不了条目的出处。读了但没引用这种情况，由 O6 检查运行记录。

**domain graph 也不作输入。** 我在 go-multirepo 上看过 `excavator-domain` 的产物：6 个域、29 个流程、157 个步骤，流程名已经是业务说法。它看起来能直接当区域和功能的草稿，但不用，理由有四：
- 它也是模型写的产物。拿它分区，地图就继承了另一个模型的归组，验收时也分不清地图是从源码推出来的还是照抄的。
- 它不守恒：没有定时任务、对外接口和多个菜单区域，29 个流程和入口候选对不上。
- 它的业务规则（共 27 条）没有出处，不能当事实。
- 它有自己的修订和新鲜度，依赖它就多了一个「先跑 domain」的前提。

它的用处放在两处：
- O6 里由审读者拿地图的区域和 domain 的域对照，作为分区合理性的旁证。
- 做跨功能问题的那一片里，它的跨域交互可以当搜索起点，但每条都要从源码重新证明。

### D11 拼装

`handbook.md` 由 `assemble` 确定性生成，同样的输入得到同样的字节，不含时间和本机路径：

- 文档开头：按区域列出功能，并按到达方式计数。
- 每个功能一节，按条目字段排版：
  - 用途、谁能用、在哪里；
  - 字段表，三列：字段、前端规则、后端规则；
  - 各操作的叙述，句子原样拼接；
  - 状态表、通知表、自动行为；
  - 「代码里无法确定的内容」。
- 覆盖一节：候选总数与守恒结果、`unassigned` 清单、`link` 功能清单、没有条目或条目失败的功能。

正文不放出处，出处留在 JSON 里。小节名与表头取自 `ui.json`（D12）。

### D12 语言

`--language` 决定所有读者可见文字的语言，可以是中文、英文或其他语言，默认英文。

- **叙述**：地图里的区域名、条目里的叙述，由模型直接用该语言写。源码里的标签保持原文，不翻译，这样读者能对上自己在产品里看到的字。
- **固定文字**：`handbook.md` 的小节名、表头，页面上的栏目名、按钮、空状态提示，来自随 skill 发布的英文表 `ui-strings.json`。
  - 英文运行由脚本直接复制。
  - 其他语言由一个子代理只读这张表、写出 `ui.json`。`check-ui` 核对键与英文表完全相同、`{name}` 这类占位符一个不少、值都不为空；不通过就重派一次，再不通过运行失败。
  - 不在代码里内置中文等语言的表：语言种类不设上限，源码保持零中文字符的约定。
- **对用户说的话**：编排过程中对用户说的话同样用该语言，写法同旧 skill 的 Language 段。
- **叙述的语言要检查，而不只是写进提示词。** 真实运行里 lane prompt 明写了「用中文写」，条目叙述仍然全是英文；地图里模型写的未归入原因也是英文。做法：
  - 固定文字的翻译挪到地图之前（候选之后），这样后面的检查都知道这种语言用什么文字。这时还没有 `map.json`，所以 `check-ui` 收 `--language`，不给时才读 `map.json` 的语言。`ui.json` 可能先于地图存在，恢复运行时它的语言与本次 `--language` 不同就停下并提示 `--fresh`，不沿用旧语言的表。
  - 运行语言不是英文、`ui.json` 已通过 `check-ui`，并且其中至少一半的值含非 ASCII 字母时，这种语言按「非拉丁文字」处理：模型写的每段叙述必须至少含一个非 ASCII 字母。去掉其中已核对的标签与名字后只剩数字和标点的，豁免。
  - 检查范围：条目里的用途、各角色能做什么、操作名与叙述句、字段规则、状态含义、通知的四项、自动行为、无法确定的内容及其搜索范围；地图里不带引文的区域名、不带标签的功能名、未归入原因。`check-map`、`check-entry`、`try-entry`、`assemble`、`page` 都执行它。非英文运行没有通过检查的 `ui.json` 时，这些命令（连同 `select`、`reply`）都拒绝，并提示先做固定文字。
  - 拉丁字母的语言（法语、西班牙语等）没法用文字种类区分，不检查，列为已知限制：这类语言的叙述语言只靠提示词。

备选是一次运行写多种语言。否决：每种语言都要重写条目，花费成倍增加，而且不同语言的版本会各自漂移。下一片改为把一次运行的条目整体翻译：结构与出处不变，脚本核对数字和标签与原文一致。

### D13 HTML 导出

`page` 把 `map.json`、通过检查的条目、`state.json` 与 `ui.json` 组装成页面数据，填进新包 `packages/product-handbook-page` 构建出的单文件模板，写出 `<out>/handbook.html`。

- **页面**：双击即可从磁盘打开；内容安全策略禁止任何网络连接，脚本、样式、字体都内联。
- **结构**：左侧按区域列出功能，带到达方式的标记；功能页按条目字段排版（同 D11）；覆盖页列出守恒结果与各个清单。要适配手机宽度，支持浅色与深色。
- **语言**：页面上所有固定文字都取自 `ui.json`，页面代码里不写死任何一种语言的文字。`<html lang>` 取 `--language` 对应的语言标签。
- **确定性**：同样的输入得到同样的字节，不含时间和本机路径。正文不显示出处，出处在下一片做逐条核对时再以折叠方式展示。
- **构建**：沿用现有报告页的构建方式（单文件内联、许可清单、模板里的两个标记），只是一个独立的包，不与旧页面共享组件，旧页面会随旧 skill 一起删除。

### D14 逐项核对（从第三片提前到本片）

原计划本片只保证「引文真实存在、值出现在引文里、读者文字里没有代码」，逐项的语义核对放到第三片。O6 的抽查推翻了这个安排：30 项里 6 项与代码矛盾。没有凭空编造，引文全都真实存在，错在对引文的解读：
- 把函数名里的 `Admin` 读成管理员角色，写出了管理员没有的取消权限与编辑权限（4 项）；
- 把只拦两种状态的条件写成全称（「不能已被另一份使用」「发给每一位」）（2 项）。
这类错误脚本看不出来。零编造是硬指标，带着两成矛盾率的手册不能合进可安装的插件，所以把干净上下文的核对提前到本片。做法沿用学习路线 skill 已经验证过的那一套：

- **切片**：`check-entry` 通过后，`handbook.mjs slices <out> <id> [--round 2]` 把条目里每个有出处的项写成一个核对文件 `<out>/verify/round-<r>/<id>.json`：每项的 id 是它的 JSON 路径，主张是该项全部读者可见文字（例如字段规则带上字段标签与前端或后端；通知带上触发、收件人、渠道、内容四项；谁能用带上角色），出处是每段引文在文件里的位置加前后各 20 行的源码（带行号，同一文件的相邻片段合并）。「无法确定的内容」没有出处，不核对。一个功能的项多时核对文件会超过子代理一次能读的量（真实运行里 97 项、289 KB，超出单次读取上限），所以按字节把项分成若干份，每份一个文件 `<out>/verify/round-<r>/<id>/part-<n>.json`、一个核对者，每份的判词写到对应的 `part-<n>.json`；判词守恒按全部份合起来算。
- **核对者**：新的 agent 定义 `excavator-handbook-verifier`，只读那一个核对文件，不读别的文件、不搜索，给每一项一个判词：`verified`（给出的源码支持整条主张）、`unverified`（给出的源码既不支持也不否定）、`contradicted`（给出的源码与主张不符），附一行理由，写到 `<out>/verdicts/round-<r>/<id>.json`。核对者看不到条目作者的理由、地图或别的功能。不是 `verified` 的理由会出现在覆盖一节里给读者看，所以 `verdicts` 对它们执行与条目文字相同的禁词门与叙述语言检查，不通过就和缺判词一样拒绝、重派。
- **记录与守恒**：`handbook.mjs verdicts <out> <id> --round <r>` 检查每一项恰好一个判词、没有多出的项、判词只有三种；不成立退出 1，什么都不记。
- **改写一次，再定案**：第一轮里不是 `verified` 的项（矛盾与无法证实一样处理）写进 `<out>/rewrite/<id>.json`，连同理由交给一个改写子代理：只改列出的项，可以换引文或收窄说法；救不回的项原样保留，由第二轮核对后的脚本删去。改写者不增删项，这样每项的路径在两轮之间不变，删去的记录能逐项对上，而不是按条数估计。`slices --round 2` 拒绝项的路径集合与第一轮不同、或未列出的项有改动的条目。第二轮仍不是 `verified` 的项从条目里删去，删去的项、判词与理由记进 `state.json`，手册的覆盖一节按功能列出删去的条数与各项。核对文件缺失（子代理没写）时重派一次，仍缺就整条记为未核对、功能不算完成。
- **状态**：`planned → dispatched → checked → verified`，或 `failed`。`checked` 只表示形状与引文过了脚本，只有 `verified` 的功能进入手册正文；`checked` 而未核完的功能在覆盖一节列为「核对未完成」。
- **未证实也删**，而不是像学习路线那样保留：手册写给不读代码的人，读者没法自己去看源码判断一句话的真假，留下无法证实的句子等于让读者替我们担风险。代价是召回再降一些；lane prompt 要求每项引到能单独证明它的源码（权限判断要引到判断本身，不能只引函数名），减少「其实对、但给出的源码证明不了」被删掉的情况。
- **每份两名核对者，都判 `verified` 才算。** 第一次真实运行里核对者放过了 3 项与代码矛盾的说法（独立抽查 30 项里查出），而矛盾的那几行就在核对文件里：它们都是一句里装了好几件事的长说法，核对者核了其中几件、漏了错的那件。把同两份核对文件再交给核对者跑一遍，3 项全被拒；要求逐条拆分断言的写法没有更好，换 Opus 也都拒了但把被抽查确认为真的 8 项也拒了，花费约 5 倍。所以错放是单次判断的随机漏看，不是提示词看不见：每份由两名互不相见的 Sonnet 核对者各判一次，判词分别写到 `part-<n>.a.json` 与 `part-<n>.b.json`；两者都是 `verified` 才算 `verified`，任一是 `contradicted` 就是 `contradicted`，否则 `unverified`，理由取不是 `verified` 的那一份（两份都不是时取 `contradicted` 的，再不然取 `a`）。拿这次的数据回放：首轮与重跑合起来，3 项都不会过；代价是这两份里多出 3 项要改写。
- **两名核对者一起漏的，靠规则补。** 换上两名核对者后的真实运行里，仍有一项两人都放过：把类型名里的 `Leader` 写成「直属上级」，并说三个环节「总是」都在，而跳过环节的逻辑在没有给出的保存函数里。两人漏的是同一处，再加人也没用，所以核对者定义里加两条：名字不说明是哪个人、哪个角色或哪个部门（审批人、收件人同样要有给出的条件或查询）；交给一个函数体没给出的调用之后，「总是在」「一定发生」都无法证实。同一份核对文件上两名核对者都拒了这一项；代价是同一份 20 项里多拒 1 到 2 项（例如「提交后发送邮件」，发送函数体不在给出的代码里），它们先进改写，改写可以把说法收窄到给出的代码。
- 这一步不能代替 O6 的抽查：核对者与条目作者用的是同一个模型，可能犯同样的错。O6 的独立抽查照旧，矛盾数仍须为 0。

## Risks / Trade-offs

- [R1 引文恰好出现一次过严：短标签，例如 "Submit" 到处都是] → 要求引包含标签的整行或前后文；失败信息会提示加长引文。代价是重试与更长的引文。
- [R2 值核对只看数字与标签：用词写的数量、意思被改写的规则过得了门] → SKILL.md 要求阿拉伯数字；逐项核对（D14）判每一项的意思；O6 用独立的分层抽查量出剩下的编造。
- [R3 禁词误伤：PayPal 这类产品名] → 已核对标签豁免；没有标签可引时由 lane 改写。误伤率在 O6 计数。
- [R4 守恒成立但归组错：候选进了错的功能] → 守恒只保证不漏；O6 按到达方式分层抽查归组。
- [R5 条目把细节压扁] → 叙述按操作写成段落；O6 拿旧章节当召回尺，比对流程与字段。
- [R6 成本未知] → O6 实测并记录。系统视角是最贵的环节，由 O7 先做一次探针。
- [R7 固定文字译得不对：键与占位符都对，意思却错了] → 脚本只能核对形状；表很短（几十条），O6 由审读者通读一遍中文版的固定文字。
- [R8 页面代码里漏写死英文：某个按钮没走 `ui.json`] → O8 用每个值都加了标记的 `ui.json` 渲染页面，查出所有没带标记的固定文字。

## Acceptance oracles

装置先验（先用已知的坏样本证明检查看得见）：O2、O3 里每一类拒绝都要先有一个应当被拒绝的夹具，看到它变红，再看合法夹具变绿。

- **O1 门**：三件套、`node scripts/check-refs.mjs`、`tests/refs/legacy-literals`、`openspec validate --all --strict` 全过。
- **O2 `check-map`**：以下夹具各自退出 1，并打印对应那一行：
  - 漏掉一个候选；
  - 一个候选归了两次；
  - `menu` 功能的引文里没有它的标签；
  - 引文不在文件里；
  - 引文出现两次；
  - 引文路径在 `.excavator/` 下、在根外（`../`）、在 `node_modules` 下；
  - 种子文件不存在；
  - 读者可见的名字里有禁词。
  
  合法夹具退出 0。身份夹具：两个文件内容相同、路径不同，引其中一个只在那个文件里查；两个功能同名、分属不同区域，各自有独立的 id。
- **O3 `check-entry`**：以下夹具各自被拒：
  - 数字不在引文里；
  - 标签不在引文里；
  - 带千分位的数字与源码不带千分位的写法相互比对（应当通过，作为对照）；
  - 七类禁词各一例；
  - 同一片段落在已核对标签内（应当通过，作为对照）；
  - `who.role` 不在 `map.roles` 里；
  - 多出的键；
  - 某项缺出处。
  
  状态与重试：第二次失败保持 `failed`，已 `checked` 的功能重跑时不再写。
- **O4 迁移无副作用**：迁移前后，旧 skill 在同一夹具上的 `entrypoints.json` 逐字节相同；旧 skill 的测试不改断言即全过。
- **O5 拼装**：`assemble` 与 `page` 各自对同样的输入运行两次，产物逐字节相同；两种产物里都不出现任何引文路径；覆盖一节的计数等于 `candidates.json` 与 `map.json` 中的计数。`check-ui`：少一个键、多一个键、丢一个占位符、值为空，各自被拒。
- **O8 页面**：在无头 Chrome 里以 `file://` 打开 `handbook.html`：
  - 没有任何网络请求，控制台没有错误；
  - 区域导航、功能页、覆盖页都能打开；
  - 375 像素宽时没有横向滚动；
  - 用每个值都加了标记的 `ui.json` 渲染，页面上没有不带标记的固定文字（装置先验：先故意写死一个英文按钮，看它被查出来）。
- **O6 真实运行（go-multirepo）**：
  - 运行条件：Sonnet 钉死模型，`--out` 放在语料外，`--language Chinese`，`--features` 选一个同时带表单、审批链与通知的功能。
  - 语言：叙述与固定文字是中文，`check-ui` 通过；条目里的界面标签与源码原文一致，没有被翻译；审读者通读中文固定文字。
  - 页面：O8 的检查在这次运行的 `handbook.html` 上再做一遍。
  - 分区旁证：审读者拿地图的区域与 domain graph 的域对照，列出差异（只记录，不作为通过条件，见 D10）。
  - 地图守恒成立；各到达方式的计数与 `unassigned` 可见；该条目在两次尝试内通过 `check-entry`。
  - 召回：由独立的 Sonnet 审读者读旧 skill 对同一功能写的章节（运行本身不读），列出旧章节里的每个流程与表单字段，在新条目里找到或记为漏掉，漏掉的附原因。
  - 编造：独立的 Sonnet 审读者按条目项类型分层抽 30 项，对照源码判定，矛盾数必须为 0。
  - 运行记录里没有读取 `.excavator/` 下除知识图谱以外文件的调用。
  - 记录花费、时长、禁词与值核对的重试次数。
- **O7 系统视角探针**：不是产品代码。用一个视角（权限）的 prompt 在 go-multirepo 上跑一次：先写可重放的搜索，再对搜索得到的每一行给判断。记录行数、花费与时长，供系统层问题那一片定方案。
