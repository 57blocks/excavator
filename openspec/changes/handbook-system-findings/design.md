## Context

第 4a 片：每个功能一个发现单元 `<功能 id>.findings`，经过条目的全部脚本检查和建议词检查，两名核对者、一次只换引文的改写、两名追查者；范围词由追查者逐个造反例（D9）。手册的「发现」一章按类别分组。

应用根由脚本确定（`handbook.mjs applications`，一个目录一行），概览的应用表也受它约束。入口候选（`candidates.json`）有四类：`page`、`route`、`job`、`main`。go-multirepo 有 5 个应用根；`main` 候选 3 个，`job` 候选 16 个，候选最多的文件登记了 378 个后端路由。

## Goals / Non-Goals

**Goals：**
- 不属于任何单个功能的代码也有人读、写出缺陷；
- 同一处缺陷只算一次，别的陈述不丢；
- 与功能的发现同一套检查、核对与追查。

**Non-Goals：**
- 跨功能的比较（同一规则在两个功能里不同、两个渠道用不同日历），放第 5 片；
- 排级与对策。

## Decisions

### D1 部分与阶段

- `lib/sections.mjs` 的表加 `system-findings`：文件 `sections/system-findings.md`，第 4d 阶段，依赖地图。默认运行包括它，排在 `findings` 之后。
- `--features` 不影响它。新选项 `--applications <list>`：逗号分隔的应用根目录，只为这些根写系统发现；不给时为全部。不认识的目录让 `handbook.mjs` 退出 1，并列出全部应用根。
- 「部分」规则第 4 条加上：系统发现单元（`app<n>.system`）只在选了 `system-findings` 时核对与追查。

### D2 单元

- id 是 `app<n>.system`，`n` 从 1 起，按 `applications` 打印的顺序。后缀 `.system` 与功能的发现（`.findings`）分开；`.` 不在功能 id 的字符集里，所以不会和功能 id 撞上。
- 状态在 `state.json` 的可选键 `systemFindings`，键是 `app<n>`，值与其它单元相同，另记 `root`（目录）。没有这个键时，每个单元都是 `planned`、没有尝试，不需要迁移。
- 记下的 `root` 与这次的应用根不同（源码变了）时，`handbook.mjs` 退出 1，提示用 `--fresh`。
- 文件是 `entries/app<n>.system.json`，形状与功能的发现相同（`excavator-product-handbook-findings/1`、`id`、`findings`、`unknowns`）。没有发现时直接 `verified`。

### D3 种子

`handbook.mjs system-seeds <out> app<n> --project <root>` 打印这个单元的种子文件，一行一个，按路径排序。规则：在这个应用根之下，
- 有 `main` 或 `job` 候选的文件；
- 登记了至少 5 个候选的文件。

种子为空时（比如一个只有库代码的根），单元直接 `verified`，没有发现，与空发现一样。

### D4 检查

与功能的发现相同，另加两道：
- **在应用里**：每条发现至少有一段引文在这个应用根之下。
- **归属**：一条发现引用的每个文件都是同一个功能的种子文件，而且没有一个是这个单元的种子时，拒绝，并写出那个功能的 id。

### D5 子代理的提示

`sections/system-findings.md` 的提示从发现子代理的提示改写，区别是：
- 范围是这个应用里各功能共用的部分：启动与关闭、配置的读取、路由与中间件的注册（哪一组路由带哪些中间件）、定时任务的注册，以及种子文件交给出去的共用代码（鉴权、错误处理、发信、日历与时区）；
- 列出每个功能的名字与种子文件，并说明只在一个功能自己代码里的缺陷由那个功能写；
- 跟出去最多 20 个文件，与发现子代理相同；
- 写作规则（陈述、引文、数字、无代码、范围词、证据）逐字沿用。

### D6 核对与追查

- 第 5、6 阶段把系统发现单元与其它单元同列：第 5 阶段第 1 步多一条 jq 列出 `checked` 的，第 6 阶段第 1 步多一条列出 `confirmed` 的。
- 主张：`System finding > <类别的显示名> > <陈述>`。追查文件的 `scopeWords` 与功能的发现相同。
- 核对者、改写者、追查者的 agent 不变。改写者用 `try-system-findings`。

### D7 同一处缺陷

拼装与页面都从已核实的发现单元（功能的与系统的）读出全部发现，按下面的规则分组：
- 两条发现**类别相同**，并且各有一段引文**在同一个文件里、行号范围重叠**，就在同一组；分组可以传递。行号范围是引文在文件里定位到的行。
- 组内顺序：功能按地图的顺序在前，系统单元按 `n` 在后；同一单元内按发现的顺序。组的第一条是代表。

规则只看类别与位置，可能把同一行上两处不同的缺陷并在一起。所以组里的每条陈述都照写，只是计数按组算，不丢内容。

### D8 呈现

**手册**，两个视图：
- 「发现」一章：
  - 计数行写出组数、陈述数，以及合并了几组；
  - 每组一条：代表的陈述，后面写所有归属。归属是功能名，或者应用名（概览已核实时用概览给它起的名字，否则用目录名）；
  - 组里其它陈述写在下面，前面写它的归属；
  - 技术视图另写每条的文件与行号。
- 应用一节（如果有）不另列；系统发现只在「发现」一章。
- 覆盖一节列出没核实完的系统发现单元，以及核对与追查删掉的系统发现。
- `assemble` 与 `page` 写之前重新检查已核实的系统发现单元，与功能的发现一样。

**页面**：
- 格式升到 `/10`；
- `findings` 的每组带 `owners`（`{ kind: "feature" | "application", id, name }`）与组内各条；
- 发现页按类别筛选不变，加上「系统」作为一个归属筛选；
- 功能页仍列出自己的发现（含与别的功能合并的组）。

## Risks / Trade-offs

- **种子规则是粗的。** 「至少 5 个候选」会把页面出口这类文件也算进来；一个只靠中间件文件的问题要靠子代理跟出去才能读到。阈值不调：漏读就照实记在验收里。
- **大文件。** 一个登记了几百个路由的文件，子代理读不完；它会读与自己判断相关的部分。
- **合并规则可能误并。** 同一行上两处不同的缺陷会并成一组；内容不丢，只是计数少算一条。验收逐组看。
- **花费**：每个应用根一个子代理、两名核对者、两名追查者。

## Oracles

- **O1 脚本**：新夹具，测试先红：
  - 种子的选取：`main` 与 `job` 的文件、至少 5 个候选的文件、阈值以下的不算、根之外的不算；
  - 单元 id 与状态键，没有键时为 `planned`，`root` 变了就退出 1；
  - 「在应用里」与「归属」两道检查的反例与对照；
  - 分组：同类别同文件重叠成组、类别不同不成组、不重叠不成组、三条传递成一组；
  - `--applications` 不认识的目录。

  变异，各至少一条测试变红：
  - 去掉归属检查；
  - 分组不看类别；
  - 分组不传递；
  - 阈值改成 1。
- **O2 呈现**：
  - 一组只算一条，其它陈述照写；
  - 系统发现的归属是应用名；
  - 产品视图没有路径；
  - 页面 `/10`、归属筛选。

  变异：合并后丢掉组里的其它陈述，至少一条变红。
- **O3 真实运行**（go-multirepo，Sonnet 是测量条件）：
  - 在第 4a 片第二轮输出的副本上，以 `--sections system-findings --views technical` 续跑。先用 `--applications` 跑主服务一个根标定花费，再跑其余四个。
  - 记录：花费、每个单元写了几条、核对删了几条、追查删了几条、留下几条。
  - 地图、条目与功能的发现逐字节不变。
  - 合并：第 4a 片那两条同一处的发现成一组；逐组看有没有误并。
  - **验收者独立抽查每一条留下的系统发现**，不看实现，判断：缺陷是否真实（含范围）；类别是否对；有没有建议；是不是其实只属于某一个功能。删掉的全部看是否误删。线是零编造：一条不实就先修机制。
- **O4**：受影响测试、`check-refs`、`openspec validate --all --strict` 本地过；全量门在分离检出里跑；源码零非 ASCII 字符；名字扫描无命中。
