## Context

#159 之后：抽取 → 分区 → 规划（一个代理，模块 → 域，按模块集合复用）与区分析（每区一个代理，只写流程与步骤）并行 → 合并按「起始模块的域」挂流程。模块是目录，所以一个装着多个领域业务逻辑的目录只能整体归一个域；规划在这种目录上要么选一个业务域（其余领域的流程挂错），要么选支撑域（所有业务流程挂进支撑域）。真实项目上它选了后者。

## Goals / Non-Goals

**Goals**
- 行为属于某个业务域的流程挂在那个业务域，即使它起始的目录是混合目录或支撑目录。
- 选择针对规划的固定域清单做出，由脚本校验；域清单与模块归属保持稳定，复用规则不变。
- 支撑域里的每条流程要么被明确判定为非业务（带理由），要么被脚本计数并逐条打印。
- 守恒、0 静默为零不变。

**Non-Goals**
- 不让流程级内容跨运行一致（#159 的非目标，不变）。
- 不改分区（模块仍是目录）、抽取、锚定。
- 不让脚本判断哪条流程属于哪个领域。

## Decisions

### D1 机制：分析器从固定清单里为「需选域」模块的流程选域，而不是规划按文件拆混合目录

两个候选：

- **规划按文件拆混合模块**（规划给混合目录里的每个文件一个域）。否决：
  - 文件也会混合：遗留项目里一个几千行的 `routes.js` 或 `services/index.js` 照样横跨多个领域，按文件拆只把问题下移一层；
  - 规划输入随文件数增长（遗留目录常有上百个文件，现在每模块只给 20 个文件名样本），规划代理只看到名字而看不到流程；
  - 规划的键从目录变成文件，混合目录里每加一个文件都会改模块集合摘要、触发扩展规划，「文件改动不改变划分」这条结构保证就没了。
- **分析器为流程选域**。采用：流程才是「行为属于某个领域」的单位；分析器是唯一读了这条流程代码的角色；选择被限制在规划的固定清单里，合并逐条校验 id，非法与缺失都落进可见计数。规划的键、摘要与复用不变。

选择只在「需选域」模块上生效：被规划标为 `mixed` 的模块，和归在支撑域的模块。单一业务域模块的流程仍按模块定域——那里模块归属已经是正确且稳定的判断，再让每次运行的分析器重判只会引入漂移。把支撑域模块也列为需选域，是因为规划仍可能把装业务逻辑的目录放进支撑域（实测正是如此）；这条兜底让「支撑域里出现业务流程」只能经由分析器明确选择或可见回落两条路发生。

一致性：域清单与模块归属仍由一次规划决定并复用；每条流程的选择是每次运行的判断，但流程本身每次都由区分析重新写出（#159 的非目标），所以选择的漂移不超过流程本身的漂移，而且只在需选域模块上发生。

### D2 规划：`mixed` 标记

规划输出新增 `mixed: [模块路径]`（可省略，等于空）。`accept` 校验：每项是本次要规划的模块（扩展模式下已有模块的标记不能增删，原因写明）、不重复；任一不过整份拒收。混合模块仍要在 `assignments` 里归一个域（规划说明：归它多数文件服务的领域；它只决定没有选择时流程回落到哪里）。存储：`domain-plan.json` 加 `mixed`（排序），格式升为 `excavator-domain-plan/2`；规划输入格式升为 `excavator-domain-plan-input/2`，扩展模式下已有模块行带 `mixed: true|false`。剪枝时去掉已不存在的模块的标记。旧的 /1 规划按「格式不对」走 `new`（零兼容，不读旧形状）。

规划代理说明的改动：支撑域只放没有业务行为的模块（数据模型、共享库、基础设施）；装业务路由、业务服务或业务定时任务的目录，服务一个领域就归那个业务域，服务多个领域就列进 `mixed`、归它多数文件服务的业务域。

### D3 规划先于区分析，规划写进区上下文

分析器要从清单里选，清单必须在派区分析器之前确定。`plan-domains.mjs` 在规划确定时（`prepare` 判为 `reused`，或 `accept` 接受）把 `domainPlan` 写进每个区上下文文件：

```json
"domainPlan": {
  "domains": [ { "id": "domain:billing", "kind": "business", "name": "Billing", "summary": "..." } ],
  "modules": { "services/legacy/routes": { "domain": "domain:orders", "choose": true } }
}
```

`modules` 只含本区的模块；`choose` 为真当且仅当该模块在 `mixed` 里或归在支撑域。只改上下文里的这一个字段，`areaRun` 与其他内容不变。合并不读它（合并按存储的规划重新算），所以即使分析器在规划确定前就被派出，后果只是没有选择、全部回落并被计数。

代价：冷启动与扩展运行里，区分析要等规划接受后才开始，墙钟多一次规划调用的时长；调用次数不变。复用规划的运行没有这段等待。另一个候选是合并后再派一个「挂接」代理为需选域流程选域——多一次调用，而且那个代理没读过流程的代码，否决。

### D4 合并：两档挂接与记录

起始模块 `m` 的求法不变（首个可定位步骤所在模块，否则本区持有的声明模块，否则 `unplaced`）。然后：

- `m` 不需选域 → 挂 `plan.modules[m]`，`domainBy: module`；流程若写了 `domainMeta.domain` 则计入 `choicesIgnored`（不改变挂接）。
- `m` 需选域，`domainMeta.domain` 是规划里的域 id → 挂该域，`domainBy: choice`；
- `m` 需选域，没写 → 挂 `plan.modules[m]`，`domainBy: fallback`，原因 `missing`；
- `m` 需选域，写了清单外的值 → 同上回落，原因 `invalid`，记下所写的值。

覆盖报告 `flows` 增加：`byModule`、`byChoice`、`fallback: {missing, invalid}`、`choicesIgnored`、`choices`（每条需选域流程一行：`{flow, module, moduleDomain, domain, by, reason?, chosen?}`，`reason` 取分析器的 `domainMeta.domainReason`）、`support: {total, chosen, unchosen, unchosenFlows}`。`support.total` 是挂在支撑域的流程数；`chosen` 是分析器明确选了支撑域的；`unchosen` 是回落进支撑域的。打印 `flows domain module=… choice=… fallback=… support=… support-chosen=… support-unchosen=…`，并为每条回落流程打印一行：回落进支撑域的写 `support-unchosen <flow> module=<m> reason=<missing|invalid>`，其余写 `fallback <flow> module=<m> reason=…`。`flows.choices` 的一行为 `{flow, module, moduleDomain, domain, by, reason?, fallback?, chosen?}`：`fallback` 是 `missing`/`invalid`，`chosen` 是非法时所写的值。

`homedByStep`/`homedByDeclared`/`unplaced` 保持原义（起始模块怎么求出来的），新计数描述的是域怎么定的，两组正交。守恒与四个桶不受挂接影响。

### D5 skill 编排

Phase 3.5 `prepare` 之后：若不是 `reused`，先派规划代理、`accept`（拒收重派一次，再拒收 STOP，不变），接受后才派区分析器；`reused` 时直接派区分析器。报告里加 `byChoice`、回落数与 `support-unchosen` 数，`support-unchosen` 大于 0 时列出这些流程。

## Risks / Trade-offs

- **选择是每次运行的判断**：同一条遗留流程在两次运行里可能被选到不同的域（边界领域）。测量里报告混合文件流程挂到「它所属领域的干净模块所在域」的比例，作为准确度的下限证据。
- **规划仍可能把混合目录归到某个业务域而不标 `mixed`**：那样它的其他领域流程仍挂到那个业务域。不进支撑域，但挂错；这一类脚本看不见，记为局限。规划说明专门点名这种目录。
- **分析器可能漏写选择**：回落逐条打印、计数可见；回落进支撑域的单独计数。
- **墙钟变长**：见 D3。

## Oracles（动手前写死）

- O1 规划 `mixed`：合格的 `mixed` 被接受并按序存储；含未知模块、重复、扩展模式改已有模块的标记——各自被拒且原因可读；/1 格式的已存规划判为 `new`；剪枝去掉已删模块的标记；扩展模式输入的已有模块行带 `mixed`。
- O2 区上下文：规划确定后（`reused` 与 `accept` 两条路）每个区上下文都有 `domainPlan`，`modules` 恰好是本区模块，`choose` 恰好对 `mixed` 与支撑域模块为真；`areaRun` 不变；被拒的规划不写。
- O3 挂接：单一业务模块的流程按模块定域，写了选择也不变（`choicesIgnored` +1）；混合模块与支撑模块的流程按合法选择定域；缺失与非法回落并计数、打印；回落进支撑域计入 `support.unchosen`；选了支撑域计入 `support.chosen`。装置先验：同一份输入在旧规则下（不读选择）把这些流程挂进支撑域，新规则把它们挂进选的业务域——测试先在旧代码上红。
- O4 守恒与桶：带选择的输入守恒 `ok`，四桶不变。
- O5 实测（夹具 `mixed-legacy.mjs`，32 个模块、6 个业务领域、3 个混合目录，无知识图，`claude -p --model sonnet`；前 = main 65bff693，后 = 本分支）：
  - 每边至少两次独立冷启动（全新副本），后一边在第一份副本上补一次热运行。
  - 记录：支撑域流程占比（挂在支撑域的流程 / 已挂接流程）；混合目录里业务文件起始的流程挂到「该领域干净模块在本次规划里的域」的比例；非业务文件起始的流程是否在支撑域；`support-unchosen`、回落数；域数（业务/支撑）、规划 ARI、业务域数差；四桶、静默为零、守恒、花费。
  - **阈值（运行前写死，只约束后一边）**：每次运行 `support-unchosen` 等于测量脚本数出的「支撑域里没有选择的流程数」（结构，必须相等）；支撑域流程占比 ≤ 15%（夹具里非业务入口是 3 个文件的 4 个入口，占全部 55 个入口约 7%；留出余量给分析器把一个入口拆成几条流程）；混合目录业务流程挂对比例 ≥ 80%；静默为零 0、守恒 `ok`。两次冷运行间规划划分 ARI ≥ 0.8、业务域数差 ≤ 2；热运行规划划分、域 id 与名字与冷运行完全相同、规划调用 0 次。前一边只记录。未达阈值如实记为未达，不事后挪阈值。
