## 背景

- `handbook-free-chapter` 把功能改成「自由正文 + 小事实表」，正文用 `check-chapter` 检查，内容问题只记数，整章标「未核对」。
- 技术视图的「技术架构」一块（大纲里的块 `architecture`）现在只画概览里「应用 → 外部系统」的连线。
- 数据一块已有确定性的 `data` 步骤，这一片不改。

## 决定

### D1 新的一节，一个子代理

- 新加一节 `architecture`，阶段文件 `sections/architecture.md`，阶段号 4f。
- 它不需要地图：应用根目录用 `handbook.mjs applications` 列出，外部系统的名字用 `handbook.mjs names` 列出，与概览阶段相同。
- 派一个写作子代理，类型与功能写作者相同（`excavator-handbook-writer`）。子代理写两份文件，自己运行 `try-architecture` 检查，再交回；编排者运行 `check-architecture` 记录结果。
- 状态记在 `state.architecture = {status, attempts, notes}`，最多 3 次。
- 这一节没有第 5、6 阶段的单元：不核对、不追查，和 `/3` 功能章一样。
- 代价：多一个子代理，预计 $3–8。

### D2 正文沿用 `check-chapter`

- 规则与功能正文完全相同（出处、80 行、时序图子集或 `no-diagram`、内容问题只记数）。
- 推荐的时序图：一次请求从浏览器经前端到后端、认证与数据库的路线。
- 不另造检查，是为了两种正文在页面上的写法、未核对标记与内容问题计数完全一致。

### D3 事实表 `architecture.json`

```json
{
  "format": "excavator-product-handbook-architecture/1",
  "components": [
    {"id": "c1", "label": "...", "kind": "frontend", "application": "<应用根目录>", "stack": "...", "evidence": [{"file": "...", "passage": "..."}]}
  ],
  "links": [
    {"from": "c1", "to": "c2", "text": "...", "evidence": [{"file": "...", "passage": "..."}]}
  ]
}
```

- `kind` 取 `users`、`frontend`、`backend`、`database`、`external`、`cloud`。
- `application` 只在前端与后端组件上出现，取 `applications` 列出的根目录。守恒：每个根目录恰好是一个前端或后端组件。这是结构性的检查，能拦住「漏掉一个应用」。
- 引文的核对用功能事实表已有的同一套（照字出现、文件在项目内、空白规整后比较）。
- 连接说明不长于 16 个字符，是为了图上放得下；超出的意思写进正文。
- 组件名称、技术栈与连接说明里的代码样字词和语言问题只记数，与功能正文一致。
- 不检查连接说明是否出自引文：说明是写作者的话，正文才是详细的地方。

### D4 分层结构图

- 层由种类决定：`users` 第 0 层，`frontend` 第 1 层，`backend` 第 2 层，`database`、`external`、`cloud` 第 3 层。同层内按事实表里的顺序排。
- 后端之间的连线画在同一层内；页面图用现有的分层流程图组件，按层放节点，连线说明沿用领域流程图的留白与描边。
- `handbook-technical.md` 用 mermaid `flowchart LR`，每层一个 `subgraph`，标题用固定文字。
- 画法是确定性的：同一份事实表，图一字不差。

### D5 没写成时

- 状态不是 `checked`、或文件缺失时，「技术架构」一块照旧画「应用 → 外部系统」图，加一句固定文字：没有选中、写作失败或文件缺失，三选一。
- 这保证这一片对已有的运行是只增不减的。

### D6 写作提示词

- 内容清单见 spec。还要求：
  - 先从各应用的清单文件（依赖声明、构建与容器文件、部署与流水线文件、环境配置）读起，再去读启动代码、路由注册、数据访问与外部客户端；
  - 写出每个版本号与端口时引它所在的那一行；
  - 前端到后端：找到请求地址的来源（环境配置、代理、请求封装），按后端分开写；
  - 数据库：每个后端的连接配置与数据访问方式各写一句，表结构变更的位置写一句；
  - 不写评价与建议，「已停止维护」这类判断不写；
  - 不读 Markdown 文档与 `.excavator/`，与功能写作者相同；
  - 不设文件上限。
- 正文的写法沿用功能写作者的版式规则：按内容的形状选列表、表格、编号步骤，段落不超过 3 句。

## Oracle

- **O1 脚本测试**：
  - `check-architecture` 的接受与每一种拒绝（D3 的每一条）、内容问题只记数；
  - 拼装：写成时技术视图有正文、未核对标记、mermaid 分层图，产品视图没有这一块；没写成时三种固定文字之一加原图；
  - 页面：技术架构页画出分层图，层的顺序与 D4 相同；
  - 各节列表：`sections` 打印 `READ=sections/architecture.md`，`--sections architecture` 单独可用。
- **O2 变异**（在固定 commit 的分离检出里做）：
  - 去掉应用根目录守恒；
  - 接受指向未声明组件的连接；
  - 不核对引文；
  - 拼装漏掉「未核对」；
  - 层的顺序错位。
  每个都要有测试变红。
- **O3 提示词合约**：钉住内容清单、清单文件先读、版本与端口引所在行、前端到后端按后端分开、不写评价、不读文档、版式规则；换回没有这一节的 `SKILL.md`，合约测试要变红。
- **O4 真实运行**（审阅副本语料，Sonnet，上限 $8）：
  - 一次写成或 3 次内写成，记花费与轮数；
  - 覆盖：从人工参考手册的技术架构一章整理一份清单（应用的技术栈、职责与端口；结构图的连线；部署、登录与权限的事实）。由不知道哪份是哪份的审读者对照，参考结构图连线覆盖不少于 80%，清单整体覆盖不少于 70%。门槛在运行前定，没达到照记；
  - 只增不减：原图的每条「应用 → 外部系统」连线都在新图里（同一个外部系统允许换名字，审读者判）；
  - 精度：按小节分层抽 30 句，记成立、部分、错误，不设门槛；
  - 语料在运行前后不变。
- **O5**：`openspec validate --all --strict`、`check-refs`、`typecheck`、源码零非 ASCII 字符、名字扫描无命中；全量门交给 CI。

## 风险

- **编造**：正文与事实表都不核对。按用户 2026-11-11 的决定接受，由「未核对」标记让读者看见，最后一片统一处理。
- **大型多仓库项目**：一个子代理要读全部应用的配置，花费可能随应用数上升。O4 只量了一个 5 个应用的项目；应用很多时是否要按应用拆子代理，留到真实用到时再定。
- **只有配置能说明的连线**（例如经由网关或 CDN）：如果部署文件不在项目里，图上就没有这条线。这是代码与配置能证明的上限，在固定文字里不另作说明。
