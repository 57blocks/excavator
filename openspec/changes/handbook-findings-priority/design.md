## Context

第 4a、4b 片之后，已核实的发现来自两类单元（`<功能 id>.findings` 与 `app<n>.system`），拼装与页面用 `lib/findings-groups.mjs` 把同一处的发现并成组（D7）。每组有代表的陈述、类别与全部归属。核对与追查只判断陈述是否属实，不判断严重程度。

参考手册的「问题」页每条带 P0/P1/P2 和一句定级理由，根因类别旁写出「N 条 · P0 M 条」。

## Goals / Non-Goals

**Goals：**
- 每组已核实的发现有一个级别和一句理由；
- 理由不引入陈述之外的事实；
- 级别的规则固定在脚本里，模型只选后果。

**Non-Goals：**
- 对策与建议（第 4d 片）；
- 让评判者读代码：陈述已经过核对与追查。

## Decisions

### D1 部分与阶段

- `lib/sections.mjs` 的表加 `priority`：文件 `sections/priority.md`，没有共享阶段文件。默认运行包括它，排在 `system-findings` 之后。
- 它在第 6 阶段（追查）之后、拼装之前运行，是第 6b 阶段；读的是此刻已核实的发现单元。部分文件在「Sections」一步被读、它们的阶段当场就跑，而定级要在追查之后，所以 `handbook.mjs sections` 不把它写成 `READ=` 行，而是另打印一行 `AFTER_TRACE=sections/priority.md`；SKILL.md 第 6 阶段的最后一步说：有这一行时，读这个文件并做它的第 6b 阶段，再进第 7 阶段。
- 没有已核实的发现时，什么也不派发，打印一行说明。

### D2 后果枚举与级别表

脚本里的固定表，`md.priority.consequence.<键>` 是显示名：

| 键 | 含义 | 级别 |
|---|---|---|
| `othersRecords` | 一个人能看到或改动不属于自己、或无权处理的记录与操作；或不登录就能做到 | P0 |
| `money` | 计费、付款、报销或报表里的金额会算错 | P0 |
| `dataLoss` | 记录会丢失、重复或被写错，并且留在系统里 | P0 |
| `secret` | 密钥或密码会泄露，或输入能改变执行的查询与命令 | P0 |
| `wrongResult` | 正常使用中一项操作给出错误的结果，或失败而不告诉人 | P1 |
| `notification` | 该收到通知的人收不到、收错，或内容错 | P1 |
| `blocked` | 产品提供的一项操作完成不了 | P1 |
| `display` | 显示错误或令人困惑，数据本身没错 | P2 |
| `inert` | 不会运行的代码、占位功能，或现在不影响任何人的写死值 | P2 |

级别只由键决定，模型不写级别。

### D3 定级单元

- 单元 id `priority`，状态在 `state.json` 的可选键 `priority`（与其它单元同形）。文件 `entries/priority.json`：
  ```json
  { "schema": "excavator-product-handbook-priority/1",
    "items": [ { "key": "<组键>", "consequence": "<枚举键>", "reason": "<一句>" } ] }
  ```
- **组键**：组的代表发现所在单元 id、它在该单元文件里的序号，以及组内全部陈述的摘要（sha256 前 16 位），写作 `<单元 id>#<序号>@<摘要>`。陈述或组的成员变了，键就变，旧的定级不再对应任何一组。
- `handbook.mjs priority-items <out>` 打印要定级的组，一行一组：组键、类别显示名、代表陈述，以及组里其它陈述（同一行内用 ` | ` 隔开）。每次运行都从此刻已核实的发现重新算。
- `check-priority <out>`：每个组键恰好一项、键是 `priority-items` 当前打印的、后果在枚举里、理由一行且通过读者文字的检查（无代码词、无文件名、语言与运行语言一致、无建议词）。通过后记为 `checked`。

### D4 子代理

`sections/priority.md` 的提示：
- 输入是 `priority-items` 的输出，不读代码；
- 每组选一个后果。拿不准在两个后果之间时，选级别低的那个；
- 理由写一句：谁能触发、触发后发生什么。只用陈述里的事实，不加推测（「可能导致」「攻击者可以进一步」之类），不写怎么改；
- 一个子代理处理全部组；组超过 40 个时分批，每批一个子代理，各写自己的部分文件，由脚本合并。

### D5 评判

- 新 agent `excavator-handbook-priority-judge`：只看判定文件（每组的陈述、后果的含义、理由），对每组给 `follows` 或 `doesNotFollow` 与一行原因：
  - 后果的含义是否由陈述撑得住（例如陈述只说「页面显示错误」，后果却是 `money`，就不成立）；
  - 理由里的每个事实是否都在陈述里。
- `priority-judge <out>` 写两份判定文件的路径；两名评判者各写一份。`priority-verdicts <out>` 记录：两名都 `follows` 的组记为已定级；其余记为未定级，原因照录。单元记为 `verified`。
- 没有改写、没有重试。未定级是可见的缺口。

### D6 呈现

- 「发现」一章：
  - 每组一行，开头是级别（`P0`/`P1`/`P2`，未定级写「未定级」），陈述之后写理由；
  - 同一类别内按 P0、P1、P2、未定级排序，同级保持原来的顺序；
  - 计数行加上各级与未定级的条数；每个类别的标题后写「N 条 · P0 M 条」。
- 覆盖一节写出未定级的组数，以及每组评判者的原因。
- 定级单元不是 `verified` 时，发现照常写，全部算未定级，覆盖一节说明定级没有完成。
- 页面：格式 `/11`；每组带 `priority`（`{ level, consequence, reason }` 或 `null`）；发现页加级别筛选；功能页的发现也带级别。
- `assemble` 与 `page` 写之前重新算组键；与 `entries/priority.json` 对不上的项不写，那一组算未定级。

## Risks / Trade-offs

- **后果比真实严重度粗。** 同为 `othersRecords`，读别人一条日期与改别人的工资都是 P0。级别表不细分，读者看理由。
- **评判者不读代码。** 理由与陈述一致，不保证陈述没有说过头；那是核对与追查的事。
- **「选低的那个」会系统性压低级别。** 宁可低估也不编造严重性。

## Oracles

- **O1 脚本**，测试先红：
  - 组键：陈述改一个字、组多一个成员，键都变；
  - `check-priority`：缺一组、多一组、后果不在枚举里、理由两行、理由有代码词或建议词，各退出 1；
  - 级别表：每个键的级别；
  - `priority-verdicts`：两名都 `follows` 才定级；一名 `doesNotFollow` 即未定级并记原因；判定文件缺项或多项退出 1。
  
  变异，各至少一条测试变红：一名评判者同意就定级；组键不含摘要；级别表把 `display` 改成 P0。
- **O2 呈现**：级别与理由出现在组的那一行；类别内排序；计数；未定级与定级未完成的覆盖说明；产品视图同样有级别；页面 `/11` 与筛选。变异：不排序，至少一条变红。
- **O3 真实运行**（go-multirepo，Sonnet 是测量条件）：在第 4b 片的输出副本上以 `--sections priority` 续跑。
  - 记录花费、组数、各级条数、未定级条数；
  - 地图、条目、发现单元逐字节不变；
  - **验收者独立抽查**全部定级（不看实现）：后果与理由是否由陈述撑得住；理由有没有陈述之外的事实；级别是否明显偏高或偏低。线：理由零编造；级别偏差照实记录。
- **O4**：受影响测试、`check-refs`、`openspec validate --all --strict` 本地过；全量门在分离检出里跑；源码零非 ASCII 字符；名字扫描无命中。
