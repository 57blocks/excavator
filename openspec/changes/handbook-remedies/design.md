## Context

第 4c 片之后，已核实的发现按同一处并成组，每组有级别（或未定级）与理由，定级单元 `priority` 在第 6b 阶段运行，`AFTER_TRACE=sections/priority.md` 让它在追查之后读。脚本已经算出系统事实（`lib/system-facts.mjs`：每个应用的语言、文件、行数与版本历史）和数据部分（`data.json`：每张表在各应用里被提到的位置）。

手册其它部分只陈述现状、不给建议。这一部分是唯一的例外。

## Goals / Non-Goals

**Goals：**
- 每类已核实的发现有一段共同原因与对策；
- 一份按先后排列的建议；
- 其中每句事实都能在引用的发现或脚本事实里找到。

**Non-Goals：**
- 读代码找新的问题；
- 评判建议本身好不好：评判者只看事实是否有出处。

## Decisions

### D1 部分与阶段

- `lib/sections.mjs` 加 `remedies`：文件 `sections/remedies.md`，没有共享阶段文件，默认运行包括它，排在 `priority` 之后。
- 与 `priority` 一样在追查之后运行：`handbook.mjs sections` 为它打印 `AFTER_TRACE=sections/remedies.md`，在 `priority` 那一行之后。第 6c 阶段在第 6b 之后、第 7 阶段之前。
- 没有已核实的发现时，什么也不派发，打印一行说明。

### D2 可引用的事实

`handbook.mjs remedy-facts <out> --project <root>` 打印，一行一项，制表符分隔：
- `group`：`<组键>`、级别（`P0`/`P1`/`P2`/`unranked`）、类别键、代表陈述；
- `app:<目录>`：应用名（概览已核实时用它的名字，否则用目录名）、主要语言、源文件数、行数、提交数、作者数（没有版本历史时写 `-`）；
- `tables-shared`：被两个以上应用提到的表的个数，以及每张表和提到它的应用；
- `counts`：已核实的组数、各级组数、各类别组数。

id 是每行第一个字段（组键、`app:<目录>`、`tables-shared`、`counts`）。

### D3 对策单元

- 单元 id `remedies`，状态在 `state.json` 的可选键 `remedies`。文件 `entries/remedies.json`：
  ```json
  { "schema": "excavator-product-handbook-remedies/1",
    "categories": [ { "category": "<类别键>", "cause": "<一句>", "measure": "<一到三句>", "cites": ["<id>"] } ],
    "recommendations": [ { "title": "<短标题>", "text": "<一到三句>", "cites": ["<id>"] } ] }
  ```
- 键：整组事实（`remedy-facts` 的输出）的摘要记在状态里；事实变了，旧的对策不再用，下次重写。
- `check-remedies`：
  - 类别都在枚举里、每个类别至多一段、只写有已核实组的类别；
  - 每段的 `cites` 只引用这一类的组，至少一个；
  - 建议 1 到 10 条，每条至少引用一项；
  - 所有 id 都在 `remedy-facts` 当前的输出里；
  - `cause`、`measure`、`title`、`text` 通过读者文字的检查（无代码词、无文件名、语言一致），不查建议词；
  - 文字里的每个数字都出现在它引用的事实或陈述里。
- 失败时与其它单元一样重派一次（第 2 次尝试），再失败就记为失败，手册写明对策没有完成。

### D4 子代理

`sections/remedies.md` 的提示：
- 输入只是 `remedy-facts` 的输出，不读代码；
- 共同原因只写引用的每组陈述都说到的事；说不出共同点时写最窄的一句，不推测；
- 对策与建议可以给出做法，但其中提到的现状（「有 N 张表被三个服务共用」「越权的问题有 M 条 P0」）必须来自引用；
- 建议的顺序：先是不必等重构就能处理的 P0，再是引用最多组的机制，最后是清理与测试。顺序由子代理定，评判者不判断顺序。

### D5 评判

- 新 agent `excavator-handbook-remedy-judge`：判定文件列出每段与每条建议的文字和它引用的全部内容（组的陈述与级别、事实行）。对每段、每条给 `follows` 或 `doesNotFollow` 与一行原因：
  - 文字里陈述现状的每句话，是否都在引用里；
  - 共同原因是否对每个引用的组都成立。
  - 做法本身（「建立统一的授权层」）不判断。
- `remedy-judge` 写判定文件；`remedy-verdicts` 记录：两名都 `follows` 的才保留，其余删除并记录原因。单元记为 `verified`。

### D6 呈现

- 「发现」一章每个类别标题下，先写「共同原因」与「对策」，再写这一类的组。
- 新的一章「建议」，放在「发现」之后：按顺序编号，每条写标题、文字，再列出它依据的组（级别与代表陈述）与事实（按行写出事实的内容）。
- 覆盖一节写出删掉的段落与建议及原因；单元不是 `verified` 时写明对策没有完成。
- 产品视图与技术视图都写；技术视图在依据的组后面写文件与行号，与「发现」一章相同。
- 页面：格式 `/12`；`remedies: { categories: [...], recommendations: [...] }`；发现页每个类别显示原因与对策；新的建议页。

## Risks / Trade-offs

- **共同原因可能太泛**（「缺少检查」）。泛不算错，评判者只管有没有出处。
- **建议只建在已写出的发现上。** 发现召回低，建议也就覆盖不全；手册写明建议依据的组数。
- **不读代码的建议看不到架构全貌。** 架构事实在第 5、6 片补上后，可以成为新的可引用事实。

## Oracles

- **O1 脚本**，测试先红：
  - `remedy-facts`：组行、应用行（有无版本历史）、共用表（只被一个应用提到的不算）、计数；
  - `check-remedies`：不认识的 id、跨类别引用、没有已核实组的类别、11 条建议、数字不在引用里、文字有代码词，各退出 1；建议词不拒绝；
  - `remedy-verdicts`：两名都 `follows` 才保留。

  变异，各至少一条测试变红：一名 `follows` 就保留；数字检查关掉；跨类别引用放行。
- **O2 呈现**：类别下的原因与对策、建议一章的顺序与依据、删掉的列在覆盖、页面 `/12` 与建议页。变异：建议不写依据，至少一条变红。
- **O3 真实运行**（go-multirepo，Sonnet 是测量条件）：在第 4c 片真实运行的输出副本上以 `--sections remedies` 续跑。
  - 记录花费、段落与建议数、评判删掉的数目；
  - 条目、发现与定级逐字节不变；
  - **验收者独立抽查**每段与每条建议（不看实现）：陈述现状的每句话是否都在引用里；共同原因是否对每个引用的组成立。线：零编造。
- **O4**：受影响测试、`check-refs`、`openspec validate --all --strict` 本地过；全量门在分离检出里跑；源码零非 ASCII 字符；名字扫描无命中。
