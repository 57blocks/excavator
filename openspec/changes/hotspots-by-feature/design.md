## Context

扫描历史时，每个文件都有自己的提交号集合与作者编号集合；目录行就是把它下面各文件的集合取并集，再算按年的提交与作者份额（`aggregate.mjs` 的 `foldIntoDir` 与 `dirRow`）。一个组和一个目录唯一的区别是：目录的文件由路径前缀决定，组的文件由分组文件列出。

`/excavator-domain` 产出 `.excavator/domain-graph.json`：领域通过 `contains_flow` 连到流程，流程通过 `flow_step` 连到步骤，步骤带 `filePath`。这份图要通过 `domain-freshness.mjs` 的检查才能用，而检查要比对知识图的 `factDigest`，所以前面要先跑过 `/excavator`。

## Goals / Non-Goals

**Goals:**
- 能按功能回答「哪个功能改得多」，数字按提交去重。
- 分组从哪里来、哪些路径没对上，汇报里都看得见。

**Non-Goals:**
- skill 自己判断哪些文件属于一个功能。
- 按领域汇总、路径通配符、按 JSF 页面导航分组。
- 检查一个组的文件是不是真的构成一个功能。

## Decisions

**1. 组行复用目录行的计数。**
- 把组当成一个文件由列表给出的目录：每个文件折进组，用同一个 `dirRow` 出行。
- 按年的提交、作者份额、bot 的排除都跟着有，不另写一套。
- 头部只多四个数：组数、属于至少一个组的文件数、属于多个组的文件数、没对上的路径数，字段名是 `groupsListed`、`filesInAGroup`、`filesInSeveralGroups`、`pathsUnmatched`。
  - 命名跟 `coChange.pairsListed` 一样是「名词 + 动词」的计数；
  - 不用 `groups`、`unmatchedPaths`：它们已经是组行数组和每组的路径数组，同名不同类型，jq 查询容易写错。

**2. 分组文件只有组名和路径；目录用末尾的 `/`；不支持通配符。**
- 领域图给的是文件，人手写时常写目录，这两种够用。
- 不带 `/` 的路径只匹配同名文件，不会退化成前缀匹配。没对上时宁可显示出来，也不放宽匹配去找一个「差不多」的文件，否则会把「找不到」变成「找到了别的」。
- 代价：想按命名规律分组时，要把目录或文件逐个列出来。

**3. 没对上的路径放进可见的桶，格式错误才报错。**
- 领域图里的 `filePath` 是模型写的，可能指向已删除或写错的文件。一条错路径不应该让整个产物写不出来，但必须看得见：每组列出 `unmatchedPaths`，头部给出总数。
- 不是 JSON、缺 `groups`、组名为空或重复、`paths` 不是字符串数组，属于文件本身坏了，报错，不写产物。
- 一个组一个文件都没对上时，`files` 为 0，历史字段为 `null`。按「没有可数的东西就不报 0」的规则，不写成 0 次提交。
- 人写的分组文件格式不对时，skill 不带分组重跑，其余各节照常，按功能一节给出脚本的报错；不替人改文件。
  - 代价：这次运行没有按功能的数字，要人改好文件再跑。

**4. 行按分组文件的顺序，不排序。**
- 按提交数、分数还是作者数排，没有唯一的答案；汇报和 chat 的查询自己排序。
- 保持原顺序，读者也容易和分组文件对照。

**5. 分组的来源：人写的优先，其次是领域图的流程；导出用 jq 写在 skill 里，不进脚本。**
- 哪些文件属于一个功能是判断题，`/excavator-domain` 已经由模型做了，而且有步骤锚定和校验。脚本只做必须由脚本做的事：要完整提交记录的去重计数。
- 导出结果写到 `.excavator/feature-groups-from-domain.json`，每次运行都重新导出。这样：
  - 过期的导出文件不会被拿来用；
  - 人写的 `.excavator/feature-groups.json` 永远不会被覆盖；
  - 用户想调整时，可以把导出文件复制成 `feature-groups.json` 再改。
- 读领域图之前先跑 `domain-freshness.mjs`，这是领域图对所有使用者的约定。不能用时不导出，汇报说明原因。
- 代价：要先跑 `/excavator` 和 `/excavator-domain`，按功能的数字才出得来；功能边界的质量取决于业务流程分析的质量。

**6. 每个流程一组，不按领域。**
- 流程就是一个功能（「发表文章」「下单」）；领域是一组功能。
- 导出的细节：
  - 一个流程属于多个领域时仍是一组，组名里列出各领域；不属于任何领域的流程只用流程名；流程没有名字时用它的 id；
  - 两个组名相同时，各自在名字后加流程 id，保证组名不重复，否则脚本会拒绝整个文件；
  - 没有 `filePath` 的步骤不贡献路径；一个流程没有带文件的步骤时，`paths` 为空，这一组 `files` 为 0；
  - 路径去重排序；组按组名排序。
- 代价：没有领域级的行。要的话可以手写分组，把一个领域的文件列在一起，去重由脚本完成。

**7. skill 不自己提出分组。**
- 没有领域图时再让 skill 读目录和代码来分组，就多了一条没经过锚定和校验的判断路径。
- 汇报的自检词表加上 whole feature、entire feature、整个功能，拦住把组的数字说成整个功能的改动。
- 代价：没有领域图也没有手写分组的项目，汇报里只有一句怎样得到分组。

**8. 产物不记分组文件的位置。**
- 每行原样带 `paths`，读者能直接看到算了哪些路径；记文件位置会把本机路径写进产物。

## Oracle

- **单测**：覆盖规格里的每个场景，包括组内去重、目录路径、重复列出、跨组、没对上、格式错误（不写产物）、没有历史、跨仓、没传分组文件。
- **独立 oracle**：
  - 另写一段 Python，只按规格从 `oracle.py --commits-out` 的每文件提交 sha、各仓 `git log` 的作者邮箱与提交年份，算出每组的全部字段与头部四个数；
  - 分组文件由一个带固定种子的脚本生成，每份 30 组左右，故意包含：目录路径、同一文件重复列出、跨组的文件、已删除和写错的路径、空的 `paths`；多仓时让组跨成员仓；
  - 语料：dataverse、sakai、openmrs-workspace；
  - 先手动改产物里的几个数，确认比对能报出差异；
  - 同时核对带分组与不带分组的产物，除 `featureGroups`、`groups` 与新的残余假设外完全相同。
- **耗时**：sakai 全历史，传 100 组与不传各跑两轮，增加不超过 5 秒。
- **真实模型**：Sonnet，headless，在一个公开的 RealWorld 示例应用上（前后端都是 JS，154 个文件，140 次提交）：
  - 依次跑 `/excavator`、`/excavator-domain`、`/excavator-hotspots`；
  - 导出的分组与按 jq 规则从领域图手算的一致，汇报的各组数字与产物逐行一致，自检 0 行；
  - chat 问「哪些功能改得最多」和某个功能改了多少；
  - dataverse 上（没有领域图）chat 问哪个功能改得最多：说明没有按功能计数和得到的办法，不拿目录代替。
