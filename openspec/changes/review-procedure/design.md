## Context

上一步之后，进 `main` 的改动都要通过 `CI gate` 与 `Privacy scan`，但没有任何一方读过改动本身。参考的做法（一篇关于 Anthropic 内部代码审查的文章）有几层：
- 审查者给出带档位的发现，作者对每条要么修掉、要么写明理由后解决；
- 风险档由改动本身决定，不由作者决定，CI 工作流这类路径总要有人看；
- 审查循环要收敛：轮数上限、后续轮只审差异、不重复、按类报告；
- `REVIEW.md` 写这个仓库里什么算失败、Nit 上限、不审的路径、要求 file:line 证据、总结以计数开头；
- PR 模板要求 Testing、Risk、How to revert；
- 审查者的质量用过去的缺陷做评测（下一步）。

本仓库的约束：
- agent 用用户的 GitHub 账号开 PR，同一账号不能批准自己的 PR，所以「批准数」在这里强制不了任何事；
- 托管的 Code Review 服务要 Team 或 Enterprise 方案并由 Owner 开启，属于用户的动作；
- 能由模型按提示词做的，不写成代码。

## Goals / Non-Goals

**Goals：**
- 写明这个仓库的审查看什么，审查者与托管服务共用一份；
- 一个干净上下文的审查代理，能审 PR（发评论）也能审 git 范围（只打印），后者供下一步评测；
- 按路径定风险档，写明各档合并前要做什么，改检查与审查本身的 PR 由用户合并；
- 每条发现都有回应，GitHub 强制讨论都已解决；
- 审查会收敛。

**Non-Goals：**
- 不接入托管服务，也不在 CI 里调用模型：都需要用户提供方案或 API key；
- 不写判定风险档或检查 PR 正文的脚本；
- 不评测审查者的召回与误报：那是下一步。

## Decisions

### D1 审查者是本仓库自带的审查代理

可选的审查者：
- **托管的 Code Review 服务**：要用户开通，暂不可用。它读 `main` 上的根目录 `REVIEW.md`；本仓库是经典分支保护，它承认这种保护。所以把规则写进 `REVIEW.md`，日后开通时直接适用。
- **本地 `/code-review`**：任何方案都能用，但不读 `REVIEW.md`，只读 `CLAUDE.md`；行内评论的格式与档位也不由我们定。
- **CI 里调用模型**：要把 API key 放进 secret，是用户的动作；而且每次推送都花钱。
- **自带的子代理**：`.claude/agents/reviewer.md`，与已有的 `coder` 代理并列。选它，因为它能读 `REVIEW.md`、能按我们定的格式发评论，也能审 git 范围供评测用。

审查代理用 opus。审查是判断题，按「贵模型只给判断与审计」的原则。

### D2 `REVIEW.md` 的内容

英文，放在根目录。内容按文章与托管服务文档建议的几项写，换成本仓库的失败形态：
- **Important 的定义**：只给以下几类：
  - 报告编造或静默丢失；
  - 检查本该红却绿；
  - 名单、凭据或真实项目产物进仓库；
  - 违反 `AGENTS.md`，或削弱合并与审查流程；
  - 一般的行为错误。
  其余最多是 Nit。
- **Pre-existing**：不是本 PR 引入、也不是本 PR 才让它能触发的，不挡合并。
- **证据**：file:line 加失败的输入与结果；从名字或注释推断不算证据；构造不出失败的情形就不报 Important。
- **按类报告**：一条发现是某个模式的一例时，列出本改动里的所有实例。
- **Nit 上限**：五条。
- **不报**：
  - CI 已经强制的检查；
  - lockfile、`dist/`、已归档的 OpenSpec 变更；
  - 中文 OpenSpec 文档的措辞，除非它与代码或别的文档矛盾；
  - 已经提出过的发现。
- **每次都查**：
  - 新行为有没有它不在就会失败的测试；
  - 改过的检查有没有证明它能失败的用例；
  - 从产物读来的路径收敛在根目录内；
  - 代码、注释、测试与 skill 散文没有中文字符，代码、注释与测试里没有语料名；
  - build-free；
  - PR 正文声明的风险档与路径给出的一致：声明得比路径低是 Important，因为低报的高档 PR 会被 agent 自行合并。
- **总结**：第一句是各档计数；没有要修的就直说。

### D3 审查代理怎样工作

- **输入**：调用方给 `pr <编号>` 或 `range <base>..<head>`，以及轮次；第二轮起再给上一轮审到的提交。
- **规则来源**：`REVIEW.md` 与 `AGENTS.md` 从 `origin/main` 读（`git show origin/main:REVIEW.md`），不从 PR 的分支读。PR 对它们的改动是被审的内容。这与托管服务的做法一致：一个 PR 不能放宽审它自己的规则。
- **读的内容**：
  - 改动，以及改动行周围的代码；
  - 第二轮起只读新提交的差异，再读 PR 上已有的审查讨论，避免重复。
- **只读**：不改文件、不建分支、不提交、不推送、不批准、不请求修改、不解决讨论、不合并。临时内容走管道，不落文件。
- **发布**：对 PR 只发一次审查，事件是 `COMMENT`：
  - 能定位到改动行的发现作为行内评论，开头写档位；
  - 定位不到的放进总结；
  - GitHub 拒收某一行时，把那条移进总结。

  对范围只打印，格式与发到 PR 上的相同：一行总结，再加一个 JSON 数组，每项有档位、路径、行、标题与正文。
- **账号**：评论与 PR 来自同一个账号，所以审查永远不是批准，合并与否由流程决定。

### D4 风险档按路径

| 档 | 路径 | 合并前 |
|---|---|---|
| 高 | `.github/`、`scripts/ci/`、`REVIEW.md`、`.claude/agents/reviewer.md` | 审查；讨论都已解决；由用户合并 |
| 中 | 其余 | 审查；讨论都已解决；agent 可以合并 |
| 低 | 只有 `openspec/`、`docs/`、根目录除 `AGENTS.md`、`CLAUDE.md`、`REVIEW.md` 外的 Markdown | 两个必过检查通过 |

- **取最高档**，由路径决定，作者不能自选。
- **高档只放定义检查与审查的路径**：改了它们，后面的检查与审查都可能失效。文章里「总要有人看」的也正是 CI 工作流与敏感路径。
  - `AGENTS.md` 放在中档。它改得较勤（自 9 月 10 日起约 10 次，`.github/` 与 `scripts/ci/` 合计约 12 次），整份定为高档会让大部分流程改动都停下等用户。
  - 削弱合并与审查流程的改动由审查代理按 `REVIEW.md` 报为 Important。
- **低档只放不改变行为的文档**：`AGENTS.md`、`CLAUDE.md` 是给 agent 的规则；`skills/` 下的 Markdown 是提示词，都会改变行为，归中档。
- **不写判定脚本**：路径到档位是一张三行的表，由 agent 对照 `git diff --name-only` 判定，审查代理再核对一次（D2 最后一项）。脚本也挡不住会自行合并的 agent：它用的就是用户的账号。

### D5 回应与解决

- **回应**：
  - 修掉的，回复修复的提交；
  - 不修的，回复理由，即错的、有意的或无关紧要，再写一句为什么；
  - 回复之后解决讨论。
- **总结里的发现**：放在总结里、无法开讨论的发现，用一条 PR 评论逐条回应。
- **分支保护**：开 `required_conversation_resolution`。它强制的是「没有被遗忘的讨论」，不是「有另一个人同意」：解决讨论的也是同一个账号。

### D6 收敛

按文章的四条做，数字取文章的：
- **第一轮审整个改动**；之后只审上一轮审到的提交之后的新提交。
- **不重复**：审查代理先读已有的讨论。
- **按类报告**（D2）。
- **何时再审**：上一轮有 Important 并因此改了代码，或新提交触及中高档路径，才再审一轮。新提交只触及低档路径（例如验收记录）时不再审。
- **轮数上限**：最多三轮。第三轮仍有 Important 时停下，不合并，向用户说明并重新考虑做法。文章里一个 PR 一夜跑了五十多轮，三轮上限也是文章的数字。

### D7 PR 模板

`.github/pull_request_template.md` 有四节：Summary、Testing、Risk tier、How to revert。
- **Testing** 写跑了哪些命令、结果的计数，以及检查会漏掉什么。这句取自文章：说不出检查漏什么，就该要一次真正的审查。
- **How to revert** 写明回滚撤不掉的东西，例如分支保护与 secret。
- `gh pr create --body-file` 不会套用模板，`AGENTS.md` 写明按模板的四节写。

### D8 本变更自身的档位

本 PR 改了 `.github/`、`REVIEW.md` 与审查代理，按自己的表是高档。规则在它合入之后才生效。
- **合并**：用户在开始这一系列时明确要求无人值守地完成所有步骤，所以本 PR 仍由 agent 合并，并在汇报里写明。
- **生效**：从下一个 PR 起，高档 PR 停下等用户。
- **其余照做**：本 PR 用本变更定的流程走一遍，包括审查、回应与收敛。
- **规则来源**：本 PR 合入前 `main` 上还没有 `REVIEW.md`。审查代理在 `main` 上找不到它时，改用 PR 里的版本，并在总结里写明。

## Oracles（动手前写死）

- **O1 装置看得见缺陷**：
  - 在 scratchpad 的分离检出上提交一个植入的缺陷，提交信息不提示缺陷：把隐私扫描器语料范围里的 `':(exclude,glob)*.md'` 改成 `':(exclude)*.md'`。非 glob 的路径规格在任意深度都匹配，于是 `skills/` 下 Markdown 里的语料名不再被扫。
  - 用范围模式交给审查代理。它 SHALL 报一条 Important，指向这一行，并说出哪类文件会被漏扫。
  - 没报出，审查代理就不能当门用：先改提示词再继续，改过之后在同一个缺陷上重测。
  - 同时核对范围模式没有向 GitHub 写任何东西：各 PR 的审查数不变。
- **O2 门**：
  - 本地：`openspec validate --all --strict`、`node scripts/check-refs.mjs`；
  - PR 上 `CI gate` 与 `Privacy scan` 都绿。
- **O3 自用**：本 PR 按本变更的流程走：
  - 审查代理审第一轮；
  - 每条发现都回应并解决；
  - 按 D6 决定是否再审。

  记录轮数、各轮各档的计数、每轮的耗时与 token 用量。
- **O4 保护**：
  - 开 `required_conversation_resolution` 后读回，其余设置不变；
  - 有未解决的讨论时，即使检查都绿，`mergeable_state` 也是 `blocked`。审查没有发现时，自己发一条探针讨论来验；
  - 全部解决后变为 `clean`。
- **O5 隐私**：改动行、提交信息、路径与正文，本地名单检查全为 0；`.github/` 新增行的汉字数为 0。

## Risks / Trade-offs

- **同一账号自审自解决**：GitHub 只能强制讨论都被解决，不能强制回应是否合理。回应留在 PR 上，可以事后查。
- **审查代理会错**：
  - 误报：作者回应「错的」并写理由，花一轮来回；
  - 漏报：没有发现不等于没有问题。

  它的召回与误报在下一步用过去的缺陷评测。
- **花费**：中高档 PR 每轮一次 opus 子代理。实际花费在 O3 记录；下一步的评测串行跑，先实测一次再估总额。
- **高档等用户**：无人值守的连续工作会在高档 PR 处停下，这是有意的代价。
- **规则只在 agent 的提示词里**：
  - 不经 agent 的人可以跳过审查直接合并中档 PR，GitHub 只挡未解决的讨论。
  - 日后有第二位维护者时，可以改用 CODEOWNERS 加代码所有者批准，把高档的「由用户合并」交给 GitHub 强制。
