## Context

- 源码快照有三种 adapter：Git 仓（只看 HEAD）、多仓父目录（每个成员仓看各自的 HEAD，父目录里的非成员文件按目录读）、普通目录。选择规则（默认规则加 `.excavatorignore`）由快照统一给出，事实层用的也是它。
- 事实图里的文件节点没有行数；符号节点只出现在有解析器的语言里。
- unused-code 是同类先例：确定性脚本写 `.excavator/` 产物，宿主 skill 汇报，chat 读产物回答，没有新增 MCP 工具。
- 语料的历史情况：
  - 完整历史：sakai（5.5 万次提交）、dataverse（3.7 万）、oscar（2.2 万）、本仓库（约 500）；
  - 浅克隆：hadoop 等多数 Java 语料只有 1 次提交；
  - 多仓父目录：openmrs-workspace，4 个成员仓；
  - 非 Git：`_nongit`。
- sakai 上的实测（HEAD 有 18,127 个文件）：
  - `git log --no-merges -M --numstat -z`：30 秒，git 进程峰值内存约 800 MB，输出 36 MB；
  - 改动 35.2 万次，其中改名 2.6 万次；历史路径 8.6 万个，HEAD 里没有的 6.8 万个；
  - 沿改名链归属后，5,612 个文件的提交数变了，中位数是原来的 2 倍，前 20 名换掉 6 个；
  - git 默认的改名上限在一次大提交上跳过了详尽检测，只打印一条本地化警告，漏掉 214 次改名；`-l0` 时 37 秒。

## Goals / Non-Goals

**Goals：**
- 一次运行给出文件与各级目录的改动统计和热点排名，可复现、可测。
- 没有历史、历史不完整、二进制，都落进看得见的分类。
- 不必先跑 `/excavator`。

**Non-Goals：**
- 不追复制，不追跨仓移动。
- 不算圈复杂度之类的代码度量，体量只用行数。
- 不做按时间段的趋势。
- 不处理 Git 以外的版本库：非 Git 目录一律按「没有历史」处理。

## Decisions

### D1 普查用脚本，其余交给模型

先和 TS 框架支持的做法对照：那里的全部分量只是一份检测配置加一份附录，没有确定性阶段。

这里没有框架知识要教给模型，要做的是全仓普查：
- 每个文件沿改名链的提交数；
- 每级目录去重后的提交与作者。

这正是「全仓完整候选集与大批量结构化事实」那一类例外：让模型每次现写 awk，不可测，也不可复现；从文件行求和得目录数，又会把同一次提交算多次。

所以脚本只做普查与打分，下面这些交给模型：
- 把用户说的时间范围换成日期；
- 选汇报几名；
- 按模块回答问题；
- 解释头部的分类。

### D2 一次 `git log` 读全部，从新到旧沿谱系归属

每个仓只跑一次：`git log HEAD --no-merges -M -l0 --raw --numstat -z`，格式里带提交号、mailmap 后的作者邮箱（`%aE`）与提交时间（`%cI`）。

结果只由 HEAD 决定（acceptor 在本仓库的副本上实测：工作区里一个未跟踪的 `.mailmap` 改了 19 个文件的作者数，一个 `.gitattributes` 改了 340 个文件的增删行数）：
- 屏蔽用户级与系统级配置与属性：`GIT_CONFIG_GLOBAL=/dev/null`、`GIT_CONFIG_NOSYSTEM=1`、`GIT_ATTR_NOSYSTEM=1`、`-c core.attributesFile=/dev/null`（用户级属性文件不算配置，前两项挡不住它）；
- 仓库本地的 `.git/config` 与 `.git/info/attributes` 没有开关可关，仍会生效，写进残余假设；
- mailmap 与属性只取 HEAD：`-c mailmap.file= -c mailmap.blob=HEAD:.mailmap -c attr.tree=HEAD`，并让 git 读不到工作区，例如用 `--git-dir` 从一个空目录运行；
- 其余影响输出的默认值显式写出：`--diff-algorithm=myers`、`-c log.showRoot=true`、`--no-ext-diff --no-textconv`、`LC_ALL=C`。

- `--raw` 给出每个路径的状态（新增、删除、改名），`--numstat` 给出增删行数。两者在同一次输出里，按路径对齐。
- 输出流式解析，按提交从新到旧处理。维护「历史路径 → 当前路径」的映射，初值是 HEAD 的每个路径映射到自己：
  - 遇到改名 `old → new`：这次改动归给 `new` 对应的当前路径，再把 `old` 映射到同一当前路径；
  - 遇到新增 `p`：这次改动照常归属，然后删掉 `p` 的映射，更早的同名历史不再归给它；
  - 改名的目标也是新出现的路径：先归属这次改名，删掉 `new` 的映射，再把 `old` 映射到同一当前路径（sakai 上有 121 个文件是别的文件改名到一个空出来的路径上，只在新增时切断会把旧文件的历史算给它们）；
  - 提交按 git log 的默认顺序处理，不加 `--topo-order` 或 `--date-order`。在分支历史里两种顺序对少数路径（sakai 上 16 个，都是并行分支各自新建同一路径）给出不同结果，默认顺序对同一个 HEAD 是确定的；
  - 映射不到当前路径的改动，计入选择之外。
- 浅克隆的边界提交（`.git/shallow` 里列出的提交）跳过不计。git 把它显示成新增了当时的全部文件，照算会让每个文件多一次提交，「计数是下限」就不成立了。
- 不用 `--follow`：它一次只跟一个文件，1.8 万个文件就要跑 1.8 万次，而且它的改名判断与 `-M` 不完全相同。
- `-l0` 取消改名上限。默认上限会静默跳过改名，警告文字还随语言环境变化，没法可靠解析；sakai 上只多花 7 秒。

### D2a 分支历史：宁可少算，冲突看得见

「按顺序沿单一映射归属」在分支历史上是近似。两份独立实现（产品与 acceptor 的 Python）在 sakai 上起初有 3 个文件不一致，追下去是两种近似各错在不同地方：
- 同一个改名 `helpers/X → util/X` 出现在两条并行分支上。先处理的那条用掉了 `util/X` 的映射，后一条的目标找不到谱系。保留旧路径的映射会算对（26 次，接近 `--follow` 的 27）；删掉则少算 8 次。
- 子树导入的项目根目录 `README.md` 被改名到子目录后又删掉。保留旧路径的映射，会把别的项目的 README 历史算给 sakai 自己的 `README.md`。

前一种是少算，后一种是把别的历史算进来。按「宁缺不错」，改名目标没有谱系时删掉旧路径的映射。

考虑过的另外两种做法：
- **只读第一父链**（`--first-parent`，合并按对第一父的差异算一次）：线性历史上映射精确。但 dataverse 的作者从 384 降到 95，sakai 的提交从 5.3 万降到 1.4 万，热点的两个主要读数都失真，不采用。
- **按提交图逐提交传播映射**：精确，但要读每个合并对每个父的差异，代码量与耗时都成倍增加，为 1–2% 的文件不值得。

所以接受近似，让它看得见：三种冲突迹象（规范「谱系冲突要看得见」）计在受影响的文件上。原型在 sakai 上标出 267 个文件（1.6%），几乎都是「切断之后仍有更早的改动」，即少算；「两条谱系争同一路径」为 0 次。

同一次提交里的改动同时生效，按这次提交之后的映射归属，再一起往前推。逐条更新的话，结果取决于记录的先后顺序。

### D3 体量用 HEAD 行数，不用事实图

- 行数对所有文本文件都有意义，包括 XML、Facelets 与配置文件。符号数对没有解析器的类型恒为 0。
- 行数来自快照：Git 仓用快照已有的分批读取，读 HEAD 的 blob；目录用磁盘内容。
- 结果是热点不依赖事实图，可以在 `/excavator` 之前或之外单独运行。

### D4 分数取「提交数 × 行数」

- 这是「改动频率 × 体量」最简单的形式，不需要任何参数。
- 按各自最大值归一后再乘，排序与直接乘积完全相同，所以不做归一。
- 目录的 `score` 取文件之和，用来按模块排序。目录的提交数与作者数只能在脚本里去重：文件行相加会把同一次提交算多次。

### D5 窗口只收日期，脚本自己按 UTC 零点过滤

- 相对日期（`2 years ago`）的含义随运行时刻漂移，同一个 HEAD 两次运行结果不同。
- 不把日期交给 git 的 `--since`：git 会把裸日期补上运行时刻的钟点（acceptor 实测：14:17 运行时 `--since 2026-10-16` 漏掉一半提交），遍历时还可能因时钟偏差提前停下。脚本读全部历史，按提交时间与该日 UTC 零点比较，窗口外的提交整个跳过，不改谱系映射。
- 模型把用户的说法换成 `YYYY-MM-DD`，头部记下 UTC 零点的时刻。

### D6 不加 MCP 工具，新鲜度用现有助手

- MCP 的工具面是封闭清单。chat 用 `jq` 读产物，与 unused-code 一样。
- 产物记快照 revision。chat 从 `consumer-freshness.mjs` 输出的 `currentSourceRevision` 取当前值来比对，不新增代码。
- Git 仓的 revision 就是 HEAD，而 HEAD 决定了全部可达历史，所以 revision 一致就说明计数仍然有效。

## Risks / Trade-offs

- **改动很大的改名会被当成删除加新建。** 写进残余假设。
- **超大历史的耗时与内存。** 输出流式解析，脚本只保留每个路径的计数与提交号集合。O3 在 sakai 上记录耗时与峰值内存。
- **运行器导出的副本没有历史。** 运行器与部署镜像用 `git archive` 导出样本，在副本上运行时产物如实报「没有历史」。要统计热点，需要在带历史的检出上运行。本变更不改运行器。
- **多仓父目录的 ignore 规则变化不改变 revision。** 这时 chat 判断不出产物过期。属于少见情况，写进 chat 的说明：ignore 规则改了就重跑。

## 验收 Oracle（动手前写死）

- **O1 单元测试。**
  - 测试里用固定作者与时间的脚本化提交建 fixture 仓，覆盖规范的每个 Scenario，逐字段断言。
  - 浅克隆用 `git clone --depth 1 file://…`；多仓父目录放两个 fixture 仓加一个非成员文件；非 Git 目录用不带 `.git` 的副本。
  - 改名上限：fixture 仓设 `diff.renameLimit=1`，一次提交做两次非精确改名，断言两次都被识别。已实测：不加 `-l0` 时这两次显示为删除加新建，加了就识别为改名。
  - 注入变异，每种都要变红：
    - 不追改名；
    - 新增时不切断谱系；
    - 去掉 `-l0`；
    - 计入合并提交；
    - 二进制文件的行数记成 0；
    - 目录提交数改成文件之和；
    - 去掉守恒检查；
    - 计入浅克隆的边界提交；
    - 改名目标不切断谱系；
    - 读工作区的 `.mailmap`；
    - 把窗口日期直接交给 git 的 `--since`；
    - 改名目标没有谱系时保留旧路径的映射；
    - 不记谱系冲突。
- **O2 全量门。** vitest、`check-refs`、`openspec validate --all --strict`。
- **O3 真实语料，build-free，只读。** 产物写在 scratchpad 里的 APFS 克隆中，语料本身不动。
  - sakai 与本仓库（另加 openmrs-workspace）：
    - `lineageConflicts` 与另一份独立原型（Python，按规范的三种迹象）逐文件相同；
    - 另写一份独立实现（Python，按本规范从 `git log --raw --numstat` 重新解析），与产物逐文件比对 `commits`、`authors`、`added`、`removed`、`lastChanged`，要求全部相同；
    - 再按「改过名 / 没改过名 / 删除后重建」分层，各抽若干文件，用 `git log --follow` 人工核对；
    - 记录耗时与峰值内存；守恒成立。
  - hadoop 的克隆：头部标出浅克隆与最早可见提交的时间。
  - `_nongit`：头部写明没有历史，所有分数为 `null`。
  - openmrs-workspace：每个成员仓各自计数，非成员文件的历史为 `null`。
- **O4 真实 skill 运行。** 在 dataverse 的克隆上，headless Sonnet，设预算上限，跑一次 `/excavator-hotspots`，再问 chat 一个按目录的问题。检查：
  - 汇报里的数字都能在产物里找到；
  - 残余假设逐条列出；
  - 没有重构、删除、拆分之类的建议；
  - chat 先做了新鲜度比对，再读产物。
- 不过就如实记录，不宣称通过。
