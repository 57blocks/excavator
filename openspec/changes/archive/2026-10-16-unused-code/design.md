## Context

- **需求原文。** 未使用 / 不可达代码的候选：
  - 从入口出发做可达性分析，入口包括 `main`、servlet、JAX-RS / controller 端点、JSF 页面、定时任务、消息驱动 bean、对外 API；
  - 候选带可信度与原因，例如「没有静态调用者；类在 XML 里被按名字引用」为低可信度；
  - 输出 JSON 加 chat / MCP 查询，绝不自动删改代码；
  - 依赖 JSF 与 Java EE 两项需求，二者已合入。
- **用户约束。**
  - 定义要明确：A 只被 B 引用、B 没人引用时，A 与 B 都算；
  - 严谨，不能把在用的代码报成未使用；
  - 要区分确定与疑似；
  - build-free；
  - AI 能完成的不写进代码，参考 TypeScript 的做法。
- **TypeScript 的做法。** 框架支持的全部分量 = 一个 FrameworkConfig（检测与目录提示，数据）+ 一份附录（模型照做），没有框架专属的确定性阶段。`skills/excavator/frameworks/README.md` 写明，结构事实需要确定性只有两个理由：
  - 关于不存在的断言需要完整集合；
  - 否则模型要大量转写。

  未使用代码正好落在第一条上，但只有「完整候选集」这一部分。哪些候选是入口，是读一个文件加框架知识就能判断的事，附录里已经写了：`javaee.md` 写明「容器调用、代码不调用：注解就是入口」。
- **已有事实。**
  - `calls`：Java 按接收者静态类型解析，其它语言按作用域内名字唯一解析；
  - `implements` / `overrides`：切片 A 补齐；
  - `routes`：JAX-RS 端点到处理方法；
  - `references`：视图 EL 到 bean 类；
  - `injects`：注入点到类；
  - `mentions`：描述符到类；
  - 结构结果：Java 方法的可见性、修饰符、注解，文件的类字面量，类的父类型与注解。

  产物在 `.excavator/intermediate/fact-graph.jsonl`、`.excavator/intermediate/structure-all.jsonl` 与 `.excavator/source-manifest.json`。
- **规模**（`dead-code-detection` 的只读基线，P0 之前）：Fineract 非测试 Java 方法 23,692 个，没有任何入边的 8,654 个。逐个判断入口不可行，必须按组。

## 回看已有实现（`dead-code-detection` 切片 A，PR 57blocks/excavator#13）

| 方法引用记为调用点 | `calls` 边与遍历 | 保留 |

## Goals / Non-Goals

**Goals：**
- 定义可核对：不可达，两种原因，按簇报告，测试专用单列。
- 代码只做完整候选集与名字出现普查；入口判断交给模型与框架附录。
- `high` 可信度零误报：规则确定、可机器核对，只发给证据最强的一类。
- 每个函数节点落在一个可见的状态里，两步各自守恒。

**Non-Goals：**
- 方法内部的不可达语句；
- 类 / 文件 / 模块级判定（skill 可以按类汇总候选，不另立规则）；
- 字段；
- 自动删除或重构；
- 增量计算；
- 新 MCP 工具；
- 任何形式的概率。

## Decisions

**D1：定义是不可达，不是入边为零。**
- 入边为零会两头出错：漏掉 A（只被 B 调用）与互相调用的孤岛，又把没有代码调用的入口（`@GET`、`onMessage`）报进来。
- 不可达要知道入口：
  - 路由处理方法是确定入口（`routes` 事实）；
  - 其余入口由模型判断（D4）。
- 每个未使用节点的原因是 `unreferenced`（簇入口）或 `only-reachable-from-unused`（簇成员，附直接引用者）。按组报告并列出组的入口，用户知道先删谁。
- 只被测试走到的节点标 `test-only`，不混进未使用。

**D2：分工——脚本给完整集合与事实特征，模型判断入口，脚本按规则定可信度。**
- **脚本**（`unused-code.mjs`）：
  - 读产物，零模型，不含框架或语言分支；
  - 做两件模型做不到的事：
    - 全仓候选集：「没有引用」需要完整索引；
    - 名字出现普查：上千个名字逐个 `grep` 等于让模型大量转写。
- **模型**（skill）：用 `jq` 按特征分组，读已检测框架的附录与抽样源码，决定哪些组是入口。
- **脚本**再把决定应用到簇上，按固定规则给出可信度。模型不给可信度：可信度是事实信号的函数，交给模型就是转写加不可核对。
- 备选一：`dead-code-detection` 原设计。
  - 内容：五桶、语言适配器、注解规则目录、项目活性声明文件、可能引用图、按语言记账的文本否决、MCP 工具。
  - 不选：它把框架入口知识写成目录数据和规则引擎，把「对外 API 立场」做成声明文件与人工确认闸；这些都是模型读附录与源码能做的判断。
- 备选二：全部交给模型，让它读事实图后自己列出未使用代码。
  - 不选：没有完整索引就断言「不存在」是编造；候选上千时还要大量转写。

**D3：簇的计算。**
- 引用：
  - `calls`、`routes`；
  - 函数之间的 `implements` 与 `overrides`，按双向处理：被覆写的方法在用 ⇒ 覆写它的方法可能被分派到；覆写方法在用 ⇒ 被覆写的声明不能删。
- 双向处理会让一个覆写族里只要有一个成员被调用，整族都在用。代价是少量召回，换来的是不必判断分派目标。
- 步骤：
  1. 先从路由处理方法沿引用求可达集。
  2. 其余节点都是候选。对候选之间的引用求强连通分量与缩点图；缩点图里没有入边的分量是簇入口（单个节点或孤岛）。
  3. 每个候选记录它在候选之间的全部直接引用者。`report` 只靠这份引用表就能从决定出发重算可达性，不必再读事实图。
- 不为每个节点列出「到达它的全部入口」：一个共享的工具方法可能被上千个入口到达，成员 × 入口会膨胀，而且没有精确的线性算法。改为：
  - 记录直接引用者，大小 O(E)；
  - `report` 把未使用节点按引用连成组（弱连通分量），每组列出全部入口；
  - 可信度上限在缩点图上按拓扑序做动态规划（成员不高于任一直接引用者），结果与「不高于到达它的任一入口」相同，O(V+E)。
- `references`、`injects`、`mentions` 指向类，不指向方法，不参与方法级可达性，作为所属类型的使用迹象进入信号（D6）。
- 复杂度：可达性、强连通分量、分组与可信度上限都是 O(V+E)。规模在 hadoop 上实测报告（验收 O2）。
- 候选集产物 `.excavator/unused-candidates.json` 的形状（PR 2 定，`report` 只读它和决定文件）：
  - 头部：`factsDigest`、`sourceRevision`、计数（按语言）、守恒、普查统计；
  - `types`：候选的所属类型各一条——注解、仓库外父类型（自身 / 祖先 / 后代，去重的文本）、被 `references` / `injects` / `mentions` 引用的计数与样例、作为注解类字面量出现的计数与样例；
  - `candidates`：每个候选一条——id、名字、语言、文件、行区间、所属类型 id、可见性、修饰符、方法注解、是否入口、所在强连通分量、直接引用者（各带事实边类型与方向）、普查结果。
  - 结构结果没有的字段是 `null`（未知），有而为空是 `[]`。类型信息放在 `types` 里按 id 引用，不在每个候选上重复：一个被上千个类注入的类型，其引用样例只存一份。
- 注解类字面量按简单名对上仓库里的类：同简单名的类都记这个信号。方向是多报使用迹象，只会压低可信度。

**D4：入口判断的决定文件。**
- 模型写 `.excavator/unused-decisions.json`，每条有：
  - `kind`：`entry` 或 `test-entry`；
  - `reason`：谁调用它、凭什么；
  - `query`：选出这些 id 的 `jq` 表达式；
  - `ids`。
- id 由运行查询产生，不手抄。
- 决定可以针对任何候选节点，不限簇入口：一个成员若另被反射调用，也可以单独移出。
- 决定只能把节点移出候选，所以不设人工确认闸：错判只会少报，不会多报。决定的理由与计数全部写进产物，用户可以质疑。
- 不设持久的项目声明文件：每次运行由模型重新判断，上次的 `query` 留在产物里可以复用。

**D5：名字出现普查。**
- 范围：源码清单里选中的全部文件，包括非代码文件。
- 读的内容必须是事实所据的源码：
  - 先读工作区，按清单的 `contentHash`（sha256）核对；
  - 不一致（例如 git 仓库有未提交的改动，而 Lazy 读的是 HEAD）就改读源码快照（`resolveSourceSnapshot(root).readFile`）再核对；
  - 仍不一致即失败，提示重新运行 Lazy。
- 计数：按标识符 `[A-Za-z_$][A-Za-z0-9_$]*` 切分、整词、区分大小写、逐行计数。
- 已解释的出现只有两种：
  - **本节点的声明：** 行区间内第一个出现该名字的行上的 1 次；
  - **直接引用者体内：** 落在一个直接引用它（D3 的引用图里有边指向它）的函数节点行区间里的出现，全部算已解释。
- 其余出现即「别处出现」，记录总数与位置样例。总数不截断。
- 为什么按引用者体内、不按边的证据行：
  - 事实图对每个（类型、起点、终点）只留一条边与它的第一条证据（`build-fact-graph.mjs` 的去重）。按证据行允许，会把同一调用者的第二次调用算成别处出现，给一个只被 B 调用的 A 安上「使用迹象」。
  - 放宽是安全的：引用者体内的出现只在引用者执行时生效。引用者未使用，这处出现不会执行；引用者在用，A 已经沿边可达。它不提供独立于引用者的使用。
- 名字含标识符字符以外的字符（例如 Unicode 字母）时，切分看不见它，普查结果记为未知，不当作零。
- 三条刻意的保守：
  - **只认直接引用者。** 解析到别的同名方法的调用、Kotlin 等语言里没有成边的调用、方法体之外的调用，都算别处出现。所以不需要按语言记账。
  - **别的同名声明也算别处出现。** 例如两个类各有一个 `formatDate`。代价是召回；候选集统计「别处出现全在同名声明行上」的候选数，多了再收窄。
  - **注释与字符串里的出现也算。** 反射字符串、`@MethodSource("name")`、XML 里的方法名都靠这一条看见。

**D6：可信度规则。**
- `low`：至少一个使用迹象：
  - 别处出现（D5）；
  - 所属类型被 `references` / `injects` / `mentions` 引用，或在注解实参里作为类字面量出现（`@Mapper(uses = X.class)`）；
  - 非 `private` 非 `static` 的方法，所属类型自身、祖先或后代有不在仓库索引里的父类型。最直接的情形是所属类型自己实现了仓库外接口；私有方法不受这条影响，只降到 `medium`（`readObject` 场景）。

  「不在仓库索引里」= 结构结果里写了、但事实图没有对应 `inherits` / `implements` 边的父类型。这包括嵌套类型与其它 JVM 语言的类型，是有意的保守。
- `high`：同时满足：
  - 没有使用迹象；
  - `private`；
  - 方法与所属类型都没有注解；
  - 所属类型与祖先没有不在索引里的父类型。

  这和只报 `private` 的成熟工具（PMD `UnusedPrivateMethod`、detekt、Roslyn IDE0051）同一立场：不知道入口与框架约定时，只有私有成员能证明。祖先条件挡住序列化：`Serializable` 类的私有 `readObject` 由 JVM 调用。注解条件挡住 `@PostConstruct private void init()`。
- `medium`：其余情形。仓库里没有发现使用，但对文件之外可见、带注解，或所属类型继承了仓库外的类型。它就是「疑似」，模型已经移出了它认得的框架入口。
- 簇成员的可信度不高于任一直接引用它的未使用节点，因而不高于到达它的任一入口：A 是否未使用取决于 B。
- 没有可见性事实的语言不给 `high`。
- 没有为 getter 与序列化约定写专门规则：公开的访问器至多 `medium`，私有的访问器序列化框架要靠注解或仓库外父类型才会调用，已被上面的条件覆盖。

**D7：产物与查询。**
- `candidates` 写 `.excavator/unused-candidates.json`，`report` 写 `.excavator/unused-code.json`。两者头部都有事实图的 `factsDigest`；`report` 拒绝与当前事实不一致的候选集或决定。
- 查询走 `excavator-chat`：先比对摘要，再按 id、名字或文件回答状态、原因、可信度与信号。
- 不加 MCP 工具。需求原文是「chat / MCP 查询」，chat 已满足。代价：只接 MCP 的宿主查不到，需要时另立变更。

**D8：删除报告模式。**
- 去掉的部分：
  - `resolveFileCalls` 的 `{ report }` 选项；
  - `reportSite`、`candidateIds`、`probeSite` 及其状态；
  - 结果上的 `lookupType`、`outsideHierarchy` 与歧义结果的 `candidates`（`unionOfCandidates`）；
  - 测试 `tests/facts/java-call-report-mode.test.mjs`。
- 按类型注入的类型查询用到的部分不动：`ambiguousAmong` 的 `types`、`methodsMaybeOutside` 等，以 grep 与测试核实。
- 非报告模式本来就逐字节不变，删除后事实图输出必须逐字节相同（验收 O0）。

## Risks / Trade-offs

- **[同名声明压低召回。]** D5 把别的同名声明算作出现，常见名字的候选几乎都是 `low`。接受：方向是少报。实测（见测量记录）不计同名声明行只让 `high` 候选池多 2%–5%，保持保守。
- **[模型错判入口。]** 只会把节点移出候选，造成少报，不会造成误报。决定的理由与计数进产物，审计抽查理由是否成立。
- **[模型漏判入口。]** 漏判的入口留在候选里，可信度由规则决定。公开方法至多 `medium`，带注解至多 `medium`，所以漏判不会产生 `high` 误报。`medium` 的含义是「需要人确认」，skill 不得把它说成确定未使用。
- **[入口数量大。]** 上千个入口要按组判断。skill 给出分组配方：按方法注解、所属类型注解、仓库外父类型、名字模式、路径。模型对每组抽读源码后决定；决定针对组，不针对单个节点。
- **[非 Java 语言的 `calls` 稀疏。]** 按名字解析的语言里，大量节点会成为入口，名字普查又让它们多为 `low`。产物按语言计数，skill 汇报时写明。不为此加语言规则。
- **[未选中的文件。]** 被忽略规则或默认规则排除的文件不参与普查。写进残余假设；选择账本可见。
- **[运行时拼接的名字、构建期生成的代码。]** 看不见，写进残余假设。已知的生成器靠注解与注解类字面量信号降到 `medium` / `low`。

## Migration Plan

合入即生效。产物在首次运行时产生，没有迁移步骤。事实图不变，旧项目不需要重跑 Lazy。回滚即 revert 对应 PR。

### 采纳的发现

1. **`medium` 的措辞。** 「仓库里没有使用」改为「名字在别处没有出现」，规格、skill 与 chat 同改。同时加了第 5 条残余假设：不写出方法名的使用看不见。来源是 dataverse 的 EL 属性与 JSON-B setter。
2. **按语言计 `calls`。**
   - 两个语料的 shell 都没有一条 `calls` 边，全部 shell 函数都成了候选，被报为 `unreferenced`。
   - 现在候选集头部与产物按语言给出 `calls`；`report` 拒绝没有这个计数的候选集。
   - 对 `calls` 为 0 的语言，skill 与 chat 说明结果只说明事实里没有它的调用。
3. **测试代码一律 `test-entry`。**
   - dataverse 一条决定把 150 个测试替身（实现生产接口）记为 `entry`。
   - Fineract 把一个只被测试依赖的测试支持模块记为 `entry`；35 条决定里，共有 13 个测试代码成员记成了 `entry`。
   - 记成 `entry`，会把它们触及的生产代码算作生产在用，藏起只被测试使用的代码。方向保守，但分类错了。
4. **程序启动每次都判入口。** Fineract 的运行没有判 4 个 `main`（其中一个是应用自己的启动类），也没有判 Python `__main__` 下调用的函数；dataverse 的运行判了。现在写成每次都判，两次运行就会一致。
5. **第 6 条残余假设：事实图没能解析的调用没有边。** 这类调用包括嵌套或匿名类型里的调用、同元数重载、没有声明类型的接收者、泛型覆写。对应的方法被报为 `unreferenced`，只靠名字普查留在 `low`。Fineract 审读抽到的这类情形，都被普查挡住了。

### 不采纳的发现

1. **「没有任何地方启动的 `main` 不是入口」**（dataverse 决定 7，审读判为不成立）。仓库里看不出有没有人运行一个程序；判为入口只会少报，不会多报。这与采纳的第 4 条一致。
2. **Serializable 这类没有方法的标记接口，让 `visible-with-outside-supertype` 成立**（dataverse 有 365 条仅因此为 `low`）。要排除它，就得在脚本里维护标记接口名单，这是语言分支。代价只是 `low` 与 `medium` 之差，不影响 `high`。
3. **在普查里按 JavaBeans 约定认属性名**（`#{x.foo}` 对应 `getFoo`）。这是框架与语言约定，规格要求脚本不含这类分支。`high` 要求 `private`，不受影响。已改为残余假设与措辞（采纳第 1 条）。
4. **为没有覆写边的 `@Override` 另立信号。** 缺边属于 Java 成员解析的缺口。`@Override` 方法带注解，不会是 `high`；名字普查（同名声明行也计入别处，D5）已经把它们留在 `low`。
5. **方法自身体内的出现、非代码文件（YAML、adoc）里的同名词也计为别处出现。** 规格只解释声明行与直接引用者体内的出现。这样做只会压低可信度，不会抬高。
6. **为 JSF 页面层、ShellSpec、JSON-B、OASFilter 补入口规则。** 附录里已有 EL 成员到方法的规则，skill 也有「事实没连上的处理方法仍是入口」这一条。这次运行没判，它们留在 `low` / `medium`：缺口可见，没有编造。每遇到一个框架就给 skill 加一条规则，skill 会无限增长；需要时补进框架附录。
