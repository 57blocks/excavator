## Context

动机见 proposal.md。现状：

- `packages/core/src/ignore-filter.ts` 导出 `DEFAULT_IGNORE_PATTERNS`，有两个使用者：
  - `createIgnoreFilter`：增量准备用；
  - `createSourceSelectionPolicy`（`source-selection.ts`）：唯一的选择边界，git、目录、多仓库三种快照都经过它。
- 选择策略把默认规则、项目规则、CLI 规则依次加进同一个 `ignore` 实例。判定依次为：敏感 → 分析数据 → 归档 → 规则。
- 默认规则逐条以 `default:<规则>` 写进选择描述符。描述符的摘要就是快照的 `selectionDigest`。同步时 `sourceRevision`、`selectionDigest`、`pipelineVersion` 任一不同，就做完整的确定性重投影。
- `ignore` 库实现 gitignore 语义：
  - 不以 `/` 结尾的规则同时匹配文件与目录，在任何深度生效；
  - 默认不区分大小写；
  - 判定一个路径时，先看它的上级目录，上级被排除，下级就无法再纳入。
- 默认规则里不以 `/` 结尾的有：
  - 锁文件与二进制、资源文件的扩展名规则；
  - 生成文件规则（`*.min.js`、`*.map`、`*.generated.*`）；
  - 操作系统元数据（`.DS_Store`、`._*`、`Thumbs.db` 等）；
  - `LICENSE`、`.gitignore`、`.excavatorignore`、`.editorconfig`、`.prettierrc`、`.eslintrc*`、`*.log`。

## Goals / Non-Goals

**Goals：**
- 默认规则里的每条文件规则只排除文件，不排除同名目录；文件的判定与改前完全相同。
- 用结构判定，不逐条列举：以后新增的文件规则自动适用。
- 三种来源的选择结果一致；用户规则的排除与重新纳入照旧生效。

**Non-Goals：**
- 目录规则（`build/`、`out/`、`dist/`、`target/`、`obj/`、`coverage/`、`vendor/` 等）误伤同名源码包的问题。实测 TomEE examples 有一个 Java 包叫 `out`（3 个文件）。其余命中都是第三方库内的 `dist/`、`build/`、`vendor/`，按本意排除。要分辨构建产物目录与同名源码包，得按模块根（构建清单所在目录）定位，而选择策略是不读文件系统的纯函数。这需要另立设计，放到后续变更。
- 改选择策略的判定顺序、敏感文件与归档规则。
- 改选择策略的版本标签。

## Decisions

### D1 从文件规则机械派生目录取反规则

为每条文件规则派生一条 `!<规则>/`，导出的 `DEFAULT_IGNORE_PATTERNS` 按三段排列：文件规则、派生的取反规则、目录规则。
- 文件规则：不以 `/` 结尾、不以 `!` 开头；
- 派生规则：只匹配目录，把文件规则对目录的排除撤回；
- 目录规则：以 `/` 结尾。手写列表里全是正向规则，它们之间的先后不影响判定，所以重排不改变任何已有的结果。

为什么这样能成立：
- 撤回只作用于名字匹配文件规则的目录。目录下的文件仍逐条判定，名叫 `LICENSE` 的文件照旧被排除。
- 目录规则排除的上级（如 `node_modules/`、`build/`）先被判定，下级无法再纳入，所以 `node_modules/license/` 仍被排除。
- 目录规则排在取反规则之后。对同一个路径，最后一条匹配的规则生效。带通配的目录规则（`.excavator.*/`、`.excavator-*/`、`.trash-*/`）可能与某条文件规则同时匹配一个目录，如 `.trash-1.log/`；目录规则在后，这样的目录仍被排除。若把取反规则放在最后，它会把这类目录放回来：选择策略因先判分析数据不受影响，但增量准备用的 `createIgnoreFilter` 会把它当作源码，扫描器硬跳过的目录也不再是 Core 默认排除的子集。实现时发现了这一点，有测试与绊线。
- 项目规则与 CLI 规则排在派生规则之后，写 `license/` 仍能排除这个目录。

只读实测：`ignore` 库对 `a/license/Foo.java`、`src/License/I.cs` 判为不排除；对 `a/LICENSE`、`a/license`（文件）、`a/license/LICENSE` 判为排除；对 `LICENSE.md`、`License.txt` 判为不排除，与改前相同；加用户规则 `license/` 后，目录又被排除。

派生放在 `ignore-filter.ts`，作为导出常量的一部分。这样两个使用者、选择描述符与文档看到的是同一份规则，不另建第二个来源。

考虑过、没采用的：
- **从默认规则删掉 `LICENSE`**：许可证文件会被选中，扫描输出与事实图对每个仓库都变，范围远超缺陷本身。
- **把 `ignore` 改成区分大小写**：大写目录 `LICENSE/` 仍会被排除，而且所有规则的大小写语义都会变。
- **只给 `LICENSE` 加例外**：其余文件规则有同样的缺陷，逐条列举会在下一条新规则上重犯。

### D2 版本标签不变，靠描述符换摘要

选择描述符逐条带上默认规则，派生规则加入后，`selectionDigest` 自然改变，每个项目的下一次同步完整重投影一次。

版本标签 `source-selection-v1` 指的是判定算法（顺序与类别），算法没变，所以不升。升级会牵动类型字面量、schema 与多处测试，换不来更多的正确性。

语义层按文件内容缓存，不受影响。

### D3 测试

- **性质测试**：对 `DEFAULT_IGNORE_PATTERNS` 里的每条文件规则，用 `x` 替换 `*` 得到一个具体名字，构造三条路径：
  - 同名目录下的 `Foo.java`：断言被选中；
  - 同名文件：断言是 `filtered-by-defaults`；
  - 大写与小写两种写法各测一次。

  文件规则的集合从常量本身派生，不手写清单。
- **规格场景**：每个场景一条测试，在选择策略层面断言判定与原因。三种快照的一致性用现有的适配器夹具加一个 `license/` 目录。
- **绊线**：去掉派生，性质测试与 `license/` 场景必须变红。
- **钉住的值**：测试里钉住的选择描述符或摘要如有变化，用生成器整块重冻，并逐项写明来源。

## Risks / Trade-offs

- 每个已分析的项目，下一次同步做一次完整的确定性重投影，耗时等于一次全量事实构建。这是一次性的，换来的是选择结果正确。
- 有这类目录的项目，事实图会多出节点与边。原本按唯一候选连上的边，可能因为新出现的候选变成歧义或别的缺口。这是在纠正原来不完整的候选集，验收要逐条归因。
- 目录规则的误伤（Non-Goals）仍在，验收摘要会写明。

## 验收 Oracle（动手前写死）

全部 build-free，语料只读，产物不进仓库。

- **O1 单测与绊线**（coder）：D3 的全部测试，以及绊线变红的记录。
- **O2 选择差异，独立核对**（acceptor）：
  - 对象：本地全部语料，改前（main）与改后两版选择策略各判一遍。
  - 独立计算：不引用 `ignore` 库与本仓库代码，自写判定：一个文件被新选中，当且仅当它某个上级目录的名字匹配某条默认文件规则（不区分大小写的 glob），没有上级目录匹配默认目录规则，它自己的名字不匹配任何默认规则，且不被敏感、归档、分析数据与项目规则排除。
  - 断言：两版选中集合的差集与独立计算完全一致，且只增不减。预期 Dataverse +3、koel +7、私有 C# 语料 +4，其余为 0。
  - 装置先验：在一份副本上人为制造一条差异，确认能报出。
- **O3 事实不回归与增量归因**（acceptor）：
  - Dataverse 与私有 C# 语料跑 Lazy，改后对比改前（`lazy-fact-graph/12`）。
    - 新增节点只来自新选中的文件；
    - 新增边至少一端是新节点，或者能逐条归因到新文件提供的声明；
    - 减少的边与新增的缺口，逐条归因到新文件带来的新候选；
    - 不允许其他变化。
  - 两个选择集合不变的语料（TomEE examples、fineract）跑 Lazy：节点、边、缺口与覆盖与改前一致，只有选择摘要不同。
- **O4 真实 MCP**（acceptor）：在 Dataverse 上：
  - `project_status` 的选择计数比改前多 3；
  - `recall` 能找到 `LicenseServiceBean`；
  - 若改后有指向它的 `injects` 边，从实现 1 跳入边能到消费者。
- **O5 耗时**：不测。本变更不改计算，只改选择集合。
- **O6 全量门**（我跑），依次：
  1. `pnpm --filter @excavator/core build`；
  2. core 测试；
  3. `pnpm typecheck`；
  4. `pnpm exec vitest run --maxWorkers=4`；
  5. `node scripts/check-refs.mjs`；
  6. `openspec validate --all --strict`。

预案：
- 若 O3 出现无法归因到新文件的变化，就停下，查明是选择、扫描还是事实阶段的问题，再定修复范围。
- 若 O2 发现派生规则误放了不该选中的文件，回到 D1 重新设计，不加逐条例外。
