## Context

第一片 `handbook-system-overview` 之后的情况：
- 运行里有地图、各功能条目、概览单元（`state.overview`）；
- 脚本能算出应用根目录与系统事实（`applications.mjs`、`system-facts.mjs`）；
- `page-data` 格式到了 `/3`，含 `system`。

页面包按区域列功能，有功能页、概览页、通知页、定时任务页、覆盖页。手册只有一份 `handbook.md`，正文不含引文路径。

## Goals / Non-Goals

**Goals**：
- 实体页与索引成为手册的骨架，全部由脚本算出；
- 产品与技术两个视角是同一份数据的两种投影；

**Non-Goals**：
- 区域改为业务领域（`handbook-map-by-domain`）；
- 按视角跳过阶段；
- 新的模型写作；
- 数据表、状态、问题等实体，留给后续切片。

## Decisions

### D1 `--views`

- **取值**：`product`、`technical`，逗号分隔，至少一个，默认 `product`。
- **解析**：第 0 阶段解析成 `$VIEWS`，原样交给 `assemble`、`page` 与 `reply`。脚本拒绝其他取值，并打印可选值。
- **不记进 `state.json`**：视角只影响输出，换视角续跑只是重新拼装。

### D2 实体与关系（`entities.mjs`）

一个纯函数，从已载入并重新核对过的运行与系统事实，算出实体与关系。

**实体**：
- 领域：地图的区域；
- 功能；
- 角色：地图的角色；
- 应用：每个应用根目录，以及已核实概览在其下列出的子应用。名称与职责取自已核实概览，没有时写「未核实」，与第一片的应用表一致；
- 定时任务：`job` 候选；
- 通知：已核实条目的通知项；
- 外部集成：已核实概览的项。

**关系**，全部只取 `verified` 的单元：
- 功能 → 应用：功能的每段引文归到目录最长匹配的应用，按应用计引文数。关系名是「引文落在该应用中」。
- 角色 → 功能：条目 `who` 里有这个角色的项，带它的「能做什么」。
- 领域 → 应用：该领域各功能的引文数之和。
- 通知 → 功能；定时任务 → 功能（沿用总表的规则）。
- 外部集成 → 应用，两种关系，分开存、分开显示：
  - 「引文所示的调用方」：已核实概览项的 `callers`；
  - 「源码里出现该名称的应用」：在与候选列表相同的那批源文件里按字面查找系统名，区分大小写，有一处即算；文件按目录最长匹配归到应用（根目录或子应用），与引文同一粒度。匹配到的文件数随关系一起记下，落在所有应用之外的文件另计。

  第二种不说调用：名称可能只出现在注释或配置里。它的作用是让读者看见模型可能漏列的应用。

落在任何应用之外的引文另计一个可见的桶，不丢弃。

**矩阵**：
- 角色 × 功能：单元格是该角色在该功能里能做什么，没有就空；
- 应用 × 领域：单元格是引文数。

### D3 两个视角

| | 产品视角 | 技术视角 |
|---|---|---|
| 导航 | 领域 → 功能 | 应用 → 该应用里的领域 → 功能 |
| 概览 | 与第一片相同（含应用表与外部系统表，主规格要求） | 同左 |
| 实体页 | 领域、功能、角色、通知、定时任务 | 全部，另加应用、外部集成 |
| 矩阵 | 角色 × 功能 | 两张都有 |
| 引文位置 | 不显示 | 概览与每个功能末尾一节「引文位置」，逐项列出文件与行范围 |

引文的行范围由脚本按段落在文件中的位置算出，与引文检查用同一个函数。

两个视角都选时，HTML 顶栏加视角切换，路由带视角前缀，切换时停在同一实体（另一个视角没有这个实体时回到概览）。只选一个时没有切换。

Markdown：
- 产品视角写 `handbook.md`；
- 技术视角写 `handbook-technical.md`。

没有选的视角，`assemble` 删去它上次留下的文件，以免留下旧内容。

### D4 不夸大的关系名

所有关系与矩阵的标题、栏目，都写实际检查了什么：
- 写「引文落在该应用中的功能」，不写「该应用实现的功能」；
- 写「条目里写明该角色能做的事」，不写「该角色的权限」。

页面与 Markdown 的固定说明里，写明只计已核实的条目。

## Oracles

**O1（夹具，脚本与页面包）**：
- `--views` 的解析：默认值、两个都选、非法值。
- 实体与关系：
  - 引文归属取目录最长匹配；
  - `confirmed` 的条目不计入关系；
  - 没有已核实概览时，应用仍是全部应用根目录，名称写「未核实」；
  - 矩阵的单元格与关系一致；
  - 名称出现的关系：注释里的名称也算，大小写不同不算，跳过的目录不算，结果与引文所示的调用方分开。
- 产品视角：输出里不出现任何引文文件路径。扫描 `handbook.md` 与页面数据里产品部分的全部字符串，与所有引文的 `file` 比对。
- 技术视角：每一项都有文件与行范围，行范围与引文检查定位的一致。
- 页面：
  - 只选一个视角时没有切换；
  - 两个都选时切换后停在同一实体；
  - 技术视角的导航按应用；
  - 手机宽度下没有横向滚动。
- 两次生成逐字节相同。
- 变异检查，各至少一个测试变红：
  - 归属改为第一个匹配而非最长匹配；
  - 关系计入 `confirmed` 条目；
  - 产品视角漏出引文路径；
  - 视角切换不保留实体；
  - 名称出现的关系并入引文所示的调用方。

**O2（合约测试）**：SKILL.md 第 0 阶段解析 `--views`；第 7 阶段把 `$VIEWS` 交给 `assemble`、`page`、`reply`。

**O3（go-multirepo 现有输出，零模型花费）**：在第一片的真实运行输出（概览与两个已核实功能）上，以两个视角拼装与导出。
- 线：
  - 「源码里出现该名称的应用」包含第一片审读找出的 4 处漏列：S3 与邮件服务器下的审读服务，Slack 与 Jira 下的 v2 服务；
  - 产品视角的 `handbook.md` 与页面数据里没有任何引文路径；
  - 技术视角每一项的行范围与引文检查定位的一致。
- 用无头浏览器打开页面：视角切换停在同一实体；技术视角按应用导航；手机宽度下没有横向滚动。
- 只报告：每个外部系统两种关系各列出的应用。

**O4**：受影响测试、`check-refs`、`openspec validate --all --strict` 在本地通过；全量门在分离检出里跑；源码零非 ASCII 字符。
