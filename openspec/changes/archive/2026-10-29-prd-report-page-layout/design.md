## Context

报告页是 `packages/prd-report-page` 构建的模板加一个内联数据块（`xv-prd-report-data`）。读者是产品经理：先想知道这个产品有哪些功能、哪里问题最多，再进某个功能读章节，或者按级别看 findings。真实产物的量级：30 个功能，章节中位数约四万字、几十个小标题，318 张图，136 条 findings，总览的参考表（术语、角色、待确认项）合计两万多字，覆盖表十几万字。

浏览页（`explorer.html`）的外观是：顶栏放分段的页面切换与工具按钮，下面是主区域，右侧是带标签的信息栏。两页属于同一产品，布局语言应一致。

## Decisions

**D1 外壳：顶栏、左栏、正文、右栏目录。** 顶栏高 56px、吸顶、毛玻璃底，从左到右：项目名（衬线体）与小字 `PRD report`；分段的页面切换 Overview、Findings（带条数）、Coverage，当前页按浏览页的选中段样式；快速跳转按钮（写出快捷键）；靠右是源码版本（等宽、截短，完整值在提示里）与 Theme 下拉按钮（D8）。左栏宽 300px，在顶栏下吸顶并自己滚动：顶部一个筛选框（按编号或名字过滤），然后按 `kind` 分组（`flow` 写 Flows、`automated` 写 Automated、`reference` 写 Reference，其它种类按原名排在后面），组内按章节顺序，组标题带条数。每个功能一行：编号（等宽）、名字（单行省略，完整名字在提示里）、状态记号（✓◎◐○✕，带无障碍名字与提示；颜色不是唯一信号；verified 用弱化的颜色，其它状态用各自的颜色，免得 30 个相同的勾抢眼）、finding 条数，有 P0 时条数前加 P0 色的点并在提示里写出各级别条数。正文区按页面类型给宽度：阅读页（总览正文、功能章节）正文列最宽 780px；表格多的部分（功能矩阵、覆盖页）用整个正文区。视口不小于 1280px 时，总览、功能页与覆盖页的正文右侧有 220px 的「On this page」目录（D6）。顶栏随宽度逐级收起文字：小于 1200px 时快速跳转只留图标与快捷键（左栏仍在旁边，放不下按钮文字）；小于 1024px 时左栏收进顶栏的 Menu 抽屉，页面切换仍在顶栏且可横向滚动；小于 900px 时版本、快捷键提示、`PRD report` 小字与 Menu 文字隐藏；小于 640px 时 Theme 也只留图标。理由：顶栏让三个页面与快速跳转在任何滚动位置都能一步到达，和浏览页一致；左栏一行一个功能，30 个功能一屏能看完大半；按种类分组让「流程」和「自动行为」分开。代价：功能导航不再严格按章节号排，`reference` 章节不在最前面；组内仍是章节顺序。

**D2 总览：先概要与功能矩阵，再正文与参考表。** 标题区：项目名、`As-Is PRD report`、一行元信息（Reader、Language、Scope、Revision）。概要是三列网格（窄屏堆叠）：第一列上下叠放功能与图两块，后两列各一块，同一行等高；四块是：功能数（下注各种类条数与各状态条数）；图数；findings 总数，带一条按 P0/P1/P2/Unranked 堆叠的横条和图例，图例与 product/technical 条数都链到筛选后的 findings 页；核对的陈述，带一条按 verified/contradicted/misattributed/unverifiable 堆叠的横条，下面列出待确认项的五个计数（resolved right、resolved wrong、still open、conflicts、not checked）。九个核对计数与各级别、各类别条数都仍在总览上，只是不再各占一张卡片。随后是功能矩阵：按与左栏相同的种类分组，每组一个组标题行（例如 `Flows · 19`），每个功能一行，列为功能（编号与名字，链到功能页）、状态记号、流程数、P0、P1、P2、Unranked（全体都没有未定级时省略这一列）、四个陈述结论数；级别格子的底色深浅按该格条数相对该列最大值变化，非零的格子链到 `#/findings?feature=<id>&priority=<级别>`，零显示为淡色的 `·`。之后是总览正文与参考表，顺序照旧：`overview.md`、术语表、流程索引、角色、待确认项。理由：读者第一屏就能看到「哪些功能问题多」，并一步进到对应的 findings；参考表是查阅用的，放后面。代价：总览比原来多一张表的高度，但原来的功能表移到这里，总长不变。

**D3 功能页：事实、findings 摘要、正文、findings、核对报告、翻页。** 标题上方是一行小标签：编号、种类、状态徽标。标题下是事实卡：参与者与权限角色（标签，空时写 None）始终展开；触发、流程与入口各是一个可展开的行，摘要写出条数（例如 `Flows (15)`），默认收起。失败的功能在事实卡之前显示失败说明。事实卡下是 findings 摘要条：总条数与各级别条数，点击滚到本页的 findings 小节；没有 findings 时写明。然后是章节正文（没有章节时的说明照旧），findings 小节（卡片同 D4），核对报告（折叠，照旧），最后是按章节顺序的上一个与下一个功能。理由：四万字的章节里，读者需要先知道这个功能有多少问题、在哪，并能随时跳到；触发、流程与入口清单最长有几十行，默认收起后 findings 摘要与正文开头在 1440×900 的第一屏里。代价：这三项要多点一次才能看到；条数始终可见。

**D4 findings 页：吸顶筛选条、按级别分组。** 筛选条在顶栏下吸顶，一行放类别分段、级别分段（每个按钮写出当前其它筛选条件下的条数）、功能下拉、搜索框，右端是「Showing n of m」。列表按 `findings.json` 的顺序，在级别变化处插入小标题（例如 `P0 · 29`）。卡片四边同一种中性边框，级别只由头部的级别徽标表示（用户要求去掉彩色左边）；头部一行是级别、类别、`anchor-checked`、编号，功能链接靠右；陈述、定级理由（弱化的段落，不加底色）与每条证据完整显示，每条证据是一个代码框，顶部一条写 `文件:行`，下面是引文。窄屏（小于 640px）时筛选控件收进一行「Filters」，这一行写出当前筛选与条数，点开才显示控件，筛选条高度不超过约 96px。功能页上的 findings 用同一张卡片。理由：136 条里先看 P0 是最常见的读法，分组小标题让级别边界一眼可见；筛选条吸顶后，读到第 80 条也能改筛选。代价：小标题占一点高度。

**D5 快速跳转。** 顶栏按钮、Ctrl/⌘+K 或在不在输入框里时按 `/` 打开一个居中的对话框：一个输入框和结果列表。功能按编号与名字匹配，finding 按编号与陈述匹配，不区分大小写；编号完全相等的排最前，其次是编号前缀，再其次是名字或陈述包含；功能在 finding 之前，最多列 50 条并写出总匹配数。方向键移动、回车打开、Esc 关闭，关闭后焦点回到打开前的位置。打开功能去 `#/feature/<id>`；打开 finding 去 `#/feature/<所属功能>?finding=<finding id>`：功能页渲染后滚到那张卡片并短暂高亮（尊重减少动效设置）。路由解析多认 `finding` 参数，值不是该功能的 finding 时照常打开功能页、不滚动；其它未知参数照旧丢弃。理由：30 个功能与 136 条 findings 靠滚动找太慢；评审时常拿到一个 finding 编号，要一步打开它的上下文。代价：路由与路由测试多一个参数。

**D6 本页目录。** 正文里 Markdown 的 h2 与 h3 由 `Markdown` 组件给出确定的 id（`<idPrefix>-L<源码行号>`），目录在渲染后从正文容器里读这些标题生成，另外加上页面自己的小节（总览：Summary、Features、Terminology、Flow index、Roles、Open items；功能页：Findings、Verification report；覆盖页：各表的小节）。滚动时用 IntersectionObserver 高亮当前小节。点击目录项用 `scrollIntoView` 滚动，MUST NOT 改 URL 片段（片段是路由）。目录过长时自己滚动，当前项保持可见。理由：章节小标题多达几十个，没有目录就只能整章滚；用行号做 id 不依赖标题文字，重复标题也不冲突。代价：目录在宽度不足 1280px 时不显示。

**D7 不加依赖，数据与打包不变。** 所有改动在模板里：不新增 npm 依赖，图标用内联 SVG 或 Unicode 字符；`lib/page-data.mjs` 与页面数据格式不动，页面字节仍只由产物目录决定（目录、跳转、高亮都在运行时算）。已有产物目录用新模板重填原数据块即得到新布局，不必重跑分析。

**D8 主题用下拉菜单，两页默认 Light Violet。** 用户要求两页都用下拉菜单切换主题、默认 Light Violet。浏览页本来就是 Theme 按钮打开的下拉菜单，只把默认的预设改为 Light Violet 配 Violet，并把样式表里 JavaScript 应用主题之前的回退值改为 Light Violet，避免先闪深色。报告页去掉两段式开关，换成与浏览页同样的 Theme 按钮（调色板图标加文字，窄屏只留图标）与下拉菜单：列出 Light Violet 与 Dark Violet，各带三个颜色预览点，当前项打勾；选择后菜单关闭，点外面或按 Esc 关闭并把焦点还给按钮。报告页没有 `data-theme` 的文档按 Light Violet 显示，首次绘制前的内联脚本与本地存储读写失败时都退回 Light Violet。两页里手动选过的主题仍优先于默认。代价：此前没选过主题、一直看深色的人，下次打开会看到浅色。

## Oracle

- 单测：
  - 主题：没有存储时默认 light；存过 dark 时用 dark；读存储抛错时为 light；浏览页的默认预设为 light-violet、强调色 violet。
  - 路由：`#/feature/<id>?finding=<fid>` 解析与序列化往返；空的或缺失的 `finding` 等于没有；其它参数仍丢弃。
  - 左栏分组：每个功能恰在一组一次，组的顺序为 flow、automated、reference、其余按种类名，组内按章节顺序；筛选按编号或名字、不区分大小写。
  - 快速跳转匹配：编号完全相等排第一、编号前缀其次、包含再次；功能先于 finding；超过 50 条时只列 50 条并报出总数。
  - 功能矩阵：每个功能的各级别格子之和等于该功能的 finding 数，全体之和等于 `findings.json` 条数；格子链接带对的 `feature` 与 `priority`。
  - 级别分组：分组小标题的条数之和等于显示的条数，每条 finding 恰在一组。
  - 改掉任一排序或分组规则时至少一个测试变红（先在旧实现上确认新测试红）。
- 构建：`pnpm --filter @excavator/prd-report-page build`（含模板检查）、`test`、`typecheck` 全过。
- 真实语料（go-multirepo，不进仓库）：用新模板重填现有 `report.html` 的原数据块，数据块逐字节相同；在 headless Chrome 里以 1440 与 390 两种宽度、两种主题打开总览、一个功能页、findings 页与覆盖页，控制台没有错误；左栏与功能矩阵各列出每个功能一次；findings 页显示全部 findings 各一次；从快速跳转打开一个 finding 时滚到并高亮它；章节目录项数等于正文 h2 与 h3 数加页面小节数。
