## Why

Core 默认忽略规则里的目录规则（`build/`、`out/`、`target/`、`dist/`、`vendor/`、`obj/`、`coverage/` 等）只按目录名判定。名字相同的源码包会和真正的构建产物一起被排除。

在本地 32 个语料根目录上只读实测（按扫描的实际枚举方式）：
- 真正的源码包只有一处：TomEE examples 的 Java 包 `org.superbiz.ws.out`，3 个文件；仓库里没有别的代码引用它。
- 其余命中都按本意排除：第三方库内的 `dist/`、`build/`、`vendor/`，IDE 配置目录，以及 Go 仓库 `build/` 下的打包文件。

所以这个问题眼下没有造成错误输出。但机制会在没见过的代码库上出错：
- 如果被排除的包被别的 Java 代码引用，调用解析会把调用判成「目标在仓库外」，而实际上只是没读到。
- 按类型注入在判「唯一候选」时假定仓库里的声明都看得见，被排除的包里若有另一个实现，就会连错边。

上一个变更（default-file-patterns）把这个问题列为后续：要分辨构建产物目录与同名源码包，得看文件本身，而选择策略是不读文件系统的纯函数。

## What Changes

- 宿主 skill 的忽略规则预检（`skills/excavator/SKILL.md` 第 0 阶段 6.4）新增一个方向：除了提议新的排除规则，也找回默认目录规则按名字误排的源码包。
  - **依据只有一个**：被排除文件自己的 `package`（或 `namespace`）声明，必须包含该路径上被默认目录规则命中的每一个目录。例如 `src/main/java/org/acme/out/Calculator.java` 声明了 `package org.acme.out;`。
  - **不算依据的**：名字、源码扩展名、文件看起来是手写的。第三方库与生成代码同样带源码扩展名，生成代码也有 `package` 声明，但它们的包路径不包含 `target`、`vendor` 这些命中的目录。
  - **写法**：每个这样的目录提议一条项目取反规则，例如 `!src/main/java/org/acme/out/`。之后照预检原有的流程走：先比较前后两份扫描结果，再写入根 `.excavatorignore`，最后复核。
  - **审查找回的路径**：前后比较时，逐条审查新被选中的路径。找回的文件必须都是该源码包里的文件，否则放弃那条取反规则；不改变任何选择结果的取反规则也放弃。
- 运行时代码不变：选择策略、默认规则、选择摘要都不变，已分析的项目不会因此重算。

## Impact

- Skill 散文：`skills/excavator/SKILL.md` 第 0 阶段 6.4 的第 3、5、8 步。
- 测试：新增契约测试，断言找回规则写在发现候选的第 3 步、审查找回路径写在比较的第 5 步。
- 不涉及：Core、扫描、快照、事实图、MCP。
- 限制：预检只在根 `.excavatorignore` 不存在、存在旧版数据目录规则文件、或用户要求复查时运行。已有根规则文件的项目要用户要求复查才会找回。
