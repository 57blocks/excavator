## Context

第二步（`doc-map-link`）之后，产物里每条功能是 `found`（带复核留下的证据）、`not-found`（带搜过的内容）或 `not-checked`。覆盖报告的前两类已经在里面了，这一步补「有代码没文档」，并让 `excavator-chat` 读这份产物。

动手前在四个验收语料的克隆上跑了 `/excavator` 的 Lazy 模式（只做确定性抽取，不调用模型），量了现有事实能给什么：
- 由脚本抽取的路由只有 JAX-RS 一种。病历系统有 267 个 `endpoint` 节点，maui-app、go-multirepo、sakai 都是 0。Spring、Gin、Struts、MAUI 页面的入口在 Full 模式里是模型推断的边，不是事实。
- `source-manifest.json` 列的是快照里的全部文件，包括 `.jar`、`.nupkg`、`.otf`、`.docx`（病历系统 9490 个条目里有 188 个不是事实图的文件节点，其中 79 个 `.jar`）。事实图的文件节点是 `/excavator` 实际分析过的文件。
- Lazy 模式耗时：病历系统 71 秒，sakai 96 秒。
- 第二步留下的证据落在函数行范围里的比例：go-multirepo 128 / 156，maui-app 15 / 34（多是 XAML 与配置），病历系统 75 / 158。
- 按目录汇总有信息量：go-multirepo 有两个整仓与一个迁移目录没有任何证据，文档写的功能集中在少数几个目录里。

约束：
- build-free：不编译目标项目，不装运行时；
- 零编造：「这里没有证据」是关于缺失的断言，要有完整的分母，桶名只说检查了什么；
- 没有第四态：每个文件、每处证据都落进一个看得见的桶，守恒由脚本核对。

## Goals / Non-Goals

**Goals:**
- `/excavator` 分析过的每个文件落进 `documents`、有证据、没有证据三者之一；每处保留下来的证据落在一个代码文件里，或者单列。
- 每级目录给出子树里的代码文件数、有证据的文件数、证据落在这里的功能。
- 报告与 chat 能回答「某条功能在代码哪里」「哪些代码没有任何功能的证据」，措辞只说检查了什么。

**Non-Goals:**
- 按函数、类或路由算覆盖；
- 判断没有证据的代码是不是一个独立的功能、该不该写文档；
- 把功能写进知识图；
- 第二步的两处软残余（复核窗口只看到类声明的字段；正文只有「见某节」的功能会漏）。

## Decisions

**1. 分母取事实图里的文件节点。**
- 列文件是关于缺失的断言（「没有一处证据落在这里」），需要完整清单。模型列会漏、会编；路由事实只覆盖 JAX-RS；`source-manifest.json` 里有二进制文件。
- 事实图的文件节点与 `/excavator` 其它产物用的是同一套选择规则（排除目录、忽略规则），不在 `doc-map.py` 里另写一份语言与扩展名清单。
- 代价：计数前要有新鲜的事实。Lazy 模式不调用模型，大仓库要几分钟。被 `/excavator` 排除的文件不在分母里；证据落在这种文件里时单列（第 4 条）。

**2. 粒度是文件与目录，不到函数。**
- 第二步每条功能最多列 5 处证据，起点在前。一个功能用到的大部分函数不会是证据。按函数算，文档写了的功能的大部分代码都会落进「没有证据」，这个桶就没有用了。
- 目录（Java、Go、C# 里大致就是包）这一级上，「没有一条功能的证据落在里面」能看出整块的区域：整个仓、整个模块、迁移脚本。
- 代价：按目录汇总时，一个目录里只要有一个文件有证据，这个目录就算有证据，其余的文件仍逐个列在 `files` 里。

**3. 「是不是文档」与 `link` 用同一个判定。**
- `link` 拒收的三类（文档格式、文档目录里、内容与一份已读文档相同）抽成一个函数，`coverage` 用它把文件分进 `documents`。两处不会各说各的。
- 内容相同只查字节数与某份文档相同的文件，其余不读：事实图可能有上万个文件。
- `documents` 不算代码文件：文档永远不会有证据，算进去会让「没有证据」虚高。

**4. 证据路径先规范化再比对；对不上的单列。**
- `link` 记下的是子代理写的路径（核对过在项目里），可能带 `./`。规范化后（`posixpath.normpath`）再与事实图的路径比对。
- 规范化后仍不在任何代码文件里的证据单列：功能序号、文件、行号。常见原因是 `/excavator` 的选择规则排除了那个文件，或证据落在被归为文档的文件里。单列让它看得见，也让守恒成立。

**5. 守恒由脚本核对，不守恒就报错、不写入。**
- 文件数 = 文档数 + 代码文件数；代码文件数 = 有证据 + 没有证据；证据数 = 落在代码文件里的 + 单列的；`.` 这一行等于代码文件的两个计数。
- 事实图读不了也报错（第一行不是 `excavator-knowledge-graph-lines/1` 的头部、节点记录数与头部不符、同一路径两个文件节点）：读到半份事实图会让「没有证据」虚高。
- 只读事实图里需要的字段（头部的 `factsDigest`、节点的 `type` 与 `filePath`），用 Python 标准库逐行读，不依赖 Node 的读取模块：`doc-map.py` 的其它子命令也都只用标准库。

**6. 计数写进同一份产物；`read`、`units`、`link` 把它清回 `null`。**
- 与第二步的第 1 条相同：证据一变，旧的计数就不成立。放在同一份产物里，脚本在重写证据时把它清掉，不会留下与证据不符的计数。
- 计数记下事实图的 `factsDigest` 与 `source-manifest.json` 的 `sourceRevision`。事实重建后摘要不同，chat 据此说明计数已过期。
- 格式名仍是 `excavator-doc-map/1`：只增加字段，现在的读者只有本 skill 与 chat。

**7. skill 一开始就检查事实，缺失或过期时运行 `/excavator --mode=lazy`。**
- 放在读文档之前：补事实不花模型的钱，失败了也还没开始花。
- 写明 `--mode=lazy`：项目的 `config.json` 可能把默认模式设成了 `full`，那会调用模型分析全部文件。
- 补完仍不新鲜（运行失败、项目不支持），照常做前两步，跳过计数，报告写明原因。前两步不依赖事实。
- 没有另设只重算计数的入口：事实新鲜时一次运行就有计数。代价：先跑了 `/excavator-doc-map`、后补事实的用户要再跑一次全流程。

**8. 报告与 chat 的措辞只说检查了什么。**
- 桶名是「没有一条功能的证据落在里面」，不是「没有文档」。每次列出这个桶，后面跟一句固定的话：每条功能最多列 5 处证据，测试不算证据，所以文档写了的功能用到的代码也可能在里面。
- 报告列「没有证据、而父目录有证据的目录」：没有证据的子树只列最上面的一层，不把同一棵子树的每级目录都列一遍。按代码文件数从多到少列前 20 个，并写明一共多少个（病历系统有 1014 个目录）。这个筛选是 skill 里的一条 `jq`，脚本只写全部目录行：怎么展示是报告的事。
- MUST NOT 说「没有文档」「没人用」「可以删」，与 unused-code、hotspots 的报告规则一致。

**9. chat 只读产物，用固定查询。**
- 与改动历史、未使用代码的问题一样，在 `excavator-chat` 里加一节「文档问题」，只读 `doc-map.json`，不整份读入，不从知识图或源码推断哪段代码做哪个功能。
- 问到覆盖时先比对 `coverage.factsDigest` 与当前事实图头部的 `factsDigest`。
- 这一节的契约测试放在本能力的契约测试文件里，与 unused-code 管 chat 里自己那一节的做法相同。

**10. 为什么计数写成脚本而不是交给 skill。**
- AGENTS.md 要求能由 skill 或提示词完成的不写进代码。这里写成脚本，是因为它要对上万个文件下「没有」的断言并核对守恒，产物又是 chat 要读的持久契约。模型做不到完整、稳定。
- 展示（第一级目录、没有证据的最上层目录、排序与条数）留在 skill 的 `jq` 里，不写进脚本。

**11. 语言与前两步相同。**
- 报告用 `$LANGUAGE`，默认英文；路径照原样。
- 脚本、skill 与测试里没有中文字符；测试里的中文输入写成 `\u` 转义。

## Risks / Trade-offs

- [文档写了的功能用到的代码落进「没有证据」] → 固定的话与残余假设写明；这是证据最多 5 处的直接结果，不靠改措辞消除。
- [测试永远没有证据] → 同一句固定的话写明。不按路径猜哪些是测试：那是猜。
- [被 `/excavator` 排除的文件不在分母里] → 证据落在里面时单列；报告给出事实图里的文件数，读者知道分母是什么。
- [`/excavator` 在 headless 运行里没能补上事实] → 前两步照常，`coverage` 为 `null`，报告写明原因。
- [大仓库产物变大：sakai 有 15523 个文件，每个文件一行] → chat 与报告只用 `jq` 查，从不整份读入；与 hotspots 的 `files` 行相同。
- [对代码之后事实又重建了] → 摘要不同，chat 标明过期；报告是在同一次运行里写的，不受影响。

## 验收 oracle（动手前写死）

1. **先验装置**：单测用一个小事实图夹具，造出已知的桶：文档格式的文件、文档目录里的文件、与文档内容相同的文件、`./` 开头的证据路径、不在事实图里的证据、三级目录。断言每个桶的成员与每级目录的计数。再把判定改坏（祖先目录不累加、不规范化路径、不分出文档），确认测试变红。
2. **真实产物独立重算**：四个语料用第二步最后一次运行的产物加上新跑的 Lazy 事实，运行 `coverage`。另写一个不共用代码的脚本，从事实图与产物重算每个文件、每级目录的计数，逐行比对必须完全相等，守恒成立。记下每个语料的计数。
3. **一次完整的真实运行**：maui-app，事先删掉 `.excavator`。skill 必须自己运行 `/excavator --mode=lazy`，最后给出计数。报告要有计数的各项与固定的话，没有中文字符，收尾自检为 0；在报告里查「undocumented」「not documented」「unused」「dead」「safe to delete」，都必须为 0。花费上限 $10。
4. **chat**：maui-app 与病历系统各问 5 个固定问题（某条功能在哪里；哪些功能没找到代码、搜过什么；某个目录里有哪些功能的证据；哪些代码没有文档；一条 `not-found` 功能实现了没有），另在一个没有产物的克隆上问一次。每个回答里的文件、行号、计数与功能都要能在产物里找到（编造为 0），措辞规则逐条核对。花费上限 $5。
5. **全量门**：最后一个代码提交在分离检出里跑全量门。
