## 背景

见 proposal。几项都是检查与识别的精度问题；写作者的提示词只改一句。

## 决定

### D1 建议词表

- 英文表去掉 `must`、`need to`、`needs to`。它们在规则陈述里是描述（密码必须 8 位、需要登录），不是建议。真正的建议仍会撞上 `should`、`recommend`、`fix`、`improve` 等。
- 译文由每次运行从英文表翻译，改英文表即可；已有输出目录的 `ui.json` 里旧译文不追溯修改。
- 代价：「X must be fixed」这类句子仍会被 `fix` 拦住；「X must change」会漏过。接受。

### D2 JavaScript workspace 的应用

- 一个清单目录有 `pnpm-workspace.yaml`，或它的 `package.json` 有 `workspaces`（数组，或带 `packages` 数组的对象）时，它是 workspace 根：它不是应用，它下面最上层的清单目录才是应用。不展开 glob，按目录找：workspace 根下面的清单目录照旧取最上层的那些。
- 只认 JavaScript workspace：本次遇到的就是它；Go、Cargo、Maven 等多模块写法照旧，等遇到再加（记入风险）。
- workspace 根下面没有任何清单目录时，根本身仍是应用，与改动前相同。
- 架构事实表的 `kind` 加 `library`：被其他应用引用的共享代码包。与 `backend` 同层（第 2 层）。应用根目录守恒改为恰好是一个 `frontend`、`backend` 或 `library` 组件；`application` 只出现在这三种组件上。
- 页面与 Markdown 的分层图把 `library` 画在后端那一层。

### D3 引文比较

- 引号里的文字与所引行比较前，两边都解码 HTML 实体（命名实体与数字实体），并把连续空白规整成一个空格。
- 只放宽这两项，大小写照旧严格：大小写不同可能是另一处文字。

### D4 引文提示写出位置

- 引号里的文字不在所引行时，提示照旧，再加一句位置：先在所引文件里找，找不到再在项目文件里找（与 `files` 列表相同的范围），写出第一个出现的 `文件:行号`；都没有时说项目里没有这段文字。
- 只是提示，不改变通过与否，也不改计数口径。

### D5 引号只放原文

- 功能提示词「Labels, numbers and code in the chapter」一段加一句：引号只用来放从源码照抄的文字；你自己的话、译文和概括不加引号。

### D6 标题里的功能编号

- 章节一级标题里，功能编号（`F` 加数字）不算正文数字。别的位置照旧。

### D7 注释行里的入口

- 入口候选的匹配行去掉前导空白后以 `//`、`/*` 或 `*` 开头时跳过。只看行首，不解析多行注释的范围。

## Oracle

- **O1 脚本测试**：每个 D 一组正反例。
  - D1：「需要登录」「must be 8 characters」不再出提示；「should」「建议」照旧出。
  - D2：pnpm workspace、`package.json` 的 `workspaces` 数组与对象两种写法，成员各成一个应用；没有成员时根仍是应用；没有 workspace 声明的项目输出不变（已有的应用列表测试全过）。架构检查接受 `library`，拒绝把应用根写成 `cloud`。
  - D3：`&amp;`、`&#39;`、换行与多空格的引文通过；大小写不同仍出提示。
  - D4：提示里的位置是第一个出现处；所引文件优先；项目里没有时的固定文字。
  - D6：标题 `# F12 名称` 不出数字提示；正文里的 12 照旧。
  - D7：`// @Get(`、` * @Cron(` 不成候选；同一文件真实的装饰器仍是候选；黄金候选测试除了注释行没有变化。
- **O2 提示词合约**：D5 的一句钉在功能提示词里，换回旧文件合约测试变红。
- **O3 真实运行**：同一个私有语料全新全量重跑，记录并与上一次对比：建议提示数、专题的重试与失败数、应用数与系统问题数、引文提示数与其中带位置的比例、未分配候选数、花费与时长。不设门槛，只记录。
- **O4 门**：`openspec validate --all --strict`、`check-refs`、源码零非 ASCII、名字扫描无命中；全量门交 CI。

## 风险

- 其他语言的多模块项目仍只认出一个应用，直到遇到再加。
- 引文提示写出位置后，写作者可能把引文改到那一行，而那一行说的是另一件事；这仍然只是计数，读者看到的是「未核对」。
