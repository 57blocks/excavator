## Context

历史扫描给每个提交分配一个提交号，按仓区分。目录的 `commits` 是它下面各文件提交号的并集，`lastChanged` 是提交者日期，带提交者的时区（`%cI`）。窗口 `--since` 按 UTC 零点切。

## Goals / Non-Goals

**Goals:**
- 每个目录能看出改动落在哪些年。
- 不改脚本，也能查到「很久没动的部分」。

**Non-Goals:**
- 文件级的按年计数，按月或按季度分桶，按作者看趋势。
- 判断代码是否还在用。

## Decisions

**1. 扫描时记下每个提交号的年份，聚合目录时按年分组。**
- 做法：历史扫描为每个提交号记一个年份；目录已经有提交号的并集，按年份分组即可。
- 好处：
  - 各年之和必然等于 `commits`；
  - 同一次提交在一个目录里只算一次；
  - 不同仓的提交不会合并。
- 不多跑 `git log`。

**2. 年份取提交者日期上的年份，不换算成 UTC。**
- 理由：和 `lastChanged` 显示的年份一致。模型会对照两者，例如「最后一次改动在 2016 年」，对应的应是 2016 年最后一个非零项。换算成 UTC 后，跨年前后几个小时的提交会让两者对不上。
- 代价：`--since` 按 UTC 切。窗口起点附近跨年的提交，会计入起点的前一年。例如 `--since 2020-01-01` 时，`2019-12-31T20:00:00-05:00` 的提交在窗口内，却计入 2019 年。
- 变基、cherry-pick 的提交按重新提交的日期计，这一条写进残余假设。

**3. 只做目录级，每年都有一项。**
- 依据：用只读 git 粗测（没跟踪改名，只算 HEAD 上的文件）。

  | | dataverse | sakai |
  |---|---|---|
  | 年份 | 2013–2026（14 年） | 2005–2026（22 年） |
  | 目录行 × 年数 | 8,246 | 143,550 |
  | 文件有提交的（文件，年）组合 | 8,973 | 68,431 |

- 每年都写，0 也写：读一行就能看出走势，不需要约定「没写的年份是 0」。sakai 估计增加约 1.7 MB，当前产物约 10.5 MB。
- 年份范围取整个产物的最早到最晚年份，不取各目录自己的：所有目录的键相同，按同一年给目录排序时不会缺项。
- 文件级不做：问到文件时，`commits` 和 `lastChanged` 已能回答「最近还改吗」。代价是 chat 答不了「这个文件每年改几次」，要说明没有这项数据。

**4. 冷代码只在 skill 里查。**
- 文件按 `lastChanged` 的前四位（年份）分组计数。
- 文件和目录按 `lastChanged` 的文本排序，即按各提交者时区里记录的时间排序，与年份的定义一致。
- 代价：不同时区、相差不到一天的两次改动，排序可能与绝对时间相反；按年计数不受影响。
- 有历史但计入 0 次提交的文件，用固定的话只给个数，产物不记录原因。
- 最初的设计是同一年内按路径排，以避开时区问题。真实运行时，用户要的是最早改的几个文件，模型就自己写了按时间排序的查询，挑着列，结果有错。所以改成现在的排法，见验收记录。

**5. 「最近两年」取产物里最晚的两个年份。**
- 最后一年通常不完整，只到 `.` 行的 `lastChanged` 为止；第一年从窗口起点或最早可见的提交开始。
- skill 写明是哪两年，并说明最后一年截至哪天。

**6. 自检 grep 加冷代码用词。**
- 加入：`dead`、`unused`、`no longer used`、`obsolete`、`abandoned`、`safe to delete/remove`、`死代码`、`废弃`、`无用`、`不再使用`。
- 自检把每个命中都当成要改写的句子，命中文件路径的话永远清不到 0 行。所以先查了三份语料的全部路径：上面这些词一次也没出现；`legacy`、`stale` 出现在 4 个路径里，因此不收这两个词。

## Oracle

- **单测**：覆盖规格里的每个场景，包括跨年时区和窗口内没有提交。
- **独立 oracle**：
  - 用 `oracle.py --commits-out` 拿到每个当前文件的提交 sha，它的改名归属是另写的；
  - 用 `git log --format='%H %cI'` 拿到每个 sha 的提交者日期；
  - 另写一段 Python，只按规格算出每个目录的 `commitsByYear`；多仓按（成员目录，sha）区分提交；
  - 与产物逐目录逐年比对，并核对各年之和等于 `commits`；
  - 语料：dataverse、sakai、openmrs-workspace（多仓）；
  - 先手动改产物里的一个数，确认比对能报出差异。
- **耗时与大小**：sakai 全历史，记录前后的耗时与产物大小。增加的耗时不超过 5 秒。
- **真实模型**：Sonnet，headless，dataverse。
  - `/excavator-hotspots` 跑一次：汇报含每年的提交数、最近两年的目录、按最后改动年份的文件数与目录；数字与产物一致；自检 0 行；不说没在用、可删除。
  - chat 问两次：
    - 「`src/main/java/edu/harvard/iq/dataverse/api` 这几年改得多吗」：数字来自 `commitsByYear`，说明最后一年不完整；
    - 「哪些代码很久没人改了」：按年份回答，不说没在用。
