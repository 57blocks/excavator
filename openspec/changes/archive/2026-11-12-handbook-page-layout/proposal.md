## Why

另外，用户指出功能页的小标题用的是口语（「谁可以使用」「在哪里找到」），手册应当用正式的文档用词。

版式改完后，用户指出控件仍然粗糙：发现页与字典页的筛选是浏览器原生下拉框，三个筛选器错位成两行；统计数字是一整段「发现：70。陈述：74。……」的长句。用户允许页面用 Tailwind 与 UI 组件库，也允许输出多个文件，条件是双击 HTML 就能打开，不需要 Node 或任何服务。


用一次真实运行的页面（44 个已核实功能）在常见窗口下检查，有三处读不下去：

- **侧栏**：上方 15 个页面链接与底部图例固定占位，功能列表只剩可滚动的一条。1024×768 下它只有 26 像素高，72 个功能几乎看不到。
- **表格列宽**：源码位置是长串、在表格里不断行，把「发现」一列挤到每行一两个字；「渠道」这类短值列把两个字拆成两行。
- **源码位置**：技术视角下每个单元的源码位置是一段段纯文本，「界面 > 字段 > 规则：文件，第几行；文件，第几行……」，一个功能有几屏长，没有分组和代码样式，也不能收起。

## What Changes

- **侧栏整体滚动**：页面链接、应用与功能列表、图例放在同一个滚动区里，功能列表不再被挤成一条。顶栏仍固定。
- **表格列宽**：长文字列有最小宽度；文件路径在 `/` 处可断行；短值列（渠道、优先级、状态名等）不断行。手机宽度仍没有横向滚动。
- **源码位置结构化**：按项列出，项的路径（如「界面 › 字段 › 规则」）与主张分开显示；每处引用写成等宽的 `文件:行` 小块，同一文件的多处合在一起；整节默认收起，展开后才列出。发现表里的源码位置一列用同样的小块。
- **正式的标题用词**：固定文字表里口语化的标题与标签改成参考文档的正式写法，如「谁可以使用」→「适用角色」（英文 Who can use it → Roles）、「在哪里找到」→「入口路径」（Where to find it → Navigation path）、「读者如何到达」→「访问方式」（How readers get to it → Access）等约 15 处，只改值不改键与占位符；翻译固定文字的提示加一句：标题与标签保持正式文档的语气，不写成问句。
- **控件与视觉**：筛选下拉改用带样式的组件（Radix UI 原语 + Tailwind，键盘与读屏可用）；筛选器排成一行工具栏，右侧是「显示 n / m」；统计数字改成小卡片或键值网格；表格、标签、徽标统一一套颜色与间距令牌，配色参照参考手册（青绿主色、浅灰底、P0/P1/P2 三档颜色）。输出仍是一个 HTML 文件。
- 页面数据、手册 Markdown 的结构都不变；版式只改页面模板的组件与样式。

**不做：** 改页面数据的格式或手册文字；新增页面或导航项；产品视角的内容。
