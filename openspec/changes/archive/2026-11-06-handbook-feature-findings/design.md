## Context

手册的单元现在有两种：功能条目与系统概览。`lib/unit.mjs` 把两者在形状、项、主张、修剪、检查与状态位置上的差异收在一处，第 5、6 阶段的命令（`slices`、`verdicts`、`trace`、`trace-verdicts`、`mark`）都经它工作，核对与追查的规则只写一次。

部分由 `lib/sections.mjs` 的依赖表决定，阶段文字按部分分文件，只在选中时读。

## Goals / Non-Goals

**Goals**：
- 每个功能的缺陷，带引文；
- 与条目同样的检查、核对与追查；
- 两个视图与页面都显示；
- 覆盖一节列出删掉的发现。

**Non-Goals**：
- 系统级发现；
- 排级；
- 对策与重构建议；
- 改动条目、概览的写法与检查。

## Decisions

### D1 部分与阶段

- `lib/sections.mjs` 加一行 `findings`，依赖 `stages/map.md`，文件 `sections/findings.md`，排在 `data` 之后。默认的部分包括它。
- `sections/findings.md` 是第 4c 阶段：
  - 列出要写发现的功能：`$SELECTED`，没给 `--features` 时为地图的全部功能；
  - 记录派发、派发子代理、逐个检查；
  - 第二次尝试、失败与续跑的规则照第 4 阶段。
- 发现单元不依赖条目，所以与条目在同一轮里写。

### D2 单元

- **id**：`<功能 id>.findings`。地图的 id 不许有点（`ID_PATTERN`），所以它不会与功能或 `overview` 冲突。每条命令都用这个 id：`mark`、`check-findings`、`try-findings`、`slices`、`verdicts`、`trace`、`trace-verdicts`。
- **文件**：`entries/<功能 id>.findings.json`。
- **状态**：`state.json` 的 `findings` 键，按功能 id 存。没有这个键等于全部 `planned`、没有尝试，所以旧的输出目录不用迁移。状态与功能相同：`planned`、`dispatched`、`checked`、`failed`、`confirmed`、`verified`，最多尝试 2 次。
- **`unit.mjs`**：加第三种单元，形状、项、主张、修剪与检查各有自己的实现。其余命令不改规则。
- **一条也没有**：`check-findings` 直接记为 `verified`，0 项。没有要证明的东西，第 5、6 阶段就不列出它。
- **全部被删**：核对或追查删掉了全部发现时，单元记为 `verified`、0 条，不记为 `failed`。没有证明的缺陷不是失败，删掉的发现照常进覆盖一节。功能条目在这种情况下仍是 `failed`，规则不变。

### D3 文件形状

```json
{
  "format": "excavator-product-handbook-findings/1",
  "id": "F3.findings",
  "findings": [
    {"category": "authorization", "text": "<缺陷与发生的情况>", "evidence": [{"file": "...", "passage": "..."}]}
  ],
  "unknowns": [{"item": "...", "searched": "..."}]
}
```

- **`category` 是固定枚举**，按根因分：

  | 值 | 含义 |
  |---|---|
  | `authorization` | 缺少归属、指派或角色校验 |
  | `error-handling` | 错误被吞掉，或失败时返回成功 |
  | `notification` | 通知发不出、发错人或内容不对 |
  | `consistency` | 事务、并发、重复提交或重放带来的数据不一致 |
  | `calculation` | 计算或统计口径有误 |
  | `hard-coded` | 写死的值、占位功能、走不到的代码 |
  | `contract` | 调用方与被调方对不上：路径、方法、参数、字段 |
  | `security` | 机密、注入、传输与基础设施的安全问题 |
  | `display` | 页面交互与展示的缺陷 |
  | `time` | 日期、时区与日历规则的缺陷 |
  | `other` | 不属于以上任何一类 |

  显示名走 `ui-strings.json`。
- **核对后的文件**可以一条发现都不剩。

### D4 检查

- 条目的全部检查照样做：
  - 引文在文件里恰好出现一次，文件是项目源码；
  - 数字出现在本条的引文里；
  - 禁词：读者可见的文字里没有代码形状的词；
  - 运行语言的检查。
- 读者可见的文字是 `text`、`unknowns` 的两个字段。
- **建议词检查**：`text` 里不许有 `ui-strings.json` 键 `findings.adviceWords` 列出的词。
  - 这个键的值是逗号分隔的词表，翻译固定文字时一起翻译。
  - 英文按整词、不分大小写匹配；不以 ASCII 字母书写的语言按子串匹配。
  - 违反时写出那个词。

### D5 子代理的提示

`sections/findings.md` 里的提示，读与写的界限照条目子代理：
- 从种子文件出发，最多再开 20 个文件，排除同样的目录；
- 不读 `.excavator` 与生成的文档；
- 只写自己的文件。

内容规则：
- **什么算发现**：代码今天会表现出来的缺陷。例如：
  - 同一件事两处做法不同；
  - 一侧有校验、另一侧没有；
  - 失败时仍返回成功；
  - 调用方与被调方对不上；
  - 写死的值。

  不写风格、可读性与「可能」的问题。
- **陈述**写缺陷本身与它在什么情况下发生，读者能据此复现。不写怎么改，不评价。
- **引文要能单独证明它**：
  - 缺少校验的，引执行写入或动作的整段，让读者看到其中没有校验；
  - 两处不一致的，两处都引。
- **否定句**（没有校验、从不发送）写之前搜整个项目，确认别处（中间件、拦截器、监听器）没有做。搜不清楚的写进 `unknowns`。
- 没有发现时写空列表，不凑数。
- 提示与条目子代理一样，要求先跑 `try-findings` 改到通过。

### D6 核对与追查

- 发现单元在第 5、6 阶段与功能、概览同列：
  - 第 5 阶段第 1 步多一条 jq，列出 `checked` 的发现单元；
  - 第 6 阶段第 1 步多一条 jq，列出 `confirmed` 的发现单元。
- 核对者、改写者、追查者的提示与 agent 不变。改写者用 `try-findings`，关于地图角色的那条规则不适用。
- 主张：`Finding > <类别的显示名> > <陈述>`。
- 「部分」规则第 4 条加上：发现单元只在选了 `findings` 时核对与追查。

### D7 呈现

**手册**，两个视图：
- 在实体各节之后、覆盖之前加「发现」一章：
  - 一行按类别的计数；
  - 按类别分组，每条写功能名与陈述；
  - 技术视图另写文件与行号。
- 只写 `verified` 的发现单元。
- `assemble` 与 `page` 写之前重新检查已核实的发现单元，与条目一样：文件在核实后改过或不再通过检查时，打印一行并退出 1。
- 功能的一节末尾列出它的发现。
- 覆盖一节：
  - 未核实完的发现单元；
  - 核对与追查删掉的发现，各带理由，与条目的删除并列。

**页面**：
- 格式升到 `/9`（系统名字的变更先合并，用了 `/8`），加 `findings`；
- `#/findings` 路由与侧栏链接；
- 可按类别筛选；
- 功能页列出它的发现；
- 两个视图都有。

### D8 规则的措辞

- `SKILL.md` 开头的规则 1 加一句：手册里只有「发现」一章陈述缺陷，其余部分只陈述现状；任何部分都不写怎么改。
- 条目与概览子代理的提示不变：它们仍然不写缺陷。

### D9 范围词的追查

第一次真实运行，F8 留下了两条把范围说大的发现，都过了两名核对者和两名追查者：
- 「所有超过 40 小时的请假都会显示这个名字」：抄送节点只在有取消申请，或者状态是已批准、已完成时才出现；
- 「之后从未赋值」：那个变量在比较之后被赋值。

同一件事的 F1 版本被核对者删了，所以两次判断不一致。核对者和追查者的提示里本来就有「所有、从不要找收窄它的代码」，但他们拿代码自己的条件造例子（「一条 41 小时的请假」），或者把主张往宽松处读。再加一段散文规则拦不住，所以做成脚本能查的结构字段：
- `ui-strings.json` 加 `md.findings.scopeWords`：逗号分隔的范围词，与建议词一起翻译。匹配规则与建议词相同：只含 ASCII 的按整词、忽略大小写；含其它文字的按子串。
- `trace` 写发现单元的追查文件时，每项另带 `scopeWords`：这条发现的陈述里出现的词，按表的顺序，不重复。只看陈述，不看主张前面的类别名。一个词也没有时不写这个键。
- 追查者对带 `scopeWords` 的项判 `holds` 时，必须另写 `scope`：每个词一条 `{ word, case, result }`。
  - `case`：用主张自己的话造出的、落在这个词范围内、离代码条件尽量远的一个情形；
  - `result`：代码对这个情形做了什么。

  `trace-verdicts` 拒绝缺词、多出的词、重复的词，以及空的或多行的 `case`、`result`。判 `contradicted` 时不要求。
- 发现子代理的提示加一句：陈述里写了范围词，就要引用决定它何时发生的那几行；证明不了这个范围，就不写这个词。
- 只用于发现单元。条目与概览的追查文件不带这个键，追查者的规则对它们不变；它们已经各自验收过，扩到条目留作以后。

## Risks / Trade-offs

- **否定句难以由引文证明**，核对者多判 `unverified`，改写后仍不能证明就删。宁缺勿编：留下的发现会少。验收照实记录各环节删了多少。
- **花费**：每个功能多一个子代理、两名核对者与两名追查者。`--sections` 可以只跑发现，或者不跑。
- **范围词表**同样只认表里的词。它逼追查者为每个词造一个反例，不保证反例造得对，所以抽查仍看范围。
- **建议词表**只拦得住表里的词，模型换个说法就绕过去了。核对者不判断建议，所以抽查专门看这一条。

## Oracles

- **O1 脚本**：新夹具，单元测试覆盖：
  - 形状、类别枚举、单元 id 的解析；
  - `state.json` 没有 `findings` 键时为 `planned`；
  - 空发现直接 `verified`；
  - 引文、数字、禁词、建议词各一个反例；
  - `slices`、`verdicts`、`trace`、`trace-verdicts` 对发现单元走通，删除的项记录在案。

  变异，各至少一条测试变红：
  - 去掉建议词检查；
  - 类别不在枚举里也放行；
  - 空发现不记为 `verified`。
- **O2 呈现**：
  - 两个视图都有「发现」一章；技术视图有文件与行号，产品视图没有；
  - 只写 `verified` 的；
  - 计数与清单长度一致；
  - 功能一节与功能页列出自己的发现；
  - 覆盖一节列出删掉的发现。

  变异：产品视图写出路径，至少一条变红。
- **O3 真实运行**（go-multirepo，Sonnet 是测量条件）：
  - 在第 3c 片输出的副本上以 `--sections findings --features <若干功能> --views technical` 续跑。先跑 1 个功能标定花费，再跑其余的。
  - 记录：花费、每个单元写了几条、核对删了几条、追查删了几条、留下几条。
  - 地图与已有条目逐字节不变。
  - **验收者独立抽查每一条留下的发现**，不看实现。判断三件事：
    - 缺陷是否真实存在；
    - 类别是否对；
    - 陈述里有没有建议。

    这一条的线是零编造：抽查发现一条不实，就先修机制再交付。删掉的发现抽 10 条，看是否误删。
- **O4**：受影响测试、`check-refs`、`openspec validate --all --strict` 本地过；全量门在分离检出里跑；源码零非 ASCII 字符；名字扫描无命中。
