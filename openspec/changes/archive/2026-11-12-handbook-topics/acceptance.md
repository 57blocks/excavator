## 实现中的决定

- 通道 id 是领域 id（没有通过检查的领域文件时用区域 id），另加 `repeated`；`mark` 用 `topics:<通道>`。状态是 `state.topics[<通道>]`，各自记尝试次数、事实摘要与删掉的行。
- 部分文件是 `{schema, lane, rows}`，行 id 是 `<通道>#<n>`；一个通道可以写零行，零行的通道不需要评判。
- `check-topics` 不带 `--lane` 时检查全部通道并合并成 `entries/topics.json`；一个通道两次失败后留在失败，其余照常合并。手册与页面读部分文件，合并文件只是记录。
- 领域通道的事实后面附上其它领域的 `domain:<id>` 行，让数据行能写出提供方；这些行不能被引用。
- 数字检查只读引用项的文字，去掉 P0–P2 的级别字样。
- 一个主题的通道没有完成时写「通道没有完成」；只有完成的通道才写「所读的 N 个已核实条目都没有提到这些」。
- 页面只有表；领域之间的数据的图只在 `handbook.md` 里，页面没有画图的组件。
- 部署检查的 agent 清单升到 17 个。

### 修正与重放

- 评判提示加一条：重复问题的机制每一部分都要对每一组成立，且保留每组的条件。
- 在同一批判定文件上重放两名评判者（一轮，事先定好）：两名都删掉那 2 行，理由与验收者相同；其余 5 行两名都保留。重放后保留的 5 行，验收者都判 TRUE。
- 第一次必然失败的三个原因一并修了：`repeated` 通道列出应用名（概览已核实时用系统里的名字），通道提示写明 `cites` 放在列外、规则写成系统要求或拒绝什么。这三处没有再做一次真实运行验证，留到全量运行时看第一次检查的通过率。
- 应用名的对应加了两条测试（有名字时写名字、没有时写目录）；去掉名字的变异让 1 条变红。

### 已知限制

- **主题只和条目一样全。** 这一轮只有 2 个功能已核实，表很薄；日历与时区没有行。
- **领域之间的数据只从使用方看。**
- **应用名与目录的对应**在判定文件里只有目录，验收者凭常识对上；手册技术视图的依据列写出文件，可以回查。
