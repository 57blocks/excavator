## Context

第一步（`doc-map-read`）的产物里，每条功能有文档、编号、标题、核对过的引文和行号。这一步给每条功能找代码，结果是第三步覆盖报告的输入。

约束：
- build-free：不编译目标项目，不装运行时，不要求先跑 `/excavator` 建图；
- 零编造：模型写的位置要能由脚本核对；核对不了的（这段代码是不是在做这个功能）要写进残余假设，并在验收里抽查；
- 项目可能很大（几十万行 Java），也可能是多个仓库放在一个目录里。

## Goals / Non-Goals

**Goals:**
- 每条功能落进 `found`、`not-found`、`not-checked` 之一，计数之和等于功能数。
- 每处证据是项目里一个真实存在的代码文件，以及其中只出现一次的一段代码；行号由脚本算。
- `not-found` 带着搜过的内容，读者可以照着重搜。

**Non-Goals:**
- 判断功能「实现得对不对、全不全」。
- 有代码没文档、覆盖报告、chat 读产物。
- 代码变了之后只重做变了的部分。

## Decisions

**1. 对到代码仍是 `/excavator-doc-map` 的一步，结果写进同一份产物。**
- 功能清单一变，旧的对应就失效。放在同一份产物里，重新 `units` 时脚本把对应清回 `null`，不会留下指向旧序号的对应。
- 另起一份产物要额外判断它和功能清单是否同步；另起一个 skill，用户要记两条命令的先后。
- 格式名仍是 `excavator-doc-map/1`：只增加字段，第一步的字段含义不变，现在也没有别的读者。
- 代价：每次运行都重新列功能、重新对代码，没有缓存。

**2. 证据是「文件 + 照抄的一段代码」，行号由脚本算，代码段在文件里必须只出现一次。**
- 模型最容易写错的是数字。和引文一样，让模型抄文字、由脚本定位置。
- 要求只出现一次，位置才唯一；`return null;`、`}` 这类到处都有的行当不了证据，模型要改抄方法、类、路由或页面的声明。
- 比对用第一步的统一处理（空白、弯引号等），不做模糊匹配：放宽匹配会把「找不到」变成「找到一段差不多的」。
- 文件不是 UTF-8 时按 Latin-1 解码：老项目常有 ISO-8859-1 的源码，Latin-1 不会解码失败；非 ASCII 字符抄不对时，改抄一段只有 ASCII 的代码。
- 不另设最短长度：只出现一次已经排除了没有区分度的短代码。

**3. 哪些文件不能当证据，由脚本按规则拒绝。**
- 路径是模型写的，是不可信输入：解析符号链接后必须在项目目录里，是普通文件。
- `.git`、`.excavator`（包括转出的文本）、文档目录里的文件不算。
- 文档格式的扩展名不算：`.md`、`.markdown`、`.txt`、`.rst`、`.adoc`、`.docx`、`.odt`、`.pdf`、`.doc`。`.html` 不在其中：很多项目的页面模板就是 `.html`。
- 内容与任何一份已读文档相同的文件不算：文档目录在项目外、项目里又放着同一份文档时（比如 HTML 规格），前几条拦不住它。
- 测试、示例数据、生成的文件、第三方库没法按规则可靠识别，写在子代理的规则里，并在抽查中看。

**4. 状态三选一，`not-found` 必须列出搜过的内容。**
- `found` 至少一处证据；`not-found` 没有证据，`searched` 非空；清单里没有的功能由脚本记为 `not-checked`。
- 「没找到」只说明列出的搜索没找到，不说明系统没有这个功能，写进残余假设。报告用「没找到代码」，不用「未实现」「缺失」。
- `searched` 只写搜索本身，不写结论：maui-app 与 sakai 的运行里子代理在里面写了「这项设计没有实现」一类的话，它会原样进报告的表格行，而自检不查表格行。
- 子代理写 `found` 时不写 `searched`，skill 合并各批时补成空数组；脚本仍要求每条都有 `searched`。maui-app 第一轮里子代理在 `found` 上漏写了它，多出一轮只为补空数组的改正。

**5. 全部通过才写入；改不对的条目删掉，那条功能记为 `not-checked`。**
- 与 `units` 相同：部分写入会让一部分结果悄悄消失；一次报出全部问题，一次改完。
- 改不对的条目删掉后，那条功能落在 `not-checked`，看得见，而不是编一个状态。
- skill 里写明：MUST NOT 为了通过而写文件里没有的代码；`found` 的证据全被删掉时，要重新搜索，不能直接改成 `not-found`，除非重新搜索后确实没找到并列出搜过的内容。

**6. 按功能分批；每条功能附上文档文本里描述它的行范围。**
- 功能按记录的顺序分批，每批不超过 10 条。同一份文档的功能在记录里是连续的，同一批的功能大多出自同一份文档，子代理在代码里找过的地方可以复用。
- 行范围由 skill 里的 `jq` 算：从这条功能的 `line` 到同一份文档里下一条功能的前一行，最后一条到文档末尾。子代理据此读到这条功能的完整描述，而不是只看标题。
- 每批条数是成本与上下文的权衡。先在 maui-app 上试跑标定；若单批上下文过大或轮数过多，调整条数并在验收记录里写明。
- 子代理用 Grep、Glob、Read 搜代码，不用知识图或 MCP 工具：不要求先跑 `/excavator`。代价：大仓库里搜索更慢，也拿不到调用关系。

**7. 每处证据由第二个子代理在干净上下文里复核，判定不是在做这条功能的去掉。**
- 脚本核对得了「这段代码在这个文件里」，核对不了「这段代码在做这个功能」。真文字、错主体的错归属，正则或文本检查抓不到。
- 原定先不复核，按验收结果再定：抽查发现错归属就加复核。maui-app 第一轮验收的 11 条 `found` 里有 1 条错归属：一条讲发布流程的功能被对到一段守卫代码，这段代码在功能的文本里被提到，文本也写明它与这条功能是两回事。按原定条件加复核，并在第 4 步子代理的规则里加一句：文本只是提到、或写明是两回事的代码不算。
- 复核子代理只拿到功能的序号、标题、文本行范围与每处证据的文件和行号，不拿第 4 步子代理写的任何内容（理由、搜索、抄的代码段）。它只读这些行与证据所在行附近的代码（从前 30 行起共 150 行），不搜索、不读别的文件。上下文干净，才不会沿用前一个子代理的判断。
- 判定只有两种：`does`（在做这条功能或其中一部分）与 `not`（在做别的事、文本只是提到它或写明是两回事、读到的内容不足以判断）。拿不准算 `not`：宁可少一处证据，也不留一处错的。
- 复核只判断代码在做哪个功能，不判断做得对不对：细节与文本不同的代码仍是 `does`。go-multirepo 的验收里，复核以「病假归到了与文档表格不同的审批组」为由去掉了审批路由函数，这与 Non-Goals 里的「不判断实现得对不对、全不全」相违，于是在提示词里写明。
- 只留下判定为 `does` 的证据。证据全被去掉的功能记为 `not-checked`，不再重搜：重搜要再走一轮对到代码与复核；记为 `not-checked` 在报告里看得见。
- 结果先写成 `.excavator/doc-map/checks.json`：每处证据一行（功能序号、文件、行号、判定、原因），子代理漏掉的或判定值不对的记为 `none`，不留下。再由产物与 `checks.json` 用 `jq` 重写对应清单，运行一次 `link`。留下的证据在第 4 步都已通过核对，这一次应当直接通过，行号不变。
- 复核是 skill 的一步，脚本与产物格式不变：判定是模型的事，`jq` 只做按判定过滤与计数。
- 代价：多一轮子代理，花费按每处证据读一段代码计；判定为 `not` 的正确证据会被去掉，召回下降。验收时逐条看去掉的证据，照实记去错的条数。

**8. 记下代码基线。**
- 项目是 Git 仓库时记 `git rev-parse HEAD`，否则 `null`。读者据此知道证据对应的是哪个版本的代码。
- 不记工作区是否有未提交的修改：判断要跑 `git status`，它会刷新索引、写仓库，这一步只读代码。写进残余假设。

**9. 语言与第一步相同。**
- 报告用 `$LANGUAGE`，默认英文；代码段与引文照原文。
- 脚本、skill 与测试里没有中文字符；测试里的中文输入写成 `\u` 转义。

**10. 引文在文档里只出现一次，行范围才落在功能自己的文字上。**
- 第 6 条的行范围从功能的 `line` 起，而第一步的 `line` 是引文第一次出现的行。病历系统的验收发现两种落错：
  - 一份 `.docx` 用例文档开头有目录，11 个用例的引文只写了标题，标题先出现在目录里，`line` 全落在目录上；其中 10 条的行范围只有目录里的一行，子代理只拿到了标题。
  - sakai 的一份规格里几个角色的小节逐字相同，后几个角色的功能 `line` 都落在第一个角色的小节上（第一步验收记下了这件事，用 `occurrences` 标出次数；行范围依赖 `line` 之后它才成了问题）。
- 改为 `units` 拒收在文档里出现不止一次的引文，报出次数。子代理把引文从标题延续到功能自己的文字，直到只出现一次；小节与别的功能逐字相同时，延续到这一节之后的一行。`line` 因此就是功能自己的位置；`occurrences` 恒为 1，从产物里去掉。产物还没有别的读者，格式名不变。
- 不按功能的先后推断位置：目录在所有功能之前，取上一条功能之后第一次出现处仍会落在目录上。唯一性由脚本判定，不必认出目录。
- 代价：列功能时多几轮按报错改；逐字相同的小节，引文会多出下一节的第一行。

## Risks / Trade-offs

- [错归属：真代码、错功能] → 子代理规则要求读过代码、名字或逻辑对得上；每处证据经干净上下文复核（第 7 条）；验收分层抽查。
- [复核去掉了对的证据] → 去掉的证据与原因列在报告里，读者看得见；验收逐条看，照实记。
- [`not-found` 实际有代码：搜索没覆盖到] → `searched` 让读者能重搜；验收时对 `not-found` 逐条重搜，照实记漏判。
- [大仓库成本高] → 先在小语料上标定每批条数与花费，再跑大语料；每次运行带 `--max-budget-usd`。
- [证据落在测试或第三方代码里] → 规则里排除；抽查时看。脚本只按扩展名和目录排除文档，不猜测试目录。

## Oracle

动手前写定：

- **单测**（`link`）：
  - 规格里的每个场景；
  - 路径：绝对路径、`..` 越出项目、指向项目外的符号链接、目录、`.git` 与 `.excavator` 下的文件、文档目录里的文件、文档扩展名、与已读文档内容相同的文件；
  - 代码段：恰好一次（行号对、跨行的代码段行号取起始行、行中间开始的代码段）、零次、多次（报出次数）、Latin-1 文件、统一处理后才对上；
  - 状态：`found` 无证据、`not-found` 有证据、`searched` 为空、未知状态、未知键、序号越界、序号重复；
  - 漏掉的功能记为 `not-checked`，三种计数之和；
  - 有一条不通过时全部报出、产物不变；
  - 基线：Git 夹具记提交号，非 Git 为 `null`；
  - `read`、`units` 清回 `null`。
- **契约测试**（skill）：
  - 分批命令在一份夹具产物上跑出正确的批次与行范围（最后一条到文档末尾，跨文档不串）；
  - 合并命令按批次顺序合并；
  - 报告查询在一份带对应的夹具产物上跑出预期的行；
  - 复核：分批命令只列 `found` 的功能与每处证据的文件和行号；合并命令把漏判、判定值不对的记为 `none`；重写对应清单只留 `does` 的证据，证据全被去掉的功能落到 `not-checked`，`not-found` 原样保留；
  - 固定写法：不说「已实现」「未实现」，自检能报出这些词；
  - 源码零中文字符。
  - 每条关键规则做变异：删掉或改坏后测试必须变红。
- **引文只出现一次**（第 10 条，验收中加入）：
  - 单测：只写标题、标题也在目录里的引文被报出并写出次数；逐字相同的小节被报出；延续之后通过，`line` 落在功能自己的标题上；变异（去掉这条检查）必须变红；
  - 病历系统修复后重跑全量，精度抽查用重跑的结果；
  - sakai 只重跑列功能（第 1 到 3 步），确认逐字相同小节的功能各自落在自己的位置。
- **先验装置**：在一份真实运行得出的对应清单里，人为改坏几处证据（改一个字的代码、换成出现多次的代码、换成 README、换成项目外路径），确认 `link` 全部报出。
- **真实模型运行**（Sonnet，headless，依次运行，不并行）：
  - 项目目录是四个代码仓库的 APFS 克隆，文档目录用第一步验收时的副本；
  - 先跑 maui-app 标定花费与每批条数，再跑 go-multirepo、sakai、病历系统；
  - 每份文档副本里加一份「陷阱文档」，描述一个这些项目肯定没有的功能，它必须是 `not-found`。
- **零编造（精度）**：
  - 对复核之后仍是 `found` 的对应，我读证据处的代码，判断它是否在做这条功能。错归属必须为 0。
  - maui-app、go-multirepo 抽查全部 `found`；sakai 与病历系统按文档分层，每层至少 5 条，合计每个语料至少 20 条。
  - 每条至少看第一处证据；另抽出带 3 处以上证据的功能，看全部证据。
- **漏判（召回，软指标）**：
  - 对每条 `not-found` 用它的关键词重搜，找到对得上的代码就记为漏判，照实记；
  - 逐条看复核去掉的证据，记下去错的条数。
- **花费**：每个语料记花费、轮数、时长与三种状态的计数。
