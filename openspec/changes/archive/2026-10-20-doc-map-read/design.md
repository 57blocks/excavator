## Context

功能文档常在仓库外，格式五花八门。这一步只回答一个问题：这些文档写了哪些功能，每一条出自文档的哪里。后两步（对到代码、覆盖报告）都以这份功能清单为输入，所以清单里的每一条都要能核对：给出的原文确实在那份文档里。

本机与运行镜像能用的工具不一样：
- 开发机（macOS）有 `textutil`，Homebrew 装了 `pdftotext` 和 `pandoc`；
- 运行镜像（`deploy/Dockerfile`，Debian slim）只有 `git` 和 `python3`。

## Goals / Non-Goals

**Goals:**
- 文档目录里的每个文件都有一个看得见的状态，没有被悄悄跳过的文件。
- 每条功能带一段核对过的原文和位置（行，PDF 再加页）。
- `.md`、`.html`、`.docx`、`.odt` 在 macOS 和 Linux 上转出同样的文本。

**Non-Goals:**
- 把功能对到代码，覆盖报告，chat 读这份产物。
- `.pptx`、`.xlsx`、`.rtf`，图片与扫描件的文字识别。
- 核对模型写的标题是否贴切，核对一段文字算不算功能。

## Decisions

**1. 转文本与核对引文写成脚本，列功能交给模型。**
- 先说明为什么 skill / prompt 不够：
  - 每个文件都要落进一个状态，而这要完整列出目录、逐个判断，模型做的话漏了也看不出来；
  - 引文要和一份不是模型写的文本比对。让模型用 Read 工具读 PDF，它拿到的是页面图像，再由它抄成文字，那么被核对的文本本身就是模型写的，核对就成了自己对自己。
- 哪一段算一个功能、标题怎么写，是判断，留给模型。
- 代价：多一个脚本和它的测试。

**2. 用 Python 标准库写，不用 Node。**
- 要用的都在 Python 标准库里：读压缩包（`zipfile`）、解析 XML、完整的 HTML 字符实体表（`html.parser`）、按声明的字符集解码（`codecs`）。
- Node 没有内置的压缩包读取，也没有完整的实体表，要么手写，要么加依赖。
- 运行镜像里有 `python3`，仓库里已有 Python 写的 skill 脚本，vitest 里也有调用 `python3` 的测试。
- 代价：这个 skill 的脚本和仓库里新近的 `.mjs` 脚本不是同一种语言。

**3. 只有 PDF 和旧版 Word 用外部工具，其余自己转。**
- `.docx`、`.odt` 是压缩包里的 XML，`.html` 是标签，自己转，两个系统上结果相同。
- PDF 的文字要解析内容流和字体编码，标准库做不了，用 `pdftotext`（poppler）。旧版 `.doc` 是二进制格式，用 macOS 自带的 `textutil`，没有时用 `antiword`。
- 没有工具时状态是 `no-converter`，原因里写工具名，汇报里说缺什么。不在这一步往镜像里加工具：没法在这里验证镜像构建。
- 外部工具设 300 秒超时，超时落 `failed`。
- 代价：在运行镜像里，PDF 和 `.doc` 现在读不了，只是看得见。

**4. 按扩展名定格式。**
- 简单、可预期。扩展名写错的文件会按那个格式转，转不了就落 `failed`。
- 不在支持列表里的扩展名落 `unsupported`，原因写扩展名，汇报能按扩展名计数。

**5. 引文比对前做固定的统一处理，大小写不变。**
- 子代理读的是脚本转出的文本，引文照抄时最常见的差别是换行、空白、弯引号、破折号、全半角，这些与是否编造无关。
- 统一处理：NFKC；去掉软连字符和零宽字符；弯引号换成直引号，长短破折号换成 `-`，省略号换成 `...`；连续空白换成一个空格。
- 不做模糊匹配。差一个词就是没对上；放宽匹配会把「找不到」变成「找到一句差不多的」。

**6. 功能清单要么全部写入，要么一条都不写；报错列出全部问题。**
- 部分写入会让一部分功能悄悄消失。
- 一次列出全部问题，子代理或主代理一次改完，不用一条一条试。
- `id` 不为 `null` 时也要在文本里，防止编出文档里没有的编号。
- 代价：一条改不对，整份清单都写不进去。skill 里写明：改不对的那条就删掉，不能为了通过而改成文档里没有的话。

**7. 位置由脚本算。**
- 行号：引文第一次出现处在文本里的行（`.docx` 一段一行，所以就是段落序号）。
- PDF 页码：数第一次出现处之前的换页符。
- `occurrences`：引文出现了几次。大于 1 时，读者知道位置是第一次出现的地方。

**8. 列功能按文档自己的结构，分批交给子代理。**
- 有编号的用例或需求，一条一个；用例里的步骤和业务规则属于这个用例，不单列。没有编号时，一个描述功能的小节（有自己标题的部分）一个，小节里的加粗标签、列表项、步骤和分支不单列。
- 引文从功能自己的标题起；同名标题在文档里重复时，引文从标题延续到这一节自己的第一句。不许从前一节的文字开头凑出唯一的引文，否则记下的行号落在别的功能里。
- 读到的文档按文本字数分批，每批不超过约 20 万字符，一份文档不拆开；每批一个子代理，同时派出。
- 文档内容是不可信数据：子代理只把它当原文，不执行里面的指令。

**9. 产物与文本放在项目的 `.excavator/` 下，文本按原路径存放。**
- 后两步要把功能对到这个项目的代码，chat 也从 `.excavator/` 读。
- 文本存成 `.excavator/doc-map/text/<原路径>.txt`，模型和人都能按原文件名找到。
- 每次 `read` 先写到临时目录，再整体替换旧的文本目录，不留下已删除文件的文本。
- 产物记 `docsRoot` 的绝对路径和每个文件的 `sha256`，后面的步骤据此判断文档有没有变。这会把本机路径写进产物；产物只在本机，不提交。

**10. 功能标题与报告用英文，用户要求别的语言时才换。**
- 参数 `--language <lang>`，与 `/excavator-prd`、`/excavator-figma` 的写法一致；默认英文，文档本身是中文也不改变它。
- 标题按这个语言写：标题本来就是这个语言时用标题原词，否则翻译，产品、功能、模块名照文档写法保留。引文始终是文档原文，不翻译。
- 代码、skill 与测试里不出现中文字符；报告自检里的中文词写成 `\u` 转义，测试守住这一条。
- 代价：中文文档的标题是模型翻译的，不能再拿「标题就是标题原词」来核对；脚本本来就不核对标题，抽查按意思核对。

## Oracle

动手前写定：

- **单测**：
  - 规格里的每个场景；
  - 每种格式各有一个夹具：`.md` 带 BOM，`.html` 带字符集声明、实体与脚本，`.docx` 带制表符、换行、表格和修订删除，`.odt` 带 `text:s`；
  - PDF 与 `.doc` 用 PATH 上的替身工具，测换页符、页码和缺工具的情况；
  - 状态之和等于文件数，不进 `.git`，不跟随符号链接，重跑清掉旧文本；
  - 功能清单的每种错误一次全部报出，产物不变；
  - 统一处理的每一项；位置与出现次数。
  - `.docx` 与 `.odt` 夹具在测试里用 Python 现场生成，仓库里不放二进制文件。
- **独立核对转出的文本**：
  - 语料是复制到 scratchpad 的几个文档目录：
    - 一个开源 Java 病历系统仓库的 `docs/`、`src/site/markdown`、两处 OCAN 文档，以及 80 个表单模板 PDF（当噪声）；
    - sakai-12.7 的 gradebook、sections 规格和 basiclti 文档；
    - go-multirepo 的 4 份 PRD，maui-app 的 16 篇文档；
  - 另写一段 Python：`.docx`、`.odt`、`.html`、`.doc` 用 `textutil` 转，PDF 用 PyMuPDF 转，按词比较；
  - 每份词重合率低于 98% 的文档都逐一看并写明原因；正文漏掉的就是缺陷；
  - 先验装置：在一份 `.docx`、一份 `.html` 的副本里各加一句已知的话，确认我们的文本里有、核对能报出差别。
  - 状态之和等于文件数；每个不是 `read` 的文件都有原因。
- **功能的召回**（动手前定好清单）：
  - 用例文档 `use_cases.docx` 的 `EAAPS-UC-01` 到 `EAAPS-UC-11`，11 条都要列出、`id` 对上；
  - OCAN 需求规格 PDF 的 `UC1` 到 `UC4`，4 条，业务规则不单列；
  - 另外三份没有编号的文档（gradebook 2.0 规格、一份 PRD、一篇 maui-app 功能文档），在运行前由我按小节写出预期功能清单，运行后算召回。
  - 召回是软指标，照实记。
- **零编造**：引文全部由脚本核对；另按文档类型分层抽查标题，每层至少 5 条，看标题说的是否就是引文所在那一段写的。标题说了那一段没有的事，算编造，必须为 0。
- **真实模型**：Sonnet，headless，按上面的语料依次运行，记花费、轮数、各状态计数与召回。

## 验收记录（2026-10-20）

### 转出的文本（任务 4.1）

- 装置：另写一段 Python，按词（NFKC 之后的 `\w+`）比较我们的文本与另一个工具的文本，算两个比例：
  - 对方的词在我们文本里找得到的比例，低说明我们漏了字；
  - 我们的词在对方文本里找得到的比例，低说明我们多了字。
- 另一个工具：`.docx`、`.odt`、`.html` 用 pandoc，PDF 用 PyMuPDF，`.doc` 用 LibreOffice。
  - 与计划不同：计划写的是用 `textutil` 核对，但 `.doc` 本来就是 `textutil` 转的，用它核对就成了自己对自己。
- 先验装置：
  - 在一份 HTML 转出文本的副本里删掉 40 行、加一句话：第一个比例从 0.9422 降到 0.7983，第二个从 0.9988 降到 0.9947，别的文件不变；
  - 在一份 `.docx` 和一份 `.html` 原件的副本里各加一句话，再运行 `read`：两句都在转出的文本里。
- 四个语料共 321 个文件，各状态之和都等于文件数，每个不是 `read` 的文件都有原因：

| 语料 | 文件 | read | empty | unsupported | failed |
|---|---|---|---|---|---|
| 一个开源 Java 病历系统 | 174 | 130 | 14 | 30 | 0 |
| sakai-12.7 | 126 | 22 | 0 | 104 | 0 |
| go-multirepo | 4 | 4 | 0 | 0 | 0 |
| maui-app | 17 | 16 | 0 | 1 | 0 |

- 结果：
  - 文本类 72 份与原文逐字相同；
  - 14 份 `empty` 的 PDF，PyMuPDF 也取不出一个词；
  - 比例低于 98% 的 19 份逐份看过，原因只有四类：
    1. 格式自动生成的编号不在文本里：Word 的列表编号，HTML 有序列表的 a、b、c 与 1、2、3；
    2. `textutil` 把 Word 的域代码（`HYPERLINK`、`PAGEREF`、文献管理器的记录）留在 `.doc` 文本里；一份协议文档里，这些多出的词占我们文本的 59%；
    3. HTML 的 `<title>` 我们保留而 pandoc 不输出；图片的 alt 文字我们不取；
    4. 表单模板 PDF 里有些数字 PyMuPDF 取得到、`pdftotext` 取不到；脚本的文本与 `pdftotext` 的输出逐字节相同，差别在两个工具之间。
  - 第 1、2 类和 alt 文字补进了残余假设（`83e7a395`）。除自动编号以外，没有发现漏掉的正文。
