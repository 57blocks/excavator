# Excavator 统一入口方案

状态：定稿候选，未提交，未实现。2026-11-26。经 Fable 独立评审后修订，评审记录见第 7 节。

## 1. 要解决的问题

- 现在有 20 个 skill、16 个 agent，`skills/excavator/SKILL.md` 一个文件就有 1575 行。用户要自己选 skill，自己记前置条件（要不要先建图？用 Lazy 还是 Full？），还要记每个 skill 各自的参数。
- prd、onboard、explain 这几个散文类 skill 的报告形态是写死的。tour、chat、handbook 的输入来源和产物契约各不相同，不只是报告形态的差别。
- 目标是一个入口：普通问题直接答；要文档时走一条可中断恢复、看得见进度的管线，能产出任意形态的报告。

## 2. 约束（用户定的）

1. **以 skill 为主。** 能由 skill 或提示词在运行时完成的，就不写成代码（即 AGENTS.md 的 AI-first scope gate）。
2. **不直接用 Claude Code dynamic workflows。** 要能在 Codex 上跑。skill 和 agent 里不指定模型。
3. **子 agent 数量和 token 要有控制**，性能和准确性要兼顾。
4. **能探索百万行级的项目。**
5. **能中断恢复。**
6. **复杂任务要能实时掌控进度。**
7. **编造零容忍是最终标准**（可以先产出、标成未核对，最后再核对）。同一请求跑两次，结果要一致。

## 3. 依据（已核对原始记录）

**本仓库实测：**

- **自由写作对比逐项核对流水线**（11-11）：自由写作的覆盖约为 1.6 倍，花费约为十分之一。
- **给写作者接上图 MCP 工具**（11-19）：5 次运行里调用了 0 次。覆盖的差异落在比较器的噪声以内（同一章两次评分相差约 5 个点），不能据此说覆盖下降了。
- **D 组：先写，再由脚本列出未触达的入口，派补写者补上**（11-20）：在 go-multirepo 上，普通章节已经触达 96% 的入口（338/351），补写又加了 11 项，花费是章节总花费的 4%。广度高低取决于写作者手里有没有候选清单；标准写作提示里本来就列了这份清单（`sections/features.md:26`）。
- **读码型运行的花费约等于"轮数 × 上下文"**：一个 88 文件的功能，单个子 agent 用了约 7,900 万 token。所以每节必须按代码量设上限，节数也就会随项目规模增长。
- **hadoop 与 Fineract 花费相近**：这只在"按组查询再做判断"的形态下成立（unused-code），不能套用到枚举题的逐项判断上。
- **归属错误**：引文是真的，但安到了错的主体上。这类问题要靠干净上下文的核验者来判，核验者只拿到"陈述 + 主体 + 所引片段"，做闭合判定（supported / misattributed / overreach / dead-path / unsupported）。脚本闸只是必要条件，不能替代它。
- **问答路由要排在一切前置检查之前。** 派发子 agent 一律在前台。固定格式里的数字一律由脚本打印。

**被删分支 `codex/flow-reconcile`**（本地已恢复，5109babd）：tree-sitter 抽取的流程覆盖不全，需要 AI 补充发现。可以复用的部分有：引文核对、按目录分批、检查点，以及"对上一版结论的处置"账本。

**外部做法**（详见第 8 节来源）：

- **dynamic workflows**：取它"计划可重跑、可续跑"的思路，不用它本身。
- **Anthropic 多 agent 研究系统**：取三点。派多少个子 agent 写成档位规则；警惕"简单问题派出几十个子 agent"；评测用约 20 个真实问题，再加人工检查。
- **LLM 路由**：只按问题分类做路由，遇到复合问题会静默出错。
- **报告生成**：STORM、DeepWiki 和 CodeWiki 都是"大纲 → 分节写 → 综合"。这些产品都不单独测编造。

## 4. 方案

### 4.1 入口：一个小的新 skill，两条路线

- **新增**一个入口 skill，控制在约 150 行以内，分支内容放在单独文件里按需读取。不往 1575 行的建图 skill 里塞，否则每个点状问题都要为它付上下文成本。
- **路线一：回答（默认）。** 点状问题和枚举问题走同一条路线，规则按**答案的形态**来触发，不对问题做分类：
  - 只要答案里有清单、全称（"都""所有"）、否定（"没有""不需要"），或者"没找到"，就必须先跑一条命令得出分母，并输出固定行 `Basis: <命令> → N 项，已判 M 项`。得不出完整清单时，写"仅下限"。
  - 点状答案固定以 `Checked: <查过的路径或模式>` 收尾。
  - 前端提示和后端的强制校验分开写，各自给引用。值来自配置的，写出配置项和默认值。有多条路径的，逐条列出。找不到就说找不到，不猜。
  - 复合问题拆开，逐个回答。
  - 不建图，不检查新鲜度，不读 `.excavator/`。
- **路线二：文档。** 只有用户明确说要文档时才进这条路线，不会自动从回答升级过来。首版只是按名字转交给现有的 skill，并先报出预计花费。

### 4.2 文档管线：在 handbook 上演进，不另起一套

1. **大纲**：用预设，或者用已存的大纲文件。用户自定义的大纲和分配结果都存成文件，第二次运行直接复用，这样跨运行的一致性才有保证。
2. **候选（扩充后冻结）**：
   - 先由脚本列出入口候选。
   - 再派**按区域划分的 AI 发现者**，只输出清单外的操作（id、位置、引文），不写散文，引文由脚本核对。
   - 合并后冻结，作为本次运行的分母。这正是被删分支要补的那块：脚本漏掉的流程。
3. **分配**：脚本按目录把候选折叠成"组 + 计数"的表。主 agent 只写"组 → 节"的规则，由脚本展开并检查守恒。超过规模上限的节，由脚本按子目录再切开。不让子 agent 在组内再做分配。
4. **写作**：每节一个写作者，带着本节的候选清单，从种子文件出发自由读源码，每句话都带 `file:line` 和引文。
5. **检查（脚本）**：检查引文和格式。不通过就带着原因重写一次，第二次仍不通过就标为未通过。
6. **补漏（D 组做法）**：脚本列出本节未触达的候选，补写者只加内容、不删内容。
7. **核验（固定一轮）**：只核验高风险类别，即否定、可达性、触发机制和绝对化的说法。用闭合判定，结果不是 supported 的一律删掉并记账。不跑这一轮的产物，要标明"未逐句核对"。
8. **组装（脚本）**：生成"覆盖与缺口"一节，包括：
   - 候选覆盖率，并分别列出脚本找到的和 AI 发现的；
   - 未触达的候选；
   - 未通过检查的节；
   - 核验删除了多少条；
   - 残余风险。

**候选清单不可能保证是全的，只能保证缺口看得见。**

handbook 的候选脚本按 `entrypoint-catalog.json` 里的模式逐行匹配，现在已经做到三点：

- 识别到的框架只分两类，"有模式"或"没有模式"，没有第三种去向；
- 扫描过的每个文件都落进一个桶；
- 已知的盲区列成 residual，比如跨多行的注册、命名不含 `rout` 的路由文件。

在此之上再加四层：

1. **文件级守恒**：文件清单是完整的（它就是选中源码的全集），候选清单做不到这一点，所以分母放在文件这一层。每个选中的文件恰好落进一桶：
   - 含候选；
   - 被某节引用；
   - AI 看过并写明"不是入口"的理由；
   - 没人看过。

   最后一桶就是遗漏的上界。它按信号排出优先级（是否含框架装饰器、是否有注册调用、是否被路由配置引用），交给区域 AI 发现者处理；处理不完的留在桶里，写进"覆盖与缺口"。
2. **交叉信号**：两个独立来源应该对得上，对不上的地方就是可疑的漏项：
   - 前端发出的请求（relations 已能抽取）找不到对应的后端路由候选；
   - 菜单或路由配置里的项找不到对应的页面候选。
3. **零产出报警**：某个框架或目录被识别到了，产出的候选却是 0，就标成"疑似未识别的写法"，不当作"没有入口"。
4. **按语料实测召回**：在 go-multirepo 等语料上，用独立的事实清单量出召回率，结果只作为该语料上的下限写进文档，不当作对新项目的保证。

**入口只管广度，不管深度。**

入口清单回答的是"有哪些操作"。一个复杂功能里，真正的内容是每个操作内部的字段、校验、后端规则、分支、状态变化和副作用。实测的情况是：

- 最好的一组细节覆盖也只有约 88%；
- 喂入入口加被调函数清单的那组，细节覆盖降到 81%；
- 一个 88 文件的功能，单个子 agent 跑掉了约 7,900 万 token。

所以深度要单独处理：

1. **按操作拆单元。** 复杂功能不让一个写作者包揽，每个操作（入口）一个单元；种子文件数或行数超过上限的，再按子流程切开。另设一个功能级的综合单元，只读各操作单元，不读代码，把它们串成完整流程（handbook 的跨章节和 CodeWiki 的自底向上都是这个做法）。
2. **每个操作套用固定的深度清单。** 字段、步骤、前端校验、后端规则、分支（成功、拒绝、其他、延后）、状态变化、副作用（写库、发消息、调外部、通知），共七类，沿用被删分支的分类。每一类要么写出内容并带引用，要么写明"查过，没有"并说明查了哪里。这一条写在 skill 里，不写成代码。
3. **不从入口可达的行为单独处理：**
   - 事件监听、定时任务、消息消费者本身就是一种入口，进入候选清单；
   - 拦截器、中间件、全局过滤器、切面这类横切行为，只写一次，放在横切章节里，各操作引用它，不在每个操作里重复。
4. **深度补漏要先量再建。** 先在 go-multirepo 上用独立事实清单按七类量出深度召回，看缺口集中在哪一类。只有某一类缺得明显，才考虑让脚本列出该类的信号，然后像广度补漏一样派补写，只加不删。信号的例子：抛错或返回错误的位置、状态和枚举赋值、写库、发布消息。这样避免为猜测中的缺口先写抽取器。

**不采用的做法：** 不派"不看初稿、独立重新发现"的复核者。理由见第 7 节。

### 4.3 代码做什么

只做以下几件，都是已有代码或已有代码的薄封装，**不为覆盖缺口新写抽取器**：

- 候选清单
- 引文核对
- 集合运算：守恒、未触达
- 状态驱动：`next`、`done`、`status`
- 组装

handbook 的 `check` 目前把引文核对和手册专用的规则（版式、禁词）混在一起，要泛化先得把它们拆开，这是一次重构，单独做一个切片。

### 4.4 花费与子 agent

- **规模上限**：每节的入口数和种子文件数都有上限，是确定性的。这是真正能控住花费的杠杆。
- **并发**：默认 1，用户可以调高。注意 handbook 现在的默认值是 3。
- **花费的边界**：会话里的子 agent 没有硬性预算上限，只能在两个任务之间停下来。
- **开跑前报价**：用"节数 × 实测单价"报出预计花费。整仓文档默认要求用户先圈定范围；上千节规模的运行，开跑前先说一声。
- **几种情况下才派子 agent**：一节的工作量装不进主上下文、区域内的 AI 发现、闭合核验。

### 4.5 百万行

- 回答路线：点状问题按问题取证。枚举问题的花费会随清单规模增长，这一点要实测，不预设"与规模无关"。
- 文档路线：动手之前，先在 hadoop 上做**零模型测量**，看候选数和折叠表的大小，再决定要不要分层分配。

### 4.6 中断恢复

- 运行目录里保存冻结的计划，以及每个任务的状态和产出，写入都是原子的。重跑同一条命令，就从第一个未完成的任务接着做，已完成的任务一个都不重做。
- 首版不做增量。自由读码的写作者事先不知道自己会读哪些文件，事后只能靠它自己报告，不可靠。源码变了以后，按单元判断是否过期（规则见 5.1 第 2 条，依据是引文，不靠自报），由用户选择重跑哪些。

### 4.7 实时进度

- **事件记录不靠模型自觉。** 编排者要拿到任务提示词，就必须调用 `next`，顺带记下开始；交结果必须调用 `done` 或 `check`，顺带记下结束。不调用就拿不到提示词。
- **只追加的 `events.jsonl`**：每个任务都带一个人能读懂的标题，记录开始、结束、检查结果和耗时。
- **`status`（零模型）**：显示当前阶段、完成数 / 总数、进行中的任务和已用时间（对比同类任务的中位数），以及子 agent 正在写的产物文件的修改时间和大小，借此判断它是否还活着。超过中位数 3 倍的任务标为超时。花费只在宿主能提供用量时才显示，拿不到就只报任务数和耗时，不做估算。
- **AI 在每个任务完成后，原样贴出 `status` 的输出。**

### 4.8 现有 20 个 skill

| 类别 | skill | 处理 |
|---|---|---|
| 确定性产物 | `excavator`（建图）、hotspots、unused-code、relations、doc-map、view、domain、knowledge、figma、diff、skopo-* | 不动，入口只按名转交 |
| 有独立契约 | tour（`tour.json` 加验证器）、chat、handbook | 暂时不并入 |
| 散文类 | prd、onboard、explain | 预设大纲的候选 |

- **不改旧 skill 的文件**：多个测试直接读取 `SKILL.md`，改它们就会扩大回归面。
- **退役条件**：要退役一个 skill，先在同一语料上用独立的事实清单做 A/B，编造和遗漏分开统计，打平或更好才能退役。

### 4.9 局部修改

现状：handbook 的 `--features`/`--sections` 能只写部分章节，但已写的章节续跑时会跳过；没有"带意见重写某一章"，章节改了也不会标记依赖它的跨章节。

**怎么指定要改的部分。** 组装时每段带上来源单元的锚点（节 id）。用户可以说节名、引用一句原文，或贴一段文字，由脚本把它映射到所属单元；映射不到唯一单元就列出候选让用户选，不猜。

**意见分三类，处理不同：**

| 类别 | 例子 | 处理 |
|---|---|---|
| 内容 | 审批规则写错了、漏了退款路径 | 只重写该单元：写作者带上意见和原稿，**重新读代码**；意见本身当作待核的说法，不当事实。代码与意见矛盾时，写出代码怎么说并引用，同时在回复里告诉用户 |
| 表达 | 太长、换成表格、换给运营看 | 只改写不重读代码；脚本核对改写前后的引文集合：没删的事实引文必须保留，删掉的要列出来给用户看 |
| 结构 | 拆一节、合两节、加一节 | 改大纲文件；脚本算出受影响的单元，只重跑这些，再检查守恒 |

**改动走同一条管线。** 修改是运行目录里的新任务，经过 `next/done`、检查、补漏、核验、组装，进度和续跑照常可见。不直接手改产物文件。

**版本与回退。** 每个单元保留历史版本（`<id>.v1.md`、`v2`…），可以回退到任一版本。

**依赖变陈旧。** 计划里记录每个任务读了哪些单元（例如跨章节读功能章节）。一个单元改了，读它的单元在 `status` 里标 stale，由用户决定是否连带重跑，不自动扩散。

**意见要留下来。** 用户意见存进运行目录的 `notes.jsonl`，并挂到大纲里对应的节上。整份重跑时，写作者会拿到这些意见，用户改过的东西不会被冲掉。用户满意的节可以**锁定**，之后的重跑不再动它（大纲或代码变了时，`status` 只提示，不改写）。

**用户手改了产物。** 脚本按摘要发现文件被手改：把手改版本当作用户锁定的版本，重新核对它的引文，并在 `status` 里报出不通过的引文，不覆盖用户的修改。

### 4.10 产物形态

- **底稿**：每个单元一个 Markdown 文件，加上一份结构化的元数据（锚点、引文、覆盖与缺口、版本、状态）。局部修改、续跑、核对都作用在底稿上，不作用在渲染出来的文件上。
- **默认渲染两种**：
  - 组装后的 `.md`，有产品视图（去掉引文）和技术视图（显示引文）两个版本；
  - 单文件 HTML：双击就能离线打开，不需要服务器和网络；带导航、表格、图，可以在产品视图和技术视图之间切换，覆盖与缺口单独成一节。现有的 handbook 页面渲染器（`lib/page*.mjs`）就是这么做的，需要先把它从 handbook 专用改成通用。
- **回答路线**：直接回复在终端里，不写文件。
- **不预先做其他格式**：docx、PDF、Confluence 等格式等真有需求再加；Markdown 转这些格式的成本很低。
- **确定性产物**：tour、domain、relations 等产物维持各自的 JSON 契约，仍由 view 打包查看，不并入文档管线。

## 5. 未验证与风险

- **Codex 上的子 agent**：能不能派发、上下文是否干净，都还没验证，而文档路线整个依赖它。
- **区域 AI 发现者**：它到底能补出多少脚本漏掉的流程、要花多少，还没测。先在 go-multirepo 上量一下脚本的漏检率；如果漏检率很低，这一步可以不要。
- **把 `check` 从 handbook 里拆出来**：这是一次重构，成本还没评估。
- **答案形态规则的执行**：模型可能不遵守，靠验收里的变异检查兜底。
- **局部修改把文字映射回单元**：用户贴的文字可能跨两个单元，或者已经被改写过；映射不到唯一单元时只能列出候选。
- **表达类改写会悄悄丢掉事实**：靠改写前后的引文集合对比来发现，但这只能抓到带引文的事实。

### 5.1 第二轮自查：设计漏洞与对策

1. **文档的"两次一致"既没定义，也没保证。** 写作者自由读码，两次写出的散文必然不同。对策：
   - 一致性定义在骨架上：大纲、冻结的候选、分配、每个操作七类各自是"写了"还是"查过没有"。散文不要求一致。
   - 已完成且输入没变的单元直接复用，不重写。
   - 验收：同一请求从头跑两次，操作集合一致，七类状态的一致率达到阈值，不一致的逐条列出。
2. **代码变了，文档怎么办。** 4.6 的"基线一变就全部标 stale"在百万行仓库上等于每次提交都全部失效。对策是按单元判断，依据是引文，可以核对，不靠自报：
   - 它引用的文件变了：stale；
   - 分给它的组里候选有增减：stale；
   - 它所在目录里有未被引用的文件变了：只标"可能过期"。

   只重跑 stale 的单元。
3. **Codex 上派不出子 agent 时，文档路线无路可走。** 对策：`next/done` 发出的每个任务都自带完整的提示词文件和输出位置，不依赖编排者的上下文。执行者可以是子 agent，也可以是每个任务新起的一个无头进程（`claude -p` / `codex exec`）；小规模运行最后还能在会话内串行做。验收：一次文档运行，每个任务都交给新进程执行，结果仍然通过。
4. **枚举题在大仓库上撑爆主上下文。** 比如在 hadoop 上问"哪些接口不需要登录"，N 可能是几千。对策：
   - N 超过阈值时，改为按机制判断。同一个拦截器或注解往往决定一大批路由，所以答案写成"机制 → 影响多少项 → 例外"，花费跟机制数走，不跟项数走。
   - 还是太大，就告诉用户，转到驱动脚本分批执行，可以续跑、看得见进度。
   - 验收加一题：hadoop 上的枚举题。
5. **回答路线与 `excavator-chat` 重叠。** 对策：入口的回答路线作为默认，`chat` 仍可直接调用。两者在同一批问题上做 A/B，回答路线打平或更好，才退役 `chat`。
6. **验收依赖的金标与独立事实清单，没算进工作量。** 每个切片都要独立的真值：20 道点状题的金标、枚举清单、七类事实清单。对策：新增切片 0，在 go-multirepo 上用独立方法建真值集，冻结保存：
   - 由人写；或者让一个看不到我们任何产物的模型在干净环境里跑，再由人抽查。
   - 绝不能从我们自己的产物派生，否则就是自证循环。
7. **一个功能横跨多个仓库。** 目标项目如果前后端分属不同的 git 仓库，现在"一个项目根"的假设就不成立了。对策：引入工作区，即一组根目录；引文路径带上根 id；文件守恒按所有根的并集来算。主要语料 go-multirepo 本身就由多个仓库组成，所以这一项不能推后，要在文档路线的第一个切片里一起做。

## 6. 切片顺序（每片独立可交付）

### 切片 0：真值集

在 go-multirepo 上建立冻结的真值集，供后续所有切片的验收使用：20 道点状题的金标、10 道枚举题的清单、3 到 5 个复杂功能的七类事实清单。建法用上面 5.1 第 6 条的独立方法。产物不进公开仓库。

### 切片 1：入口的回答路线

**不做：** 文档管线、状态脚本和 `status`、改动或退役任何现有 skill、百万行分配，以及产品内的引文核对脚本（先在验收里量引文失败率，大于 0 时再按 scope gate 论证是否落成代码）。

**验收（每条都能变红）：**

| # | 测什么 | 什么情况算红 |
|---|---|---|
| O1 | go-multirepo 上 20 个点状题，金标答案事先独立写好。四类难例（前后端不一致、配置默认值、多路径、绝对化）每类至少 2 题，另加 3 题"代码里没有"的 | 出现任何一条编造就红；遗漏另外统计。由脚本从运行记录里抽出所有 `file:line` 和引文做核对。事先植入一条错误的行号，证明这个检查装置看得见错误 |
| O2 | 10 个枚举题，其中 5 个伪装成是非题或否定问法，对照独立清单 | 缺少 `Basis:` 行；或者 N 与运行记录里那条命令的输出不一致；或者清单外的发现没有单列。变异检查：删掉 skill 里的这条规则，O2 必须变红 |
| O3 | 不触发任何前置操作 | 运行记录里出现建图或新鲜度检查的命令，或者读了 `.excavator/` |
| O4 | 每题跑两次 | 点状题两次的结论值不同；或者枚举题两次的条目集合不同（逐条列出差异） |
| O5 | 规模无关性：hadoop 上 5 题的轮数和 token 中位数，与 go-multirepo 比较 | 超过 go-multirepo 的 2 倍 |
| O6 | 与运行时无关：契约测试断言 skill 里不含模型名和 Claude 专有的工具名；另在 Codex 上实际跑 5 题 | 任何一项失败 |

### 后续切片

- **切片 2**：把驱动脚本（`next`、`done`、`status` 加事件记录）接到现有的 handbook 上。验收：强杀后恢复，零重做；`status` 的输出与事件记录一致；人为制造的慢任务被标为超时。
- **切片 2b**：局部修改（4.9），接在驱动脚本上。验收：改一个单元后，其余单元的文件字节不变；依赖它的单元被标为 stale；意见在整份重跑后仍然生效；与代码矛盾的意见得到带引用的反驳，不被照写；手改过的文件被识别出来且不被覆盖；表达类改写删掉的事实引文被列出（植入一次删除，验证能看见）。
- **切片 3**：把 D 组补写并入 handbook，按操作拆单元并套用七类深度清单；在 go-multirepo 上按七类量出深度召回，决定是否需要深度信号补漏。同时在 go-multirepo 上量出脚本对流程的漏检率，据此决定要不要做区域 AI 发现者。
- **切片 4**：做第一个预设大纲（prd），与 `excavator-prd` 做 A/B，通过了才谈退役。
- **切片 5**：在 hadoop 上做分配阶段的零模型测量，再决定要不要做分层分配。

## 7. 评审记录（Fable，2026-11-26）

**采纳：**

1. **初稿有几处说法超出了证据：**
   - 11-19 的"覆盖下降"其实在比较器噪声以内。
   - D 组在 go-multirepo 上的花费是 4%，+18% 是 5 个功能的 A/B 里的数字。
   - CoVe 和闭合判定都是针对论断去核验，不是"不看初稿、重新发现"，初稿把这点理解反了。
   - "第 1、2 档的花费与规模无关"没有依据。
   - "子 agent 数量跟节数走"对，但节数本身会随规模增长。
   - "代码只做三件事"与管线自相矛盾。
   - "各 skill 只是形态不同"只是部分成立。

   以上都已改正。
2. **路由按答案形态触发、输出 `Basis:` 固定行**，验收可以机械判定。
3. **"组 → 节"规则由脚本展开**，不让子 agent 在组内分配。
4. **进度做成 `next`/`done` 这条唯一路径的副产品。** 不估算花费；用产物文件的修改时间判断子 agent 是否还活着。
5. **首版删去增量**，源码基线变化时只标 stale。
6. **现有 skill 分三类处理，入口新增、旧文件不动。**
7. **自定义大纲和分配结果存成文件复用。**
8. **第一切片只做回答路线**，验收全部换成能变红的 oracle。

**不采纳 / 修正采纳：**

1. **"用 D 组补写替换 AI 复核"**：D 组只能补脚本已经列出的入口。而用户提出 AI 复核，恰恰是因为脚本抽取会漏掉流程（被删分支的出发点），只有 D 组覆盖不了"清单外"。不过 Fable 对"独立重新发现"的反对成立：它要第二次读全部代码，花费约 +100%，结果不收敛，还会破坏一致性。折中做法是**把 AI 发现前移到候选阶段**：
   - 按区域只输出操作清单，引文由脚本核对，然后冻结复用；
   - 后面仍用 D 组补漏、用闭合判定核验。

   而且要先量脚本的漏检率，再决定做不做这一步（切片 3）。
