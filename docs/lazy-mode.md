# Lazy Mode

Excavator analyzes a codebase in two layers: a **fact layer** (files,
symbols, imports, calls — extracted deterministically, never touched by a
model) and a **semantic layer** (summaries, tags, architecture layers —
generated by a model, on top of the facts). Lazy mode is about *when* the
semantic layer gets filled in.

## Lazy is the default

The first time you run `/excavator` in a project, it builds the fact layer
only: a searchable index of every file, function, class, import, and call.
This step is fast and makes **zero LLM calls** — there's no per-file
analysis, no verification pass, no architecture pass.

Once that's done, ask questions with `/excavator-chat` as usual. Structural
questions ("where is `X` defined", "what does this file import") are
answered straight from the fact layer. Questions that need actual
understanding ("what does this service do", "why does this exist") trigger a
small, targeted semantic lookup for just the node(s) involved — generated
once and cached for next time.

This means the initial `/excavator` run stays fast and cheap even on large
codebases, and you only spend model calls on the parts of the code you
actually ask about.

## Modes and flags

| Flag | Scope | Effect |
|---|---|---|
| `--mode=lazy` | this run only | Facts only; semantics filled in on demand. |
| `--mode=full` | this run only | Facts, then generate summaries and architecture layers for every file/symbol that needs them. |
| `--full` | this run only | Same as `--mode=full`, plus a forced rebuild (ignores any existing graph). |
| *(none)* | persistent | Uses the mode stored in `.excavator/config.json`'s `analysisMode`, or `lazy` if nothing is stored yet. |

`--mode` and `--full` only affect the current run — they are never written to
`config.json`. To change the persistent default, edit `analysisMode` in
`.excavator/config.json` directly.

Precedence, highest first: `--full` > `--mode=lazy|full` > stored
`analysisMode` > default (`lazy`).

## On-demand semantics vs. Full

- **Structural questions** (location, imports, direct callers, "what
  functions does this class have") are answered instantly from the fact
  layer and the source index — no semantic generation, no model call for the
  lookup itself.
- **Semantic questions** (summaries, purpose, business meaning) generate a
  node-local summary the first time they're asked, and cache it in
  `semantic-cache.json`. The next question that touches the same node (as
  long as the underlying file hasn't changed) reuses the cached summary
  instead of regenerating it.
- **Full mode** (`/excavator --mode=full` or `/excavator --full`) instead
  pre-generates summaries for every file and symbol that's missing or
  out of date, plus architecture layers, up front — useful before a review or
  when you want the whole picture cached in advance.

Either way, the semantic layer never overwrites the fact layer: summaries and
tags live in `semantic-cache.json` and `semantic-graph.json`, separate from
`knowledge-graph.json`'s facts.

## Worktree behavior

If you run `/excavator` inside a git worktree (not the main checkout), its
`.excavator/` data directory is written **inside that worktree**, not
redirected to the main checkout. The knowledge graph in that `.excavator/`
corresponds only to that worktree's own revision, so two worktrees on
different branches never overwrite each other's graph.

The trade-off: deleting the worktree deletes its `.excavator/` cache along
with it. This is a deliberate choice — favoring a graph that's always
correct for the revision it describes over cache reuse across worktrees.

## Freshness

Every consumer (`/excavator-chat`, `-diff`, `-explain`, `-onboard`, `-domain`)
checks freshness the same way: by comparing the current source revision
against the `sourceRevision` recorded in `source-manifest.json` the last time
analysis ran.

- In a git repository, the revision is the current HEAD commit. Uncommitted
  changes (staged, unstaged, or untracked) don't affect it — Excavator always
  analyzes committed content, and tells you so in the terminal.
- In a plain (non-git) directory, the revision is derived from the content of
  every tracked file, so any edit, addition, or deletion changes it.

When the current revision no longer matches what's recorded, Excavator
re-syncs the fact layer (and drops any semantics that no longer match the
file they were generated from) before answering — so an answer is never
based on stale facts.
